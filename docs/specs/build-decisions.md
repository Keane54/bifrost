# Build decisions

This file holds the decisions that the build of each milestone made. Code comments and tests cite them by ID, for example D8 or P3.
An ID belongs to the milestone of the file that cites it. The same ID can mean different things in different milestones.
The design spec has the final text for some of these decisions (sections 18 to 26). Where a later build changed a decision, the spec and the code win.

## M1 data

- Zod: not used. The hand-written checks stay small (spec 14.0 says "decide in M1"). Task 12 records this.
- Settings UI: not in M1. M1 uses the spec defaults as constants (escalation 10 minutes, poll 2 seconds).
- The debug view uses plain CSS. Tailwind comes in M2.

| D7 | The "focused chat window" is the active chat panel of the top frame that is not minimised. | M2 moves a frame to the top on each pointer down. |

| D12 | Open project runs `/usr/bin/open -a <app bundle path> <cwd>`. The list is Finder, VS Code, Zed, and the first installed of Warp, Ghostty, iTerm2, Terminal (spec 12) until Settings exist (M5). | The main process finds the cwd and the app. The renderer sends only IDs. |
| D13 | A session in a git repository can move into `.claude/worktrees/<name>` (M1 finding). The Project column then shows the repository, not `worktrees/<name>`. The Branch column shows `worktree-<name>`. | The last two path parts of a worktree path do not name the project. |

## M4 actions

| # | Decision | Reason |
|---|---|---|
| D1 | All input to a session goes through the main process (`input.send`, `input.interrupt`). The main process writes into the open `chat:` PTY of the session, or else into a hidden `send:` attach that it opens and closes. The renderer reports the agent view of a chat window with `pty.setBlocked`. The renderer can use only `chat:` views. A chat attach waits until the hidden send of its session ends. | One place checks the red box, the ready time, the write order and one attach for each session (spec 8.4). |
| D2 | An attach is ready after its output was quiet for 1.5 s one time after its open. The wait stops after 15 s with no write. Text goes as a bracketed paste, then CR after 300 ms (the M0 Q5 form). A slash command uses the form of the Task 1 ruling. The hidden attach opens at the size from `readSessionSize` (M3), or Bifrost sends nothing. It closes with SIGHUP 1 s after the last write. | Spec 8.4 and the M3 finding: an attach sets the session size. A busy session never gets quiet, so a send needs a limit. |
| D3 | Bifrost removes ESC and the other control characters (not tab and line feed) from the text. It refuses empty text and text over 20,000 characters. A red box blocks Send message, Run slash command and Rename, not Interrupt. Interrupt sends one Esc. A second Interrupt within 1.5 s has no effect. One action at a time runs for each session. | Text cannot press keys. Esc is a deliberate stop. Two Esc open the rewind menu. A second Resume starts a copy (spec 4). |
| D4 | The Resume all candidates are `lastActive` in `registry.json`. An owned session goes in when a sample shows it with a PID. It goes out after it was parked for 60 s while Bifrost runs, or at once after a Stop or a Delete in Bifrost. At start, Bifrost keeps the loaded list as the candidates of this run. | Sessions end some seconds before Bifrost quits when the computer restarts (spec 18 item 8). |
| D5 | Delete runs `claude stop` for a session with a process, then `claude rm`, then removes the session from the started list, the names, the priorities and `lastActive`. A row without a short ID is only removed from Bifrost. The confirmation names the git worktree and the branch that `claude rm` deletes. Delete closes the chat window. Stop keeps it open. | The M1 clean-up order. `claude rm` deletes the worktree and the branch (M1 F4). |
| D6 | Take control checks that `ps -o comm= -p <pid>` gives `claude` before SIGTERM. After the process ends, Bifrost marks the session as started, so a failed resume leaves a parked row. The registry parks a started session of any kind. Bifrost waits up to 30 s for each new entry on the registry updates, with no extra `claude agents` process. New session and Take control open the chat window. Resume and Resume all do not. Resume starts the attach of an open chat window again. | No signal to a reused PID and no lost session. Spec 13 allows one `claude agents` process. Spec 18 item 6 and 9.2 step 7 name only these two. |
| D7 | Terminal apps: one `ps -axo pid=,ppid=,comm=` read for new external PIDs. The walk runs in memory. The outermost `.app` of the path gives the name and the bundle. The icon comes from Electron `app.getFileIcon`. Open in terminal (owned) opens a `.command` file with `open -a <app>` when Task 1 shows that the app runs it. Else Bifrost brings the app to the front and copies `claude attach <id>` to the clipboard. | One process read and no library. No documented method types into each terminal app (spec 4). |
| D8 | New session: the models are Default, Opus, Sonnet and Haiku. The permission modes are the `claude --help` choices without `bypassPermissions`. Default gives no flag. A name or a prompt cannot start with `-`. The worktree option passes `--worktree <name>` (Task 1 ruling). The dialog history (directories, model, mode, recent slash commands) goes in `ui-state.json` under `history`. The slash favourites are the spec default list until Settings (M5). The New session and Resume all buttons go in the side bar. | A fixed list stops a free flag. `--permission-mode bogus` exits 0 (M0). Spec 9.5 gives no place for the two actions without a row. |

## Live details

| # | Decision | Reason |
|---|---|---|
| D1 | Names and paths as in Global Constraints. The marketplace name `bifrost-local` is not `bifrost`, so a clash with another marketplace is less likely. Bifrost refuses a `bifrost-local` marketplace that has another path. | A fixed ID for the CLI calls. `marketplace remove` uninstalls every plugin of that marketplace. |
| D2 | The source of the mod is `resources/live-mod/` (electron-builder already unpacks `resources/**`). Bifrost copies exactly four files (`MOD_FILES`) to `~/.bifrost/mod` and adds that folder as the marketplace. Claude Code reads a plugin of a folder marketplace in place. At each start, when the plugin is on and the folder differs, Bifrost copies the files again. A running session gets the new files after `/reload-plugins` or a restart. | A path that does not move with the app, has no spaces, and is not inside a signed app bundle. No version bump is necessary for an in-place plugin. |
| D3 | Wire kinds: `session.start`, `session.end` (`reason`), `turn.start`, `ask`, `tool.done` (`tool`), `permission` (`tool`), `turn.complete` (`reason`, `answer`), `stop.failure` (`error`), `usage` (`model`, `context`, `costUsd`, `rateLimits`). Each line also has `v`, `kind`, `sid`, `at`, `seq`. The mod sends facts. The main process maps them (Task 1 table). | A thin mod. A change of the box rules needs no new mod. |
| D4 | Order: the registry drops a state event that is older than the newest applied event of the session (`at`, then `seq` when both events have one). | Each send is its own request. Two sends can arrive in the other order. One producer for each session makes "newest wins" correct. |
| D5 | Events that are not `classic.*` give all states. `classic.PermissionRequest` only makes the red box for a permission prompt faster (it arrives before the dialog). `classic.StopFailure` only repeats the error of `turn.complete`. `tool.check` gives no box, because in auto mode an `ask` goes to the classifier. Fallback where the guard `cc-plugin-sec-default` skips `classic.*`: the poll gives the permission red box within 2 s, and nothing else changes. | Spike: `classic.*` hooks do not run on Team or Enterprise logins. The poll already gives `waiting`. |
| D6 | Turn ends of the main loop: `answer` and `refusal` give a yellow box and keep `answer` as the last message. `aborted` gives `idle`, no box, and keeps the partial answer (the M1 hooks also gave no Stop for Esc). `error` gives the red error box. A subagent turn (`agentId`) changes nothing. `tool.done` of any loop gives Working (as `PostToolUse`). `ask` gives the red prompt box. | Parity with the M1 hook rules (spec 6.2, 7). A stop by the user needs no alert. |
| D7 | `session.start` from the mod only ends the parked state. For a running session it changes nothing. | The mod runs `session.start` again at each reload. A reload must not clear a box. A resume of a parked session starts a new process. |
| D8 | Usage comes from `session.start`, `session.measure`, one read 2,500 ms after each main-loop `turn.complete`, and a 30 s heartbeat. A usage line is not activity (`lastActivity` ignores it). The registry keeps the last usage line of each session and maps the model ID to a display name (`modelName`). | Spike gap 2: the cost changes about 2 s after the turn. Without the heartbeat, idle rows have no model, context or cost after a Bifrost start. The heartbeat also keeps the `live` flag of an idle row. |
| D9 | Bifrost listens on the socket only while the plugin is on (or the plugin state is unknown and the mod folder exists, or `BIFROST_LIVE_LISTEN=1` is set for a check). Turn off stops the server at once. Then the sends of running sessions fail in about 1 ms. | `enabledPlugins` does not reach a running session. The server is the switch that acts at once. |
| D10 | Install, Turn on and Remove first remove an old hook install with the M1 `uninstall`. A failure stops the action, and Bifrost then runs no `claude plugin` command. Bifrost no longer installs hooks or the wrapper. It makes no `active` file, reads no event files or status files, and writes no `quiet` files. It keeps `statusline-original.json` and the backups. | The user's decision: the mod replaces the hooks and the wrapper. One data path. An old install without `active` does nothing. |
| D11 | API for M5a: `live.status()`, `live.install()`, `live.enable()`, `live.disable()`, `live.uninstall()`, each with `LiveStatus` (Task 6). `enable` refuses when the plugin is not installed. A Live details switch in M5a calls `install` when `plugin` is `not-installed`, else `enable` or `disable`. | A clear API. M5a owns the UI. |
| D12 | Rate limits: the parser keeps `five_hour` and `seven_day` as `RateLimits` (the type that M5b Task 1 names) and drops other windows. The registry keeps them in the usage of each session. This plan adds no Usage HUD. | M5b reads them from the registry, not from status files. |
| D13 | New session always passes `--settings NO_STATUSLINE_SETTINGS` (Task 7). M4 passed it only when the wrapper was not installed (spec 22). After this plan, Bifrost never installs the wrapper and reads no status files, so the wrapper gives Bifrost nothing. Resume and Take control still add no flags. | O4 option a. The user chose "flag only without the wrapper" while the wrapper still gave Bifrost the usage data. The mod now gives that data. |
| D14 | The spec gets a new section 23 for this plan. Section 22 (M4) keeps its text, with a note that section 23 changes its statusline line. | M4 already used section 22. |

## M5a settings, keys and alerts

| # | Decision | Reason |
|---|---|---|
| D1 | The main process keeps `settings.json` in userData. The renderer reads it with `settings.get` and `settings.onChange`, and writes with `settings.set(patch)`. The main process refuses a patch with an unknown key or a bad value. A bad value in the file gives the default. The display mode stays in `window-state.json` (M2). The Display mode row uses the M2 `display` API. | The main process needs the poll interval, the escalation time, the login item and the alert settings. One source for the mode. |
| D2 | A change applies at once. Escalation time: the next registry tick. Poll interval: the next active poll. Snap distance: the next drag. Terminal font: each open chat window refits. Start at login: Bifrost calls `app.setLoginItemSettings` only when the setting changes, only in the packaged app and not in the test home. At start, the real login item state wins over the file. | No restart. System Settings > Login Items can also change the item. A dev Electron binary must not become a login item. |
| D3 | `settings.keys` holds only the changed slots (slot ID to binding, or null for no key). Each slot ID is a storage contract. The effective map is the default map plus these changes. Bifrost does not use the TanStack app hotkeys catalog or `customHotkeys`. | The main process also reads the keys for the menu accelerators. New defaults reach the user. |
| D4 | A binding is a TanStack chord string with `Mod`. Modifier order: Mod, Control, Alt, Shift. Letters are upper case. The recorder records physical codes. `recordedToBinding` changes `[KeyS]`, `[Digit1]` and the punctuation codes to key names, so recorded keys and defaults compare. | TanStack matches a logical key and falls back to the code for Option keys. Physical and logical bindings do not compare (library note). |
| D5 | All Bifrost hotkeys listen on `document` in the capture phase, with `ignoreInputs: false`, `preventDefault: false`, `stopPropagation: false` and `conflictBehavior: 'allow'`. The callback finds the focus zone. Only when `keyAllowed` is true does it call `preventDefault`, `stopPropagation` and the command. | xterm.js never sees a Bifrost key, and it gets every other key unchanged. One function holds the spec 9.3 rules. |
| D6 | Focus zones: `modal` (a dialog, a menu or a listbox) takes no Bifrost key. `chat`, `send-box`, `text`, `control` (a button, a link, a checkbox, a tab) and `other`. Esc clears the selection in `other` and `control`, leaves the send box in `send-box`, and does nothing in `chat` and `text` (a text field keeps its own Esc). Enter and Space on a control stay with the control. | Base UI dialogs and menus handle their own keys. The M3 tab rename field uses Esc to cancel. |
| D7 | Close panel (Cmd+W) and Toggle Fullscreen (Cmd+Ctrl+F) stay menu accelerators (M2). Their accelerators come from the key map. The renderer does not register them. The key editor refuses the keys of spec 9.7 and the menu keys Cmd+Z, Cmd+Shift+Z, Cmd+X, Cmd+C, Cmd+V, Cmd+A, Cmd+Option+H, Cmd+= and Cmd+- (Zoom In and Zoom Out of the Interface scale, spec 12). Bifrost removes `optimizer.watchWindowShortcuts`. The dev Reload item gets F5. (Changed 2026-11-06: Cmd+= and Cmd+-.) | CDP and the renderer cannot press a menu key (M2 finding). The optimizer blocks Cmd+R in production. One owner for each key. |
| D8 | A key that is also a hold key (O, M, I, J, X, 1 to 5 by default) acts at the keyup, and only when no row click used it during the hold. A hold action needs exactly one held hold key that went down in the `other` zone. It acts on the clicked row and does not change the selection. | O alone must not open the selected session when the user holds O to click another row. |
| D9 | The focused Overview is the active Overview panel of the highest frame that is not minimised and shows an Overview. Cmd+0 with no Overview opens `overview:1`. Row steps stop at the first and the last row. Overview tab steps and stack tab steps wrap. Cmd+Option+S opens the Layout menu with the name field focused. Cmd+Option+n loads the n-th saved layout in the list order. | Spec 9.4 gives the keys, not these edge rules. M2 already moves a frame to the top on a click. |
| D10 | The setup dialog shows when `setupDone` is false and `live.status()` gives `plugin` `not-installed` or `unknown`. "Turn on Live details" calls `live.install()`. It and Skip set `setupDone`. Esc does not close the dialog. A plugin that is `enabled` or `disabled` sets `setupDone` with no dialog. The dialog lists the steps: the old hook removal (only when `oldInstall` is true), the folder `~/.bifrost/mod`, and the `claude plugin` commands. After a good install it shows the reload note and a Done button. (Changed 2026-11-06 for Live details, Live D10 and D11.) | Spec 11.1 after the Live plan. The dialog needs a choice. |
| D11 | Live details notice: `not-installed` gives "Not installed" with an Install button and no warning. `disabled` gives "Off" with Turn on and Remove. `enabled` and listening gives "On" with Turn off and Remove. `unknown`, `enabled` without a listener, and `enabled` with `modCurrent` false give a warning with the reason. `oldInstall` true gives a warning that Install or Turn on removes the old hooks first. A Claude Code version below 2.1.281, or no `claude`, gives a warning. The side bar Settings button shows a white dot for a warning. (Changed 2026-11-06.) | Spec 11 and 12 after the Live plan. After Skip, Live details off is the choice of the user. |
| D12 | The test home: `BIFROST_TEST_HOME=<absolute dir>` makes Bifrost use `defaultPaths(<dir>)`. So `.bifrost`, `.bifrost/live.sock`, `.bifrost/mod` and `.claude/settings.json` are under `<dir>`. Bifrost also uses `<dir>/user-data` as userData, the first `claude` on `PATH`, and the env of the process. It never sets the login item. The value cannot be `/`, the real home or a parent of the real home. Keep the path short: the socket path must stay under 100 bytes. (Changed 2026-11-06: the socket and the mod folder.) | The controller and the M5b smoke test can click Install and Remove with no risk to the user's files. A second userData gives a second single-instance lock. |
| D13 | Alerts run in the main process. A new box is a new `(box, boxSince)` pair of a row. The first registry update after the start only records the boxes. A notification is silent, shows only when the window is not focused, and shows at most 3 for one update (more give one summary). The sound is `/usr/bin/afplay /System/Library/Sounds/Ping.aiff` for a new red box (also an escalated box), at most one each 2 seconds. A click shows the window, selects the session and runs Open. | One place sees all rows, also when the renderer is busy. Bifrost does not copy EVE sounds. An escalation is a new red box (M1 state machine). |
| D14 | Terminal app and Default app for "Open project" store `null` for the spec default rule. The Open project app list uses the chosen terminal app. Cmd+Shift+O and P open the project in the default app. | Spec 12 gives a rule, not a fixed app. |
| D15 | Settings is one panel, `settings`, with four sections as tabs: General, Slash commands, Keys, Live details. The `integration` panel kind and `IntegrationPanel.tsx` (with the Live debug block of the Live plan) go away. M4 already passes `ctx.labels` to each `actionLabel`, `buttonTip` and `confirmFor` call. M5a replaces the fixed `LABELS` constant of `actions-context.tsx` (and its import in `RowMenu.tsx`) with the `labels` setting, and the key editor uses it too. Panel titles stay plain. (Changed 2026-11-06.) | Spec 12 has one Settings. The debug panel is from M1. Spec 9.1 names menus, buttons, tooltips and dialogs, not panel titles. |
| D25 | In a test home, each `claude plugin` command runs with `HOME=<test home>` and `CLAUDE_CONFIG_DIR=<test home>/.claude` in its env. Each other `claude` call (the session lists, attach, the actions) keeps the env of the process. Recommendation: accept. The controller confirms it in Task 9 Step 3 with the SHA-256 of the user's three Claude files. If a plugin command still changes a real file, stop and record it. | A plugin command at user scope writes to the Claude config folder. The docs do not say which variable `claude` reads, so the env sets both. The session list must stay the real one, so the check app shows the `bifrost-test-` rows. |
| D26 | The `escape` key callback calls `preventDefault` but not `stopPropagation`. Each other key keeps D5. A Watchlist row click also calls `holdClick` first, as an Overview row does. Recommendation: accept. | The M4 Watchlist drag cancels on an Esc `keydown` listener on `window` (`WatchlistPanel.tsx`). A capture listener that stops the event would block it. Spec 9.4 says "click a row", and the Watchlist has rows. |
| D27 | In the `control` zone, Tab and Shift+Tab stay with the browser and move the focus, as Enter and Space stay with the control. Recommendation: accept. | The Overview Settings panel, the tab colour swatches (roving focus, 2231a0a) and the Settings panel need Tab to move the focus. Spec 9.4 gives Tab for the Overview tabs, which still works in the `other` zone (Cmd+0 focuses the rows). |

## Performance

| ID | Decision |
|---|---|
| P1 | `PtyManager` gets `list(): Array<{ viewId: string; pid: number }>`. The monitor never sets the single-slot `onData`, `onClose` or `onExit` callbacks. |
| P2 | Orphan terminal: the renderer reports the IDs of its open chat panels on each change. A `chat:` PTY whose view ID is not in that list for more than 60 s is an orphan. A `send:` PTY that stays open for more than 60 s is an orphan. |
| P3 | CPU of a process from `ps` is the change of its cumulative CPU time (`time=`) divided by the time between two samples, because the `%cpu` of macOS `ps` is an average. Electron processes use `getAppMetrics()` `cpu.percentCPUUsage`. |
| P4 | Bifrost RAM is the sum of `getAppMetrics()` `memory.workingSetSize` (KB) of all Electron processes and the `ps` RSS (KB) of the PTY processes. The two measures differ a little; the plan accepts that. |
| P5 | One health log (`src/main/performance/health-log.ts`) gets all events: poll results, save results, crashes and Live details start errors. Each existing module gets one optional dep (default: no-op) and calls it. |
| P6 | A save failure gives one reason for each store while its last failure is less than 60 minutes old: "Bifrost couldn't save <store> at 14:05." A later good save of the same store does not clear it early. The stores: settings, UI state (layouts), registry, window state, Reviews state. |
| P7 | Poll results: the session list counts each active poll. Reviews counts `error` availability as a failure and `no-gh` or `logged-out` as no data. Account usage counts a fetch error, a 5xx answer and a timeout as a failure, and a 401, 403, 429 or missing token as no data. Service status counts a round where every service failed as one failure. While offline, the network parts (Reviews, account usage, Service status) give no failure. |
| P8 | A crash is `render-process-gone` of the main window, or `child-process-gone` with `type === 'GPU'`, with a reason other than `clean-exit`. No load event counts. |
| P9 | The renderer reports `{ showing, focused, chatPanels }` on each change, and the frame rate once a second while showing and focused. Main samples every 2 s while `showing` is true, else every 15 s. |
| P10 | `UiStore` gets `performance: { detailsOpen: boolean }` with the default `false` and a parser. |
| P11 | The Reviews poll asks `rateLimit { cost limit remaining resetAt }`. `PollData` gets `rateLimit`. `ReviewsWatcher` gets `rateLimit(): RateLimit | null`. With Reviews off and the panel showing, the monitor runs `gh api rate_limit` (it costs no points) at most every 60 s, through the same `createGh` instance (hoisted in `ipc.ts`). |
