Other facts:

- The first `claude --bg` or `claude agents` starts the shared background service. All later background sessions get the environment of that first caller.
- A new background entry has no `pid` and no `status` for about 2.5 s. The parser in `src/main/claude/agents.ts` skips it during that time.
- After `claude stop` or a service stop, an `--all` entry has no `pid` and no `status`. Its name can be missing.

## How to read this file

- The scripts are in `scripts/m0/`. Run each script with Electron as Node, because node-pty uses the Electron ABI: `ELECTRON_RUN_AS_NODE=1 ./node_modules/.bin/electron scripts/m0/<name>.ts`.
- The scripts did the plan steps without the harness window. Each attach is a node-pty PTY of 120 x 32. A headless xterm.js 6.0.0 (the package that Bifrost uses) reads the output. The xterm.js replies to terminal queries go back to the PTY, as in the app.
- Each action on a session goes through `assertTestTarget` in `scripts/m0/lib.ts`. The check reads `claude agents --json` and accepts only one entry with a `bifrost-test-` name. It refuses `bifrost-test-idle`. `scripts/m0/check-safety.ts` showed that it refuses each real session.
- "the user checks by eye" marks a result that a script cannot decide.
- Code spans quote CLI output exactly. `<U+2014>` in a quote marks an em dash character in the CLI output. This file does not use that character.

### Environment of each experiment

- Clean env: every process that the scripts started (each `claude` CLI call, each attach client and each interactive session) got `cleanEnv()`. It removes `CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_EFFORT`, `CLAUDE_PID`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `TERM_SESSION_ID`, `WARP_*`, `FORCE_HYPERLINK`, `__CFBundleIdentifier` and `ELECTRON_*`. It sets `TERM=xterm-256color` and `COLORTERM=truecolor`. It keeps `HOME`, `PATH`, `USER`, `SHELL` and `LANG`. All experiments used the clean env from the start, so each experiment has one result.
- Daemon env: a background session does not run under the process that starts it. The background daemon (PID 341, `/Users/dev-user/.local/bin/claude`) started at 15:44:58 from the controller shell. Its env has `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`, `TERM_PROGRAM` and `WARP_*`. A background session process (for example PID 672) has `WARP_*`, `CLAUDE_EFFORT`, `CLAUDE_PID`, `FORCE_HYPERLINK`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_BG_BACKEND` and `CLAUDE_CODE_SESSION_KIND`. The scripts cannot change this env. A restart of the daemon would stop the sessions of the controller and of the user. So all background sessions in Q1 to Q5, Q7, Q8, Q10 and Q11 ran with the daemon env. The interactive sessions in Q6 ran with the clean env.

## Defects found in Bifrost code

The agent did not change `src/`.

1. `src/main/claude/agents.ts` `toEntry` skips an entry with no numeric `pid`. A new background session has no `pid` for about 2.5 s. A resumed session also has none for a short time. All entries that only `--all` shows (`done`, `failed`, `stopped`) have no `pid`. So `listAgents({ all: true })` returns no finished background sessions, and the parked list of section 6.1 stays empty.
2. `src/main/claude/guard.ts` `canOpenPty` matches by `name` among other keys. A resumed session can have no `name`, or `name` equal to its short id, for some seconds. A stopped entry can have no `name`. The guard then refuses the session. This fails safe, but Take control step 6 can fail if it opens the window at once.
