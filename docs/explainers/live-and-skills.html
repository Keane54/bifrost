Live details and the skills

Live details tells Bifrost what every Claude Code session is doing as it happens, and the Bifrost skills give each session a few /bifrost-... commands. Both reach Claude Code as plugins that Bifrost ships inside the app and installs into your home folder, and both are switched on and off from Settings.

The linesA small plugin, the mod, runs inside every Claude Code session and sends one JSON line for each event (a prompt, a tool, the end of a turn, the latest usage) to a Unix socket in ~/.bifrost. Bifrost's Live server turns each good line into an event for the session's row.
The switchesSettings > Live details and Settings > Skills run claude plugin to install, turn on, turn off and remove the two plugins, after copying the app's own files into ~/.bifrost. One plugin lock makes sure only one of these changes runs at a time.
The skillsThe skills plugin is a folder of Markdown files. Claude Code reads it from ~/.bifrost/skills, lists some skills to every session so Claude can start them itself, and keeps the rest for when you type their name.

The big picture

Claude Code never reads a plugin from inside Bifrost's app bundle. It reads installed copies in your home folder, and Bifrost keeps those copies identical to the files it ships. The repo owns both plugins: the four mod files live in App/Bifrost/Resources/live-mod and the skills in App/Bifrost/Resources/bifrost-skills, and a check step fails when the built app carries other bytes than the repo.

How a line reaches a row

The mod is the only part of Live details that runs inside Claude Code. It knows nothing about Bifrost except one socket path and one small request format, which keeps it simple and keeps Claude Code safe if Bifrost isn't running: a line that nobody takes is just lost.

The server reads each connection off the main actor. Only the finished event comes to the main actor, and the first line of a batch starts a 50 ms window, so a flood of lines rebuilds the session list at most once every 50 ms.

The request

The parser takes exactly one form, POST /v1/event HTTP/1.1 with a Content-Length and a JSON body of at most 64 KB, and refuses everything else. That keeps it small and its memory bounded. HTTPRequestParser has the rules.

The line

A line has a version, a kind, the session ID, a time and an order number. session.start, turn.start, tool.done, turn.complete and the others become the events the registry already understands, and a usage line carries the model, the context, the cost and the rate limits.

Who can send a line

Any process of your own user can connect to a socket of your own user, so a line might be forged. Bifrost keeps other users out with file permissions, and treats what a line says as a hint for the display, never as the reason for an action that changes something.

Kept out

Before it listens, the server opens ~/.bifrost without following a link and checks that it's a folder of this user with no access list that lets anyone in. It takes a lock on live.lock, so two copies of the app never race for the socket, and checks that the socket is a socket of this user with mode 0600. A ~/.bifrost that is a link stays refused.

Only a hint

A forged session.end can park a row, but Resume and Delete wait until the session list agrees: no pid, and no entry in its active list, which also covers the moments after a start when an entry has neither a pid nor a status. A row that only the --all list shows, such as every parked session in the first seconds after Bifrost starts or a session that is just starting, gets a fresh read of the active list first ("Checking sessions..."). A forged yellow box can't make Take control stop a session that the list shows as busy, and a send stays blocked while the list shows an open prompt.

Installing and turning on

Each section of Settings talks to its own control: LiveControl for Live details and SkillsControl for the skills. They work the same way, and they share the one plugin lock, because two changes at once could both edit Claude Code's settings or race on the same folder.

The app starts the two controls in the same turn, Live details first, so the lock runs their starts in that order. Bifrost only ever changes its own marketplace: one with Bifrost's name at another path belongs to another program, and every action refuses it before it changes anything.

How skills are found and run

A skill is a folder with a SKILL.md file, whose short frontmatter gives its name, its description and how it may be started. Claude Code finds the skills through the installed plugin, and Bifrost reads the same files from its bundle to show them in Settings.

Listed skills

A skill with disable-model-invocation: false is listed: Claude Code adds its description to every session, so Claude can start it by itself when the work fits, for example /bifrost-humanise or /bifrost-grill. The descriptions of all listed skills together stay under Claude Code's limits, and a repo test checks that.

Called by name

A skill with disable-model-invocation: true only runs when you type its name, such as /bifrost-review or /bifrost-hand-over. It costs a session nothing until then.

Settings > Skills lists the shipped skills with their group, from the bundle's bifrost-skills folder (SkillsList), so the list shows even when claude can't be found. SkillCheck reads the frontmatter with a strict subset of YAML, so every value it accepts means the same to Claude Code. A session that already runs picks up a change after /reload-plugins or a restart.

What the window shows

One live model holds the two statuses and the Claude Code version, and everything in the window that's about Live details reads it, so the sections, the dot and the dialog never disagree.

Settings > Live details and Skills

Each section shows its state, such as "On. 3 sessions are sending live details.", with the buttons that fit it. Install first shows the steps it will take, and Remove asks in Bifrost's own dialog.

The warning dot

While Live details or Claude Code needs attention, the gear at the bottom of the side bar and the Live details tab show a small square. The model reads again on a back-off of 1, 2, 5 and 10 minutes, and when the window gets the focus.

The Setup dialog

At the first start, "Set up Bifrost" offers to turn on Live details and then to install the skills. Skip is a choice too, and the dialog doesn't come back by itself after either. The Introduction row of Settings > General shows it again.

Settings > General

A Claude Code older than Bifrost needs, or one Bifrost can't find, gives a notice at the top of General.

Glossary

Hint, not an authority
Bifrost's rule for what a Live line says: it can change what a row shows, but an action that changes something (Resume, Delete, Take control, a send) waits for the session list to agree.
Live model
LiveModel, the one place in the window for the status of Live details, the status of the skills and the Claude Code version.
Live server
LiveServer, the part of Bifrost that listens on live.sock, checks each line and hands it to the registry.
Main actor
The Swift concurrency name for the main thread, where all the window's state lives. Work that could wait, such as reading a connection, runs elsewhere.
Mod
The Live details plugin: four files, of which hooks/register.ts runs inside each Claude Code session and sends its events.
Plugin lock
SerialLock, which lets one plugin change of Live details or of the skills run at a time. A second change while one runs gets "Another change is still running. Try again in a moment."
Test home
A temporary folder that stands in for your home folder in the tests and the smoke test. Every shared path, and every claude plugin command, stays inside it.
Unix socket
A local connection point that looks like a file. Only processes on the same Mac can reach it, and its file permissions decide which users can.
