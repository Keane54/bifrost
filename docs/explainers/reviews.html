Reviews

Reviews watches GitHub for the pull requests that need you and hands Claude the parts that need judgement: a careful review of someone else's PR, or fixing and answering the comments on yours. Claude works in a locked-down session that can only read its input and write one result file. Bifrost's own code writes everything that reaches GitHub or git, through a small set of closed types that no other code can get round.

The watcherEvery two minutes by default, one GraphQL read through the GitHub CLI (gh) fetches your review requests and your own PRs. Bifrost records what it saw in ~/.bifrost/reviews/state.json, builds the rows of the two tabs, and flashes a request that's new.
The roundsA click on Review, or new comments on your PR once you've allowed Claude to handle them, puts a round in the queue. Each round runs a Claude Code background session, a PR session, in Bifrost's own clone of the repository.
The writesThe session only writes result.json. Bifrost checks it strictly, then leaves a pending review, or commits, pushes and replies, through closed types that only it can use.

The big picture

Reviews has three parties, each with its own limits. GitHub holds the truth about your PRs. Bifrost reads it, decides what needs doing and does every write itself. Claude Code does the thinking, in a session that can't reach GitHub, run your repository's code or touch git, whatever a PR's text asks of it.

Bifrost never works in one of your own checkouts. It keeps its own clones under ~/.bifrost/reviews/repos, and only one copy of Bifrost at a time can run Reviews on that folder (the Reviews lock).

The watcher

Nothing in Reviews starts on a timer of its own except the poll. The watcher is its one owner, so two polls never overlap, and everything else (the rows, the flash, the notifications, the clones) follows from what a good poll found.

The marks go into the state before the rows are built, which is why the first poll after the first turn-on never flashes: every request it sees is recorded as already there. A request flashes when it shows up after that, or when the author asks you again.

What the rows are for

To review lists the PRs where someone asked for your review, with Review, Pause, Approve or Claude's draft as the row allows. My PRs lists your own, with whether Claude is waiting, working, needs your answer or failed. A right-click opens the Bifrost menu with only the items that fit the row.

Refresh and the clones

Refresh polls at once, and a Refresh during a poll runs one more when it ends. After each good poll Bifrost clones any repository it hasn't seen yet and reads Claude Code's trust of each clone, so the Trust needed strip can ask you before a round ever waits on it.

The queue

A round is one run of a PR session on one PR. Rounds wait in one queue and run in at most three slots at a time (Maximum PR sessions in Settings), oldest first. A slot belongs to a round, not a session, so it frees up as soon as the round ends, even though the session stays around for you to read.

What starts itThe roundNotes
Review, or Try again on a failed reviewA review round on someone else's PRNever by itself, and never on a PR whose CI is failing
Handle now, Handle Copilot comments, or Try againA request round on your PRTakes the older and held items too
An answer in the Answer panelA request round on just the questions you answeredYour answer goes into the round's input
A poll with new comments on your PRA request round on the new workOnly while "Handle comments on my PRs automatically" is on and you confirmed it in this app (the consent)

Only comments from trusted people count as work: an owner, member or collaborator of the repository, or Copilot's first review. An outsider's comment still shows on GitHub, but it never starts a round, whatever it says.

Before its session starts, a round makes sure the clone exists and reads its trust again. A clone Claude Code doesn't trust waits for your trust step in the Trust needed strip. The trust panel runs claude in the clone so its own prompt appears in a terminal, and you answer it yourself: Bifrost never types into that terminal and never writes ~/.claude.json.

A PR session

A PR session is an ordinary Claude Code background session, so it shows in the Overview and you can open its chat. Two things keep it safe: the folders it runs in, and the flags it starts with, which Claude Code itself enforces.

The two kinds of session

started with claude --bg, the prompt last
Review session
--restricted, no MCP servers, only the tools Read, Glob, Grep, Write and Skill, no hooks. No shell, no web, so it can't run the PR's code or call gh or git
Request session
--restricted too, with Bash inside Claude Code's sandbox: no settings file loaded, network to package registries only, no writes to .git, no reads of the other PRs' folders, ~/.bifrost or your secret files, and a deny list that includes git push, git commit and gh
Names
<repo>-<number>-review or -request; in a test home each starts with bifrost-test-

Each round starts a fresh session and deletes the PR's previous one first, so an old session can never write into the new round's folders. Neither kind of session can read or write the folders of another PR, and a request session loads no settings file, so nothing in your ~/.claude/settings.json can weaken its sandbox.

Claude Code doesn't announce the end of a turn, so Bifrost works it out from what it can see: the session's row and the result file. It looks again whenever the row changes, whenever result.json changes on disk, and at the next deadline of the rule, with no polling. An idle row with a result that passes the round's check ends the turn at once. A half-written or broken file is no signal at all, and a red box (Claude asking something) ends the round straight away, because a round's session must never need you. The time limits, 30 minutes for the round and 120 seconds for a session that never starts working, are only fail-safes.

The result and Bifrost's writes

The session writes result.json after reading text from the PR, so Bifrost trusts none of it. The check is strict: one failed rule refuses the whole file and nothing is posted, and the reason names only the field or the limit, never text from the file. The result must also hand back the round's token, so a file written by any other session never counts.

If you already have a pending review of your own on that commit, Claude's comments go into it instead, and a fresh read just before each write checks that it's still pending and still yours. When Claude recommends approval and has no summary and no comments, the round posts nothing at all.

After a review round

The row shows Claude's suggestion: Draft ready, Changes required or Approval recommended. Approve, and every change to Claude's draft in the Review panel, needs your click (a user click), and each one reads the PR again first, so a second click never does anything twice.

After a request round

Bifrost commits only the files the result lists, with your git identity, and pushes as a fast-forward, or as a merge when someone pushed meanwhile; never a force push, never to a fork or the default branch. Then it replies, resolves and asks reviewers to look again. Every write is kept in the round's outbox, saved as sending before it goes and as done after, so a quit never posts a reply twice.

The safety surface

The safety rules live in the types, so no feature has to remember them. A GitHub call is a read or one case of a fixed list of writes, a git run is one case of a fixed list of commands, and a check over the source stops any other code from building its own.

NeverWhat stops it
Change GitHub from a readA read is a GitHubQuery; GHRunner refuses one whose text holds the word mutation before gh starts
Merge, dismiss, close, reopen or edit a PR, or edit or delete anyone's commentNo case of the closed GitHubWrite enum does any of these; the only edits touch Claude's own pending draft
Approve or submit by itselfThose writes need a UserClick, which only the buttons of the Reviews panels can make
Force-push, push to a fork, or sign a commitGitCommand has one push form, with no force; the push target is checked with local git first; a signed fix goes only through GitHub's createCommitOnBranch
Commit a workflow file, a .claude folder, a link, a submodule or a file over 1 MiBThe file rules of the fix commit (CommitFileRule), and a commit that holds only the files the result lists
Reach a remote other than GitHub over https, or show a promptEvery git command gets protocol.allow=never with only https allowed, no ssh and an empty askpass; gh runs in the Reviews folder with prompts off and Bifrost reads no token
Answer a trust prompt or write ~/.claude.jsonBifrost only reads that file, with a 20 MB cap; the trust terminal shows Claude Code's own prompt for you to answer
Push to your branch without your say-soAutomatic request rounds need the consent of a confirmed turn-on in this app; the take-over of the Electron state starts with none
Run Reviews twice on one folderThe Reviews lock: a second copy says "Reviews is running in another copy of Bifrost." and does nothing on GitHub
Grow a new way round the typesThe forbidden rules of scripts/check_forbidden.py, which run on every check

The tests follow the same rules: none reaches the network, GitHub or a real repository. The unit tests use an in-process fake GitHub and real git on local repositories, and the smoke test runs the Debug app in a test home against scripts/fake-gh and a local bare repository, where a review round must leave exactly one pending review and nothing else.

Glossary

Clone
Bifrost's own copy of a repository under ~/.bifrost/reviews/repos: a partial clone with no checkout, so it's quick to make and none of the repository's settings or hooks apply.
Closed type
A Swift enum or struct with a fixed set of cases, such as GitHubWrite or GitCommand. Code can only do what one of its cases says, so a new kind of write has to be added to the type, where review and the checks see it.
Consent
autoFixConsent in the state: true only after you turn on "Handle comments on my PRs automatically" in this app and confirm. Without it no request round starts by itself.
Forbidden rules
The rules of scripts/check_forbidden.py (github-write, github-never, git-push, user-click and reviews-process) that stop code outside the closed types from naming a write, building a push or starting its own gh or git.
Input folder
<clone>/.bifrost-io/<number>, emptied for each round. It holds what the session reads and the result.json it writes.
Outbox
The list of a request round's writes, in order, kept in the state with each one marked as waiting, sending or done, so a quit or a crash never sends one twice.
Pending review
A GitHub review that hasn't been submitted yet. Only its author can see it, which is why Claude's review lands as one.
PR session
The Claude Code background session of a round: a review session for someone else's PR, or a request session for yours.
Reviews lock
An exclusive lock on ~/.bifrost/reviews/.lock, held from the open of the state to its close, so only one copy of Bifrost runs Reviews at a time.
Round
One run of a PR session on one PR, from the queue to the writes.
Test home
A temporary folder that stands in for your home folder in the tests and the smoke test. Its clones come from local bare repositories, and every session name starts with bifrost-test-.
Token of a round
A fresh random value in input.json that the result has to give back, so a result written by an earlier session, a stopped one or another PR's never counts.
Trust
Claude Code's workspace trust of a folder, kept in ~/.claude.json. A background session won't start in a folder you haven't trusted, so you trust each clone once.
User click
UserClick, a value that only the buttons of the Reviews panels make. The approve and draft writes need one, so nothing in the background can approve or submit.
