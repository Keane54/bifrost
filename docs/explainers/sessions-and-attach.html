How Bifrost talks to Claude Code sessions

Claude Code runs the sessions, and Bifrost finds them, shows them and types into them. Bifrost only ever connects to a session that Claude Code is running, so closing anything in Bifrost just detaches from it, and the session keeps going.

The processes

To list the sessions, Bifrost runs claude agents as a short-lived command and reads its output. To show a session or type into it, Bifrost starts a claude attach child process for each open view, either a chat window or a hidden attach, and talks to it through a pseudo-terminal (PTY).

The attach child

claude attach <short id>, which keeps one process ID (pid) from start to exit.
  • forkpty creates the PTY and forks a copy of Bifrost to become the child.
  • In that copy, login_tty makes the PTY its controlling terminal.
  • posix_spawn with POSIX_SPAWN_SETEXEC then swaps the copy for claude, keeping the same pid.
  • The child's environment gains TERM=xterm-256color and COLORTERM=truecolor, so Claude Code knows it can use full colour.
A close sends SIGHUP to this pid and nothing else.

Claude Code

Its background service, which Bifrost doesn't own.
The session
An owned (background) session, which keeps running when an attach goes away.
Its terminal size
Any attach can change it, and the new size applies to every client. Bifrost reads it straight from the session's process (SessionSizeReader) and only ever changes it through an attach.

Bifrost forks first because on macOS posix_spawn on its own can't give the child a controlling terminal, and a child without one never receives SIGWINCH, the signal that tells it the terminal was resized. The spawn also runs off the main actor, because an endpoint scanner can hold up every program start while it checks it, which would freeze the interface each time a chat opened.

Finding sessions

The registry (RegistryService) keeps track of every session. It runs four loops that gather what Claude Code reports, and passes the results through SessionRegistry, which holds the rules for matching each report to a row and deciding what state that row is in.

Inputs

  • claude agents --json: the sessions running now
  • claude agents --json --all: every session Claude Code knows about
  • Events and usage from the Live details mod
  • The git branch of each session's folder
  • A clock tick

Only one claude agents process runs at a time, so the active and --all polls never overlap.

Each row keeps the first session ID Bifrost saw for it, even after a /clear or a resume gives the session a new one, so anything stored against the row, such as its name or priority, stays with it. Rows come in two kinds. Owned rows are background sessions that Claude Code's own service runs, and these are the ones Bifrost can attach to. External rows are sessions running in a terminal somewhere else, so Bifrost can show their status but can't attach to them.

Each row also has a state, shown as a label in the session list, and sometimes a box, the coloured flag that tells you a session wants your attention. A session that has ended is parked, and its row stays in the list.

The rules live in MachineState in StateMachine.swift, and docs/behaviour/registry.md covers the edge cases.

Opening a chat window

Each open chat gets its own terminal (ChatTerminal), which attaches to the session once its row is owned, isn't parked and has a short ID from Claude Code (AttachRules.target). The attach always runs in the folder recorded on the row, or in / if the row has none. Moving a chat around the canvas, stacking it, switching tabs, minimising it or tearing it out all keep the same attach, since only opening or closing the chat panel starts or ends one.

Opening the chat and running the session's jobs (queued sends and Interrupts) take turns, so a hidden attach never runs alongside the chat's own. PTYManager.open only accepts a CheckedAttach, and only AttachRules.check can make one, so nothing can open a PTY without the check, and the manager builds the claude attach arguments itself from the checked short ID. If you close the window while the child is still starting, the child gets a SIGHUP as soon as the spawn finishes.

The attach state

Getting a chat window connected takes several steps, and most of them wait on something outside the window, such as the session list, a size read or a new process starting up. Bifrost tracks how far along each window is with a single value, its attach state (AttachState in ChatTerminal.swift). A window is always in exactly one state, and each state carries only the details that matter while the window is in it.

Once attached, the window also has to watch for Claude Code's agent view. Pressing the left arrow on an empty prompt opens it, showing a list of sessions across all projects, and anything typed there doesn't reach this session. So Bifrost watches the screen for it, blocks your typing while it's open, and attaches again to get back to the session. It checks the screen 250 ms after output stops, or at least once a second while output keeps coming, and gives up after 3 reattaches in 60 seconds.

StateWhat it meansWhat it carries
waitingEvery window starts here, waiting for the first session list, for its row to be ready to attach, or for its panel to get a size.Nothing
readingSizeA window that isn't focused reads the session's current size once before its first open, so it can open at that size instead of resizing the session.Nothing
openingThe open is under way: the window waits for the session's queued jobs, then starts claude attach.The task doing the open, so closing the window can cancel it
attachedThe attach is running, and its output is going to the terminal. Whether the screen has shown any text yet (textShown), and the agent view watch (agentView): .free when you can type, .waiting while the agent view is up and the row can't attach again yet, or .gaveUp after too many reattaches
reattachingThe agent view appeared, so the window is opening a fresh attach. Your typing is blocked until it's done.The task doing the new open
endedThe attach stopped, and the window shows one line saying why.That line, and whether the agent view watch had already given up (gaveUp), so the window keeps showing the give-up message
closedThe window has closed, and nothing happens after this.Nothing

Keeping each detail inside the state it belongs to is what rules out nonsense combinations. If the window kept separate flags instead, say one for attached, one for ended and an optional open task, nothing would stop it from being ended and attached at once, or ended with an open still running in the background, and every piece of code would need to check for those mixes. With one state, an open task can only exist while the window is opening or reattaching, an end message only once it's ended, and the agent view watch only while it's attached. Swift also checks that every switch over the state handles each case, so a new state can't be left unhandled somewhere.

A failed open isn't retried automatically, because a retry could keep hitting the same error, so you close the window and open it again instead.

The output drain

Output from the attach is held until the window asks for it, then handed over in chunks of up to 262,144 bytes, with at most one chunk for each turn of the main actor (PTYAttach.output). A sudden burst of output therefore can't freeze the window. And once 1 MiB of output is waiting unread, Bifrost stops reading the PTY until the window has caught up to under 256 KiB. Claude Code's writes simply wait in the meantime, so a slow window never makes the app's memory grow without limit.

The size sync

A session has one size shared by every client, so only the focused chat window changes it. A window without focus takes whatever size the session already has, and zooms out if that doesn't fit its panel, though never below 10%. Every resize makes Claude Code redraw the whole screen, so Bifrost waits until resizing has been quiet for 150 ms and sends only the last size. There's one catch: sending a size the terminal already has produces no SIGWINCH. So when a window gains focus and its terminal already has the right size but the session doesn't, Bifrost first sends a size one row off, then the right size 60 ms later.

Typing without a window: the hidden attach

Sending a message, running a slash command, renaming a session and Interrupt all go through SessionInput as jobs, which run one at a time for each session. If the session's chat window is open, a job types into that window's attach. If it isn't, the job opens a hidden attach: a claude attach with no window, paired with a SwiftTerm terminal that has no view (HiddenTerminalModel) so it can answer the questions Claude Code asks its terminal, such as where the cursor is. Here's what happens when you press Interrupt (Cmd+.) on a session with no window open.

One attach per session

Any attach can resize the session, so Bifrost keeps to one attach per session at a time. A chat window waits for the session's queued jobs to finish before it opens (chatOpening), and any jobs that arrive while it's opening wait for it, then type into the chat's attach.

A hidden attach never resizes the session

It opens at the size the session already has, in the root folder (/), and never sends a resize. If Bifrost can't read the session's size, the job sends nothing and shows "Bifrost cannot read the session size. Open the chat window and send from there."

SIGHUP goes to the attach child only

Closing an attach (PTYAttach.close) sends the hang-up signal, SIGHUP, to the attach child's pid and nothing else. The child leads its own Unix process session, so the hang-up stops with it and never reaches the Claude Code session. Once the child has exited and been reaped, Bifrost never signals that pid again, because macOS can give it to a new process.

Interrupt timing

Interrupt sends a single Esc 300 ms after the attach's first output. It doesn't wait for the output to go quiet, because a working session's spinner never stops. Pressing Interrupt again within 1.5 s does nothing, since two Escs in a row open Claude Code's rewind menu, and the next write after an Esc waits 200 ms so the session doesn't read the two as one key. Ordinary sends work differently: they wait for 1.5 s of quiet output and give up after 15 s. The hidden terminal also stays silent when Claude Code asks whether it supports the kitty keyboard protocol, so Claude Code keeps the plain key encoding and a raw Esc still means the Escape key.

Acting on a session

Everything you do to a session from the window, whether it's a button in the Selected Item panel, a key, an entry in the row menu or the side bar's New session button, goes through one action runner (ActionRunner). It gets the action and the row's ID, never the row itself, so it always reads the row as it is at that moment, works out what the action means for it, asks first where the action needs a yes, and then hands the work to the part that does it. The shell makes the runner at the first change of the session list after Bifrost has found claude, because the session commands and the session input only exist from then on. Until that moment the buttons and keys do nothing.

A dashed arrow back from the dialog is your answer. The cyan arrows are the only places where an action reaches Claude Code.

The send box

The box at the bottom of the Selected Item panel keeps a draft for each session, so switching rows never mixes them up, and a failed send keeps the text. Sending goes through the same SessionInput job queue as everything else on this page: into the chat window's attach when one is open, or through a hidden attach when it isn't.

Stop and Resume

Stop runs claude stop <short id> for an owned session, asking first only while the session is working. It then waits, for 20 seconds at most, until the next poll shows the row as parked, and the session stays locked meanwhile, so a Delete straight after it can't run a second stop. Resume runs claude --bg --resume, waits for the row to run again and restarts its chat window, so an ended window attaches again.

Take control

Take control moves an external session, one running in a terminal of its own, into Bifrost. After you confirm, Bifrost opens the chat window with its loader, checks that the process is still the same claude, sends it SIGTERM (the only signal the session actions ever send to a session), and resumes the session in the background. The loader stays until the chat shows Claude Code, and if anything fails the window closes again.

Delete

Delete checks the worktree for unmerged work first and shows what it found in its dialog. Then it stops the session if it runs and runs claude rm <short id>, and the row leaves the list straight away. A folder that another session still uses is never removed: its claude rm waits until the last session there goes.

How an attach ends

An attach can end from Bifrost's side, when you close a window or quit, or from the other end, when the attach process exits or stops accepting input.

Glossary

Action runner
The one part of Bifrost that carries out the session actions (ActionRunner). Every button, key and menu entry hands it an action and a row ID, and it reads the row, asks where it must and runs the work.
Box
The coloured flag on a row. Yellow means the turn has ended and the session is waiting for you, and red means it needs you now, for example to answer a permission prompt.
Controlling terminal
The terminal a Unix process belongs to. The kernel signals the process through it, for example when the terminal is resized or hangs up.
Endpoint scanner
Security software that checks each program before macOS lets it start, which can make every program launch slower.
External row
A row for a session running in a terminal of its own, outside Claude Code's background service. Bifrost shows its status but can't attach to it.
Hidden attach
An attach with no window behind it. Bifrost opens one to type into a session that has no chat window open, and closes it 1 s after the last write.
Live details mod
A Claude Code mod that sends Bifrost each session's events (a prompt going in, a tool finishing, a turn ending) and usage over a local socket. A session counts as live for 90 s after the mod's last line about it.
Main actor
In Swift, the context that runs on the main thread, where the interface is drawn. Slow work has to stay off it, or the app freezes.
Owned row
A row for a session that Claude Code's background service runs. These are the sessions Bifrost can attach to and type into.
Parked
The state of a session that has ended. Its row stays in the list, and you can resume it from there.
Pseudo-terminal (PTY)
A pair of connected ends that behave like a terminal. The program on one end (here claude attach) sees an ordinary terminal, while Bifrost holds the other end, the master, where it reads the output and writes your keys.
Reap
Collecting a finished child process's exit status. Until then the process stays behind as a zombie, and once it's reaped macOS is free to give its pid to a new process.
Registry
The part of Bifrost that polls claude agents, matches what it finds to rows and keeps them up to date.
Row
Bifrost's record of one session (SessionRow): its IDs, folder, branch, state and box. The session list shows one line for each row.
SIGHUP
The "hang up" signal. An attach exits when it receives one, and the session it was attached to keeps running.
SIGWINCH
The signal that tells a program its terminal has changed size, so it can redraw.
SwiftTerm
The open-source terminal library Bifrost uses to draw a session's screen and to answer its terminal queries.
