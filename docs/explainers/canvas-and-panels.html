Canvas and panels

Bifrost's interface is made up of a few parts, and at the centre of it all is the main window, which holds a thin side bar on the left and a canvas that fills the rest of the space. On the canvas, frames can overlap or snap together, and each frame shows a panel, like a chat or the session list, or even several panels stacked together as tabs (a stack). This page covers how Bifrost models that layout, how a change to it reaches the screen, and how it's saved and brought back the next time Bifrost starts.

One value holds the layout

The whole layout lives in a single value, WindowLayout in the BifrostLayout module, which lists every frame from back to front. Anything that changes the layout does it through an action (WindowAction).

The views follow it

WindowLayoutModel owns that value, and whenever it changes, the model passes the change on to the canvas, then the chats, then the store.

Two files bring it back

The frames and your named layouts are saved in ui-state.json, and the window's position, size and display mode in window-state.json, so everything is back where you left it when Bifrost starts again.

What's on the screen

  1. The main window (ShellWindow), which can't be made smaller than 800 × 500. Bifrost's own key handling sees every key press before anything else does, as keys.md describes.
  2. The side bar (SideBarView), which is 40 units wide. From the top, it has the Overview, New Overview and Selected Item buttons, then New session and Resume all, which is faded here because no parked session is waiting to resume. The buttons of minimised frames come next, and Layouts and Settings sit at the bottom.
  3. The canvas (CanvasView), which draws the frames from back to front (their z-order) over the animated background and tells the layout how much space it has.
  4. A frame (FrameView). The chat frame overlaps two frames below it, so it gets the backdrop blur, while Settings doesn't overlap any frame below it, so it has none.
  5. The title bar (TitleBarView), which shows the panel's title or the frame's tabs, followed by the Panel menu and the minimise and close buttons. An Overview's title ends with the name of its tab set in dim brackets, such as "Overview (Default)", which the Overview part gives through PanelBodies.titleSuffix(for:).
  6. The body, the view that draws the active panel, which here is a chat's terminal. The frame on top gets the bright accent line along its top edge and a cyan glow.
  7. The side bar button for a minimised frame, which brings the frame back when you click it.

How a change flows

Everything you do to the layout, whether that's dragging a frame, clicking the side bar or pressing Cmd+W, becomes an action, which is applied according to a set of layout rules. Once the layout has changed, the views update to match it.

The mouse, keys, menus and the side bar

  • Side bar buttons: the Overview, a new Overview, the panel buttons, restoring a minimised frame, loading a layout
  • Keys and menu items, such as Close Panel (Cmd+W) or opening a chat
  • CanvasView, when its own size changes

3. The rules

In BifrostLayout
  • WindowLayout applies each action
  • FrameDrag follows a single drag from press to release
  • Geometry and Hit handle clamping, snapping, tear-out and blur

After every change, a single handler (Shell.layoutChanged) passes it on to three places, always in this order:

1. CanvasView

Puts each panel's body into its frame and redraws.

2. ChatTerminals.sync

Creates a terminal for each chat that has just opened and gets rid of the terminal of each chat that closed, then sets whether each chat is visible and focused. It runs after the canvas so that a chat is already in the window by the time it gets focus.

3. WindowLayoutModel.save

Hands a snapshot of the layout to UIStateStore to be saved. While you're dragging a frame, saves wait until you let go.

Panels and their bodies

A panel is anything you can open on the canvas. Each one has an ID (PanelID) that says exactly which panel it is, such as the chat for one particular session, and a kind (PanelKind) that says what sort of panel it is and sets its default size. There are 18 kinds in all. In a chat or Show Info ID, the session ID can be written in upper or lower case.

A body lives as long as its panel

The first time a panel appears, the canvas asks PanelBodiesHub for its body, the view that draws the panel's content. From then on, stacking it, switching tabs, minimising it or tearing it out only moves that same view around, so a chat's terminal keeps its state and focus through all of it.

Chat panels

You open a session's chat by double-clicking it in an Overview, which works for any owned session that isn't parked. If the chat is already open, the double-click brings it to the front instead. A chat keeps its terminal even when it's in a back tab or a minimised frame (ChatTerminals.sync takes care of this), and its title follows the session's name.

The session panels read one list

The Event log, the Watchlist and Show Info all read the session rows from the one session list, so none of them keeps a copy that could fall behind. Each body follows the values it shows with Observations: the Event log follows its log and the names of the rows, the Usage HUD follows the session usage and the account poller, and Show Info follows its row and asks the PR lookup for the pull request of the branch.

Panels that never take the focus

The Event log, the Usage HUD, the Watchlist and Show Info show information and take no keyboard focus, so a click on them leaves the keys where they were. The Usage HUD asks the account poller for fresh values each time it shows, and the poller polls at most once a minute.

The layout rules

Every position and size on the canvas is a whole number of layout units. One unit is interfaceScale / 100 points (CanvasMetrics), so it's exactly one point at the default Interface scale of 100% and grows or shrinks with that setting. The cards below cover the main rules, and windows.md lists every edge case.

Open

Opening a panel that's already open restores its frame if it was minimised, brings it to the front and switches to its tab. A new panel opens where it was last time, or, if it has no saved place, centred at its default size. If a frame already sits in exactly that spot, the new one steps 24 units down and to the right until it's clear.

Close

Closing the active tab switches the frame to the tab on its left, or to the first tab if there's nothing to the left. Closing the last tab closes the whole frame, and the panel remembers where the frame was so it can open there again.

Limits

A frame is never smaller than 200 × 120 and always stays inside the canvas. Rects are rounded to whole units and clamped to the canvas, so even a stray half unit in a saved file can't push a frame past an edge.

Snap

When you let go of a frame, it snaps on each axis to the nearest canvas edge or neighbouring frame edge within 8 units, a distance you can set anywhere from 0 to 32 in Settings. While you drag, small arrow marks show where the frame is going to snap.

Stack and tear out

Dropping one frame's title bar onto another's stacks the two frames into one. The drag has to move at least 4 units first, so nudging a frame whose title bar already sits over another one doesn't stack them by accident. To split a tab back out, drag it more than 12 units away from the title bar and it tears out into a frame of its own.

Z-order and focus

The frames are drawn in the order the layout lists them, so the last one in the list is on top (this order is the z-order). Clicking anywhere in a frame, even inside a chat's terminal, brings it to the front.

Minimise and lock

A minimised frame keeps its place in that order but is hidden, and nothing snaps or stacks onto it while it's hidden. A frame you've locked from its Panel menu can't be moved or resized, and it won't give up any of its tabs, either by tearing one out or by stacking onto another frame. When the frame shows an Overview, the same menu also opens that Overview's settings and holds a field for renaming its set of tabs (FrameMenu).

Blur

A frame only gets the backdrop blur while it overlaps a visible frame below it, so a frame over nothing but the background has none. The graphics card has to redo every blur each time the animated background redraws, which means the fewer frames that blur, the less it costs.

The layout always keeps the rect you gave a frame, even when it no longer fits. If the window gets smaller or you raise the Interface scale, the canvas squeezes each frame into the space it has (Geometry.shownRect), which only changes where the frame is drawn, and once there's room again the frame goes back to its saved place.

Dragging a frame

Dragging a frame doesn't change the layout until you let go. While the drag is in progress, FrameDrag works out where the frame would land, and the canvas moves just that one view to follow the pointer. The only exception is a tear-out, which changes the layout part-way through the drag because the tab needs a frame of its own to carry on with.

Tear-out

Pressing a tab in a stack doesn't move anything at first. Once the pointer is more than 12 units away from the title bar, the tab becomes a frame of its own and the drag carries on with that new frame. If you let go before then, it counts as a click and simply makes that tab the active one.

Why cursor rects go off

AppKit rebuilds every cursor rect in the window each time a view moves, and during a drag the dragged view moves on every step. Switching cursor rects off until you let go means a drag runs without dropping any display frames.

Display modes

The window can be in one of three display modes: Window, Borderless or Fullscreen. Borderless is a window style, where the window has no title bar and fills the screen with the menu bar and Dock hidden, so Bifrost can switch into it and back straight away. Fullscreen is macOS's own full-screen mode, which takes a moment and can fail, so DisplayModeController follows the six callbacks AppKit sends around a full-screen change. Because it listens to those, it also notices when you use the green button or press Esc without going through the menu.

One change at a time

Only one change runs at once. A request that arrives during a change waits its turn, a newer request replaces one that's already waiting, and two toggles in a row cancel each other out. Toggling out of full screen takes you back to the mode you were in before, Borderless included, while leaving with Esc or the green button always gives you Window.

What the menu shows

While a change is in progress, the View menu and the saved file both keep the old mode, and they only switch once the change has finished.

When nothing happens

AppKit ignores a full-screen request for a window that's hidden or minimised, so the request changes nothing. A test run (one with a test home folder) never restores a saved full screen either, because native full screen would move the window to a Space of its own and bring it to the front.

The side bar

The Overview button at the top brings the topmost Overview to the front, restoring it first if it's minimised, or opens overview:1 if there isn't one. The New Overview button under it opens another Overview with the lowest free number, and it's greyed out once all 99 are in frames. Below those there's a button for each minimised frame, which brings that frame back. At the bottom, the Layouts button (Cmd+Option+S) lets you save, load and delete up to 20 named layouts, each with a name of 1 to 40 characters. Loading a named layout replaces every frame on the canvas with the ones it saved, and SideBarModel is the only part of Bifrost that writes these layouts.

Menus

Every menu inside the window is a Bifrost menu: a small dark box in the app's own colours and font, with the look and the keys of the Electron app's menus. The Panel menu of a frame uses it, and so do the right-click menu of an Overview row and the Overview's tab menu. Only the menu bar at the top of the screen stays a standard macOS menu. The Panel menu of each frame opens below the frame's menu button, 208 units wide, and holds the Lock check box, plus "Overview settings…" and the name of the tab set for an Overview. menu.md has the full rules.

A panel above the window

A menu is a borderless panel of its own (MenuPanel) that floats above the main window, and each open submenu is one more panel. The rows are drawn in SwiftUI, while AppKit views over them take the pointer and tell VoiceOver that this is a menu. Because it's a separate window, a menu stays inside the screen rather than the window, so near the window's edge it can reach past it.

The focus stays with the window

As with every macOS menu, the main window stays the key window while a menu is open, and it passes each key press to the menu: the arrows, Return, Esc and typing to jump to a row. Only the text box of a field takes the key focus into the menu's panel while it edits, and hands it back afterwards. A press outside, Esc, a choice, switching to another app or the window losing the focus closes the menu, and the old first responder, such as a chat's terminal, keeps or gets back the keys. A chosen row acts after the close, so a dialog it opens keeps the focus.

The row menu of an Overview

Right-clicking a row opens its menu at the pointer (RowMenu). Its entries come from the action model of the session actions, so an entry that's off keeps its place, greyed out, with the reason in its tooltip. The menu shows the row as it was at the right-click, but a choice hands the action runner only the row's ID, and the runner checks the row as it is now before anything happens.

The tab menu of an Overview

Right-clicking a tab of an Overview opens its tab menu at the pointer. The tab bar knows where each tab is, so it finds the tab under the click. A filter or a column is a check box row that keeps the menu open, so you can change several in one go, and the table changes straight away.

Dialogs

The confirmations of the session actions, Rename, New session and the question of Reset all keys are Bifrost boxes inside the window, never sheets, alerts or windows of their own. They all show in one dialog layer (DialogHost), a SwiftUI view that the canvas keeps above every frame. While a dialog is open, the layer dims the canvas with the background colour at 40 % and puts the box in the middle. The side bar stays as it is. actions.md has the full rules.

One dialog at a time

Only one dialog shows at once. A confirmation that's asked for while another dialog is open doesn't show, so its action doesn't run, and the notice line says "Another dialog is open. Finish that one first.". Rename and New session do the same. A confirmation that asks twice, such as a Delete with unmerged work, changes its button on the first click and only takes a second click half a second or more later.

The focus and the keys

When a dialog opens, the layer takes the keyboard focus, and it carries the dialog mark, so the window's key rules treat everything as happening in a dialog and none of Bifrost's own keys act. The focus stays in the dialog while a save or a start runs, and a held key repeats in a field as usual. Esc cancels the dialog. Clicking the dimmed canvas closes Rename and New session but leaves a confirmation open. When the dialog closes, the old first responder, such as the rows of an Overview, gets the focus back.

Saving and restoring

Bifrost keeps the layout and the window's state in two files in Application Support. Every save writes a temporary file, flushes it to disk and then renames it into place, so a file is never left half-written. When Bifrost loads a file, it skips any item it can't read and keeps the rest, and when it saves again, it keeps any fields it doesn't recognise, so a file written by a newer build isn't damaged by an older one. stores.md has the full details.

Layoutany change→500 ms after the last change, held during a drag→SaveQueue→ui-state.json
Boundsthe window moves or resizes→normal window only→after 500 ms→window-state.json
Modea new display mode→saved straight away→window-state.json
Close, quitclosing saves at once→quitting waits up to 2 s for the last saves (QuitWait)→chats detach, and the sessions keep running

Full screen, Borderless and a zoomed window don't update the saved bounds, so only the plain window's size and position are kept. The file measures from the top-left corner of the primary screen, and WindowPlacement converts to and from AppKit, which measures from the bottom-left.

Start-up, in order

  1. Read both files in the background (AppServices.openUIStores()).
  2. Place the window (WindowPlacement.restore). It goes back to its saved bounds as long as at least 100 × 40 of its top strip lands in a screen's work area (the part the menu bar and Dock don't cover), so you can still grab it. Otherwise it opens centred at 1440 × 900. Saved bounds smaller than 400 × 300 are ignored.
  3. Build the canvas and the window, giving the canvas its size first so the layout has real bounds to work with.
  4. Load the saved layout, or if there isn't one, open overview:1 at 16, 16 with a size of 760 × 360.
  5. Show the window, apply the saved display mode, then start the services.

What each file holds

ui-state.json holds a snapshot of the current layout and up to 20 named layouts. It also carries data for features that aren't built yet (each Overview's settings, the history of recent folders, models and slash commands, and the Performance panel's state), which Bifrost keeps exactly as it found it. window-state.json holds the display mode and the window's bounds.

Because Bifrost restores the window itself, macOS's own window restoration is switched off (isRestorable = false). Closing the window detaches its chats, and clicking the Dock icon brings the window and its chats back.

Glossary

Account poller
The part of Bifrost that asks Anthropic for the usage of your account every five minutes while Account usage from Anthropic is on in Settings (AccountPoller). A test home has none.
Action runner
The part of the window that carries out a session action, such as Stop or Delete, for the row as it is at that moment: it asks first where the action needs it, runs the command and shows how it went in the notice or error line.
AppKit
Apple's framework for the windows, views and menus of a Mac app, and for the mouse and keyboard events that reach them.
BifrostLayout
The Swift module that holds the layout model and the rules for changing it. The views that draw the layout live in a separate module, BifrostWindows.
Bifrost menu
The one menu type of the menus inside the window: the Panel menu of a frame, the row menu that a right-click on an Overview row opens, and the tab menu of an Overview tab. It's a box in Bifrost's own colours and font that floats above the window in a panel of its own. The pop-up pickers of the New session dialog and of Settings are the only menus in the window that are standard macOS menus for now.
Body
The view that draws a panel's content inside its frame, such as a chat's terminal. A panel keeps the same body for as long as it's open.
Canvas
The open area of the main window, to the right of the side bar, where all the frames sit.
Cursor rect
An area of a window where AppKit changes the pointer's shape, such as the resize arrows at the edge of a frame.
Dialog layer
The one view above every frame of the canvas that shows Bifrost's dialogs. It's hidden until a dialog opens, and then it dims the canvas and holds the dialog's box.
First responder
The view in a window that gets the keys first, such as a chat's terminal or a text field. Each window has its own.
Frame
A box on the canvas that you can move, resize and overlap with other frames. It shows one panel at a time, and when it holds several, they appear as tabs.
Key window
The one window of the app that gets the keyboard events at a time. macOS shows it as the active window.
Layout unit
The measure used for every position and size on the canvas. At the default Interface scale of 100%, one unit is one point, the unit macOS uses to measure the screen.
Main actor
In Swift, the context that runs on the main thread, which is where all the UI code runs.
Overview
A panel that lists your Claude Code sessions. You can have up to 99 of them open, and each has its own set of up to 12 tabs, which you edit in its Overview Settings panel.
Owned session
A session that Claude Code's background service runs, which means Bifrost can attach a terminal to it.
Panel
Anything you can open on the canvas, such as an Overview, a chat or Settings. A panel always sits inside a frame.
Parked
A session that has ended. Its row stays in the list, and you can resume it later.
Snap
When you let go of a frame, any edge that's within a few units of a canvas edge or another frame's edge jumps onto it, so frames line up neatly.
Stack
A frame that holds two or more panels and shows them as tabs.
Tab
A panel's title in a stack's title bar. Clicking it shows that panel.
Tear-out
Dragging a tab out of its stack so that it becomes a frame of its own.
