Keyboard input

This page covers how the keys you press in native Bifrost (the Swift app) are passed on to Claude Code. Each session you open in Bifrost gets a chat window, which is a terminal connected to Claude Code through a pseudo-terminal (PTY). Most keys end up there, but on the way a key passes through several layers, and any of them can take it first.

One key, layer by layer

A key press works its way down these layers in order, and the note with each one says whether the key can stop there. Plain boxes belong to macOS, purple ones are Bifrost's own key handling, blue ones belong to the chat window, and green is where the key finally arrives.

1

macOS

macOS deals with its own system shortcuts before any app hears about them, so these never reach Bifrost at all.

Stops hereCmd+Tab, Cmd+Space, Ctrl+Space and the screenshot keys (Cmd+Shift+3, 4 and 5).
2

The app menu

When a key press includes Cmd, AppKit offers it as a shortcut to the controls in the window first, and then to the menu bar (MainMenu.swift). The window asks the key filter before its controls, which is how the key recorder gets every key while it records.

Stops hereClose Panel (Cmd+W), Toggle Fullscreen (Ctrl+Cmd+F), Copy, Paste, Undo, Quit, Hide and the Window menu items all take their keys here. While the key recorder records, it takes every key, here or in step 3, and nothing further down sees it.
3

The key filter (WindowKeyFilter)

Every event the window receives goes through the filter first, because BifrostWindow.sendEvent hands it over before the views get a look. For a key, the filter turns the raw event into a KeyEvent and works out the focus zone, which chat has focus (if any), and whether an input method is in the middle of a word.

Passes throughThe filter keeps nothing at this point. It only gathers the facts that the next two layers need.
4

Bifrost shortcuts (KeyLayer)

The key layer finds the binding that best matches the key and runs it, as long as the focus zone allows that shortcut. Row hold keys work a little differently, because they wait until you let go before they act.

Stops hereWhen a shortcut runs (KeyCommands), the key goes no further. Esc is the exception: outside the send box it waits until step 7, so a popover or a drag in progress can use it first.
5

The chat input (ChatTerminal.chatKey, ChatInput)

This layer only applies when a chat has focus. Any key you press stops a dictation that's still listening, and Esc or Ctrl+C also stop the dictation typer, even while it's typing the final text.

Stops hereThe chat input keeps Space while it waits to see whether you're holding it, and while you dictate. It turns Shift+Enter into an escape followed by a carriage return (ESC CR), which Claude Code reads as a new line. It also swallows a Cmd shortcut with a printable key that nothing else claimed, since SwiftTerm would otherwise send it to Claude Code as a kitty key.
6

The views

Next, the key goes to whichever view has focus. In a chat that's the SwiftTerm terminal, which turns the key into the bytes a real terminal would send.

Stops hereThis is where most keys end: a text field types the character, a button is pressed, or the terminal sends its bytes on.
7

The window (BifrostWindow.keyDown)

A key that no view wanted ends up at the window itself, at the end of the responder chain.

Ends hereA waiting Esc acts here, and it will open or close Settings once phase 4 of the rewrite adds that. Any other Esc or Tab goes back to AppKit, which uses them to leave full screen or move to the next field. Everything else is dropped without a beep.
→

The session

The terminal's bytes pass through the chat input (ChatInput.data) and the chat's dictation (ChatDictation.input) on their way to ChatTerminal.send. That writes them to the PTY of the chat's attach, and Claude Code reads them as typed keys.

Waits hereWhile dictation is typing its final text, the keys you press queue up behind it.

What Bifrost reads from a key

For each key event, the filter copies the parts the key rules need into a KeyEvent: the key code (which physical key it was), the text the key types with and without modifiers, which of Cmd, Ctrl, Option and Shift are held, whether it's a press or a release, whether it's a key repeat, and whether an input method is composing. Caps Lock, fn and the keypad flag are left out, because no binding can use them and macOS sets fn on every arrow key anyway. From those values, KeyEvent.key decides which key the rules should treat it as.

You press (US layout)KeyEvent.keyWhy
Return.named(.enter)Keys with a name, such as Enter, Tab, the arrows and F1 to F12, are reported by that name.
Left Shift alone.modifier(.shift)Pressing or releasing a modifier on its own counts as that modifier's key going down or up, and the left and right keys are told apart.
Option+E.deadIt's a dead key, so it types nothing until the next key.
Ctrl+C.text("c")With Ctrl or Cmd held, Bifrost uses the text the key types without modifiers, so a control character can't hide which key you pressed.
Cmd+Shift+M.text("M")Shift still counts, which gives a capital M.
Option+O.text("ø")Without Ctrl or Cmd, the key is simply the text it types.

Shortcuts and where they work

Slots and matching

Every shortcut Bifrost knows about is a slot, and KeySlot.swift defines 84 of them: 49 "always" slots, which use Cmd by default, 24 single keys, 10 hold keys and the dictation key. A binding is written like Mod+Shift+M, where Mod stands for Cmd.

When you press a key, Match.swift scores each binding against it. An exact match of key and modifiers scores 3. A match that needs an implied Shift (a symbol your layout types with Shift), or that reads the Turkish dotless ı as I, scores 2. When the typed character can't name a shortcut at all, as with another script, a dead key, the digit row, a Shift symbol or an Option letter, Bifrost falls back to the key's position on a US keyboard and scores the match 1. Only the bindings with the best score run, and they run again on every key repeat.

At the moment the window, row and layout shortcuts work, along with Focus Overview, the Overview tab keys (Tab and Shift+Tab), Interrupt and dictation. The row keys and the Overview tab keys act on the Overview whose rows have the keyboard focus now, which they get when you click them, click in that Overview's tab bar or press Focus Overview. When no Overview's rows have the focus, for example while you type in a chat, they act on the Overview that's the active panel of the highest frame showing, and with no such Overview they do nothing. The rest of the slots arrive in phase 4.

Reserved keys

Settings won't let you bind these keys, so they always reach macOS or the menu bar:

  • macOS: Cmd+Tab, Cmd+Space, Cmd+H, Cmd+M, Cmd+Q, Cmd+Alt+Esc, Cmd+Shift+3, 4 and 5, Cmd+Shift+Q, Cmd+Shift+/, Ctrl+Cmd+Q, Ctrl+Space.
  • Menus: Cmd+Z, Cmd+Shift+Z, Cmd+X, Cmd+C, Cmd+V, Cmd+A, Cmd+Alt+H, Cmd+= and Cmd+-.

The two menu slots, Close Panel and Toggle Fullscreen, must use Cmd, because the menu bar sees their keys first and a plain key would then fire inside a chat or a text box. Two slots of the same class (ordinary keys, hold keys or the dictation key) can't share a binding, and if a saved settings file has a clash anyway, the slot that comes first keeps it.

Which shortcuts work depends on where the focus is. Bifrost sorts every focused view into one of six focus zones:

Focusing a chat also selects its session, so a session shortcut like Cmd+. acts on the chat you're typing in. The row hold keys (O, M, I, J, X and 1 to 5) only work in the other zone. If you click a row while holding one, its action runs on that row, and if you don't, the key runs its usual single-key action when you let go (HoldGate keeps track of this). macOS sends no key-up event while Cmd is held, so pressing Cmd makes Bifrost forget any held key, and so does the window losing focus.

Changing a key

In Settings > Keys you change a shortcut by pressing the new one. While the key recorder (KeyRecorderView) records, it has the focus, so the focus zone is modal and no Bifrost shortcut runs.

Every key goes to the recorder

The window hands the recorder each key event, and each Cmd shortcut, before the views or the menu bar can see it (WindowKeyFilter). So Cmd+W, Ctrl+Cmd+F and Cmd+Q are recorded rather than run, and the menu bar still shows its keys while you record.

The recorder saves the key the way the matching reads it (Chord(event:)), so the key you pressed is the key that runs the shortcut on any layout. A letter or symbol that a binding can name, and that matches exactly, is saved as itself: Cmd+Z on a German keyboard stays Cmd+Z. Anything else falls back to the US key at that place, the same fallback the matching uses, so Option+O is Alt+O and the Russian key in the place of F is F. The dictation key is found by its place, so for that slot the recorder always saves the place.

Esc, and Backspace or Delete with no modifier, stop the recording without a change. A key repeat or a modifier on its own isn't a new key (KeyRecording.step). Moving the focus away, leaving the window, hiding Settings or closing it stops the recording too.

Refused keys

KeyEditor.checkRecorded checks each key against your current keys. A refused key keeps the recording going, and the row shows why:

  • a key with no binding, such as a keypad digit, F13, the ISO key left of 1, or German Ö with no modifier, which the matching can't read: "Bifrost can't use this key. Try another one."
  • a dead key such as Option+E, without Cmd or Ctrl: "That key types a character. Try another one." With Cmd or Ctrl it's an ordinary shortcut.
  • the space bar, for any slot but the dictation key: "The space bar can't be a shortcut. Try another one."
  • any of the binding checks in Reserved keys, such as "Event log already uses this key."

A good key saves at once and rewrites only its own slot. Reset all keys keeps any key that a later version of Bifrost saved (KeyEditor.resetAll).

Input methods and dead keys

Composing

While a Japanese, Chinese or Korean input method is composing a word (the focused view reports marked text through hasMarkedText()), Bifrost stays out of its way:

  • no binding matches, so no shortcut can fire;
  • Space types as normal and never starts dictation;
  • Shift+Enter goes to the input method instead of the PTY, which is a deliberate difference from the Electron version of Bifrost;
  • Enter in the send box doesn't send the message.

Dead keys and other layouts

A dead key such as Option+E hasn't typed anything yet, so the only way to match it to a shortcut is by its position, using the US key table in KeyCode.swift. Bifrost does the same for other keys whose character can't name a shortcut, such as those on a Cyrillic layout, the AZERTY digit row, Shift symbols and Option letters.

Letters are compared without case but with their accents, so Option+0, which types º, never matches Option+O.

Hold Space to talk

Holding Space in a chat lets you dictate straight into Claude's prompt. Space is just the default for the slot dictation:hold, and the dictation key does nothing special outside a chat. ChatInput tells a tap from a hold by timing the press, and a press counts as a hold once the key has been down for 250 ms.

The timeline isn't to scale after the first 250 ms. The green glow only shows while the microphone is open.

Tap

Let go before 250 ms and you get a single space, and the microphone never opens.

Roll over

Press another key during the wait, as often happens when you type quickly, and you get the space followed by that key, in the right order, with no dictation.

Hold

At 250 ms Bifrost checks whether Claude Code is in vim mode and, if it isn't, starts listening. Once the first sound level or text arrives, the green glow comes on and Space stops typing anything. Let go to stop. The final text arrives within 1.5 s, and any keys you press in the meantime wait up to 2 s for it, so they land after your words.

Edge cases

  • If you let go or press another key before the first sound level or text arrives, nothing has shown on screen yet, so Bifrost treats it as a slow tap and types the space.
  • You also get a plain space when vim mode is on (a dictated letter could run as a vim command), when the chat has no PTY or Bifrost has no speech engine, after an early error, or while the session shows a red prompt box.
  • Space with a modifier held, or while an input method is composing, is just a normal key, and the key repeats of a held Space are ignored.
  • Moving the focus away from the chat or closing it stops dictation, and so does the 2-minute limit on a single dictation.

From voice to prompt

Once a hold turns into dictation, your voice passes through a short pipeline before it appears as text in Claude's prompt. Apple's speech framework does the recognition (SpeechAnalyzer with SpeechTranscriber), which is why dictation needs macOS 26.

The typer (DictationTyper, TypingRules)

  • Each time the recogniser revises its guess, the typer sends backspaces (DEL) over the part that changed and then types the new ending. It only ever deletes text it typed itself, one DEL per visible character, so your own text is safe.
  • A single write carries at most 100 UTF-16 units of text and 1,000 DELs, and writes go at least 20 ms apart, plus 1 ms for every 2 DELs. Small writes keep Claude Code from treating the text as a paste, and the gap gives it time to work through the deletes.
  • It puts a space before the dictated text when the prompt's text doesn't already end in white space. On an empty prompt it only adds one before /, !, ? or #, which would otherwise open one of Claude's menus or modes.
  • It never sends Enter, Tab or Esc, and it never reads the screen.

The engine (DictationService, AnalyzerEngine)

  • The speech engine loads the first time it's needed, which is when a chat with a dictation key gets focus or when dictation starts. If the speech model isn't on the Mac yet, it downloads it from Apple first.
  • After 5 minutes without use it unloads again, though never during a download or a dictation.
  • Starting the engine and starting each session both give up after 10 s, because the macOS speech service can stop answering.
  • There's only one microphone, so dictations run one at a time, and starting one in another chat stops the first. When you let go, the engine waits up to 1.5 s for the final text and then uses whatever it has.

The Interrupt key

Pressing Cmd+. sends a single Esc, which is Claude Code's stop key, to the selected session. It works from anywhere in Bifrost except a dialog.

Cmd+.→KeyLayer matches the slot interrupt:mod→ KeyCommands.interruptRow, for owned rows only→SessionInput.interrupt→ cancels sends not yet written→the chat's PTY, or a hidden attach→ one Esc

Timing guards

  • A busy session's spinner means its output never goes quiet, so the Esc goes out 300 ms after the attach first produces output.
  • A second Interrupt does nothing while one is still pending, or within 1.5 s of the last Esc, because two Escs in a row would open Claude's rewind menu.
  • After an Esc, the next write waits 200 ms, so Claude can't read the Esc and the bytes after it as one key.
  • A red prompt box blocks sends, but it never blocks an Interrupt.

Plain Esc in a chat

In a chat, a plain Esc goes straight to Claude Code. On its way it stops any dictation typer and throws away the keys queued behind it, so a queued Enter can't submit half a sentence. Ctrl+C does the same.

The 318 key tests

The key rules are pinned down by 318 scenarios in Scenarios/key-scenarios.json, and KeyScenarioTests plays each one through the real pieces: a Bifrost window with its key filter, a SwiftTerm view and a ChatInput. Every scenario gets its own window, which never comes to the front. Support/Driver.swift delivers each key the way macOS does, offering Cmd shortcuts to the window's controls and then the menu before the window itself gets the key, and a manual clock drives the 250 ms hold timer so the timings are exact. A scenario passes only when the commands that ran, the calls to dictation and the bytes sent to the PTY all match exactly.

Negative controls

Two deliberately broken runs check that the scenarios really depend on the filter and the hold timer:

  • With the filter switched off, exactly 243 fail. The 75 that still pass are keys Bifrost leaves alone anyway, in text boxes, dialogs and the menu slots.
  • With the hold time cut to 100 ms, exactly 5 fail, because their taps now count as holds: slot/dictation:hold/chat-tap, dictation/tap-249, dictation/rollover, dictation/blur-in-wait and dictation/close-in-wait.

Two scenarios expect a different result from the Electron app on purpose. In shift-enter/composing, Shift+Enter during composition goes to the input method, and in hold-gate/rollover-stale, releasing a hold key always clears it, so a stale hold key can't turn a later row click into a hold action.

Glossary

AppKit
Apple's framework for Mac app interfaces. It owns the windows, views and menus, and delivers key events to them.
Composing
What an input method does while it builds a word. The unfinished text, called marked text, shows underlined until you commit it.
Dead key
A key that types nothing by itself but changes the next key you press. Option+E followed by E gives é.
Focus zone
The kind of place the focus is in, which is one of six: modal, chat, send box, text, control or other. The zone decides which shortcuts work.
Hidden attach
An attach with no window. Bifrost opens one briefly when it needs to type into a session that has no chat open.
Input method
The macOS tool for typing languages such as Japanese, Chinese or Korean, where you build up a word over several keys and then commit it.
Key filter
Bifrost's code in the main window that sees every key event before any view does, and runs Bifrost's shortcuts.
Key recorder
The part of Settings > Keys that records a new shortcut. While it records, it takes every key you press.
Kitty key
A key sent using the kitty keyboard protocol, a richer way for a terminal to report keys, which Claude Code turns on.
Owned session
A session that runs as a Claude Code background job, which Bifrost can attach to. For a session running in some other terminal, Bifrost can only show its status.
PTY
Short for pseudo-terminal, a software stand-in for a real terminal. Claude Code reads it as if it were one, so the bytes Bifrost writes to it arrive as typed keys.
Red prompt box
The red mark on a session while Claude Code waits for your answer, for example to a permission request. While it shows, Bifrost won't send text to the session.
Responder chain
The line of views that AppKit offers a key to, from the focused view out through its parents to the window.
Row
One session as it appears in a session list, such as the Overview.
Row hold key
A letter or digit you hold while you click a session row, to run an action on that row. For example, hold O and click a row to open its chat.
Send box
The box in the Selected Item panel where you type a message for the selected session. It arrives in phase 4.
Slot
One shortcut Bifrost knows about, such as Interrupt. Each slot has one binding.
SwiftTerm
The open-source terminal view that draws each chat window.
Typer
The part of dictation that types your words into the PTY, and corrects them as the speech engine revises its guess.
