# Deliberate differences

This table lists the places where the native window layout, canvas and state files work
differently from the TypeScript code of the Electron app on purpose. The TypeScript code is the
reference for what the app decides, not for how it does it. The last column says whether someone
using the app would notice the difference in normal use, and a row marked "for the hands-on test"
is one to check by hand in the real app.

The rows come in a few groups:

- W1 to W9 cover the layout rules: `geometry.ts`, `hit.ts`, `overlap.ts`, the reducer of
  `state.ts`, `toSnapshot` of `layout.ts` and the drag rules of `beginDrag` in
  `WindowManager.tsx`. A user can't see any of them.
- U1 to U10 cover the UI state and window state files: `parseUiStore`, `saveLayout` and
  `deleteLayout` of `layout.ts`, `ui-store.ts`, `window-state.ts`, the save timer of
  `WindowManager.tsx`, and the configs and history that `parseUiStore` reads with
  `overview/config.ts` and `sessions/history.ts`. U5 is visible and is for the hands-on test.
- W10 to W14 cover the canvas, the frames and the side bar (`Frame.tsx`, `WindowManager.tsx`,
  `PanelMenu.tsx`, `SideBar.tsx` and `LayoutMenu.tsx`). They're visible and stay as built, and
  the user judges each one by hand in the development app (user decision, 2026-11-15).
- W15 (the cursor during a drag, user decision, 2026-11-16) and W16 (clamping a rect with half
  units) are visible and are for the hands-on test.
- W17 and W18 change the rounding and the handling of values that aren't finite, and a user can't
  see them.
- W19 (a greyed-out global button of the side bar) is visible only with Full Keyboard Access, and
  it's for the hands-on test.
- W20 (how the cyan glow of the top frame is drawn) is for the hands-on test.
- W21 (a click on the canvas background takes the focus from the panels, user decision,
  2026-11-19) is visible and is for the hands-on test.

The window bounds are flipped between AppKit and the file, but that's a conversion rather than a
difference: the file keeps the screen coordinates of the Electron app.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| W1 | The panel IDs and frame IDs of the actions | An ID is a string, and each action checks it: `panelKind` refuses a bad panel ID, a frame ID that no frame has finds nothing, and the reducer then returns the same state. A load drops a bad panel ID and a frame with no good panel. | `PanelID` is an enum with one case for each kind, such as `.overview(2)` or `.chat(sessionID)`, and `FrameID` holds only `f<number>`. Text becomes a panel ID only through the parse `PanelID(_:)`, and `text` gives the same text back, so an action can't be made with a bad ID from a file. The session ID of a chat or Show Info panel is kept in lower case, so the two forms of one ID are one panel. A `SavedFrame` holds only good panel IDs and a good active panel. | The types do the check once, where an ID comes in: the parse for a saved layout and the test port, and `SessionID(_:)` for the session ID of a row before its chat opens. | No. For each such action the reducer changes nothing, and the layout tests check each one. A file edited by hand with an upper-case session ID gets it back in lower case at the next save. |
| W2 | The memory of a load | `load` keeps the memory object with any key. | `memory` is `[PanelID: LayoutRect]`, so it holds only keys that `panelKind` accepts. | `parseSnapshot` (`layout.ts`) drops every other key before a load, so the app never makes such a load. | No. |
| W3 | The same object | A reducer action that changes nothing returns the same state object, and React does nothing. `shownFrames` returns the same object for a frame that fits, and a load always returns a new object. | `apply` returns false when the layout doesn't change. A layout and a frame are values, so the tests compare them with `==`, and a load always returns true. | A Swift value has no identity, and the result of `apply` tells the shell when to save and draw. | No. |
| W4 | The order of the memory | The memory is an object whose keys keep their insertion order, and the save writes them in that order. | The memory is a dictionary with no order. | The key order of a JSON object means nothing to the load, and writing the keys sorted means every save of the same layout gives the same file. | No. |
| W5 | `blurredFrames` | The result is a `Set` that keeps the z-order of the frames. | The result is a `Set<FrameID>` with no order. | The callers only check whether a frame is in the set. | No. |
| W6 | The steps of a drag | A pointer move asks for one draw at the next animation frame, and the draw uses the last pointer position. A cancel keeps the rect of the last draw. | `FrameDrag.move` works out the step at each pointer move, a cancel keeps the rect of the last move, and the shell decides when to draw. | The layout rules have no clock and no display link. | No. The two rects are at most one animation frame apart (about 8 ms at 120 Hz). |
| W7 | A drag whose frame closes, is minimised or is locked | An effect on `state.frames` ends the drag at once with a cancel, which sends `setRect` with the drawn rect, and the reducer refuses it. | `WindowLayoutModel.apply` ends the drag at once with a cancel (`endDrag(at: nil)`) when the change leaves the frame closed, minimised or locked. If the drag rules see such a layout first, the next `move` gives an empty view and `end` gives `.nothing`. | The result is the same: the layout doesn't change. | No. The canvas doesn't draw a frame that isn't there, and the drag ends at the change. |
| W8 | A tab press whose tear-out can't apply (the frame lost the tab, or now has one tab) | `tearOut` ends the drag with a cancel, and the drag listeners are removed. | The drag stops: every later step gives an empty view, and `end` gives `.nothing`. The caller keeps the drag until the release. | The layout model has no listeners to remove, and the result is the same: nothing changes. | No. The layout changes nothing in either app. |
| W9 | The snap distance during a drag | Each step reads the setting again (`snapRef.current`, line 433 of `WindowManager.tsx`), so a change of the setting during a drag applies to the next step. | `FrameDrag` takes the snap distance when it starts and keeps it for the whole drag. | The layout rules don't read the settings. A drag lasts a few seconds, and the next drag starts with the new value. | No. The setting is in the Settings panel, so a user can't change it while dragging a frame. |
| U1 | `performance` in ui-state.json | `parseUiStore` applies `parsePerformance`: a bad Performance value gives `{ detailsOpen: false }`, and a save writes that clean form. | The decode keeps the stored value as it is, and a save writes it back as it came. A missing value stays missing, and a test checks that the value comes back unchanged. | Phase 5 ports the Performance panel. | No. Nothing in the app reads it yet. |
| U2 | Unknown top-level fields of ui-state.json and window-state.json | The renderer saves the parsed store, and the window store writes only `mode` and `bounds`, so a field of a newer app is lost. | `UIState` and `WindowState` keep every top-level key that their coding keys don't name (`UnknownFields`), also in a UI state of another version, and write those keys back when they save. A known key never counts as an unknown field. | A file from a newer app must lose nothing ("Files on disk" in the architecture design). | No. |
| U3 | A ui-state.json or window-state.json that doesn't parse at all (bad JSON, or the text of S6 in the stores port) | The load gives the defaults, and the first save writes over the file. For the text of S6, `JSON.parse` reads the file. | The load gives the defaults. Before the first save over the file, `FileSaver` copies it to `<file>.unreadable` once and logs where the copy is. A new copy replaces an old one, and a failed copy turns saving off so the file stays. The registry store uses the same code. | `ui-state.json` holds the named layouts the user saved. | No in normal use, since neither app writes such a file. The copy is one extra file in the support folder. |
| U4 | Trimming a layout name (D3 of the registry, S5 of the stores) | `trim` uses JavaScript white space, in which U+FEFF is white space and NEL (U+0085) isn't. | `trimmed()` uses the Unicode White_Space property, so NEL is white space and U+FEFF isn't. The trim removes whole `Character`s, so a combining mark after a space at either end goes with it. | It's the same rule as every other text in the native app. | No. A user can't type these characters at the ends of a name. |
| U5 | Comparing layout names, and their length | `===` compares UTF-16 units, and the limit of 40 counts UTF-16 units. | `UIState` and the side bar compare two names with Swift String equality (canonical equivalence), and the limit of 40 counts `Character`s. Two forms of one accented letter are one name: saving in the other form replaces the layout, deleting or loading in the other form finds it, and loading a file keeps the first of the two. | Each app has its own files now (user decision, 2026-11-16), so no second app reads the file. Swift String equality is the native rule, and every length limit in the app counts `Character`s. | Yes, for the hands-on test: a layout name of up to 40 emoji fits, where the Electron app refused more than 20, and saving under another form of the accented letters of a saved name replaces that layout. |
| U6 | The changes that start a save of the UI state | The renderer marks the store as changed at each new state of the layout, the Overview configs, the history and the Performance state, and at each `setStore`. Deleting a name that isn't there also calls `setStore`, so the same data is saved again. | `change` starts the save timer only when the state really changes, and a change that changes nothing writes nothing. | The file holds the same data either way. | No. |
| U7 | A refused save of the UI state | `save` rejects a value that isn't a plain object, and one with more than 1,000,000 bytes of compact JSON. The renderer logs `Bifrost cannot save the UI state.` with the error. | The state is always an object. A state whose compact JSON (including the unknown fields) is more than 1,000,000 bytes writes nothing and logs `Bifrost cannot save the UI state to <file>. It is larger than 1000000 bytes.` | The types refuse a value that isn't an object, and the native log takes text. | No. Only the log shows it. |
| U8 | A failed write of either file | `save` and `update` reject with the error, and the caller logs `Bifrost cannot save the UI state.`, `Bifrost cannot save the mode.` or `Bifrost cannot save the window bounds.` with the error. | The stores don't throw. They log `Bifrost cannot save the UI state.` or `Bifrost cannot save the window state.` with the text of the error (`ErrorText`, S13 of the stores) to the macOS unified log, and the state keeps the new value. A read error logs that the store won't save, with the text of the error. | After a failed write, all a caller could do is log it. | No. Only the log shows it. |
| U9 | The save after the start | The start layout (the loaded `current`, or the default layout) counts as a new layout state, so the renderer saves ui-state.json 500 ms after every start, even when the layout is the one in the file. | The shell sends each layout change to the store from before the start layout (`WindowLayoutModel.onChange` and `save(_:to:)`). A start layout that isn't the `current` of the file (the default layout, or a load that dropped a bad frame) saves 500 ms after the start, and one that is the layout of the file writes nothing, as in U6. | Writing the same data again has no use. | No. The file holds the same data in both apps. |
| U10 | `overviews` and `history` in ui-state.json | `parseUiStore` cleans both when the store loads. `parseOverviews` keeps the configs of the `overview:<n>` keys that `parseOverviewConfig` accepts, `parseHistory` keeps the good values and drops every other field, and the next save writes the clean forms, with an empty `overviews` object when there are no configs. Two folders or two commands are the same when their UTF-16 units are equal. | `UIState` keeps only the `overview:<n>` keys on load, but leaves each config and the history as raw JSON, because `OverviewConfig` lives in `BifrostWindows` and `History` in `BifrostSessions`. `overviewConfig`, `updateOverview` and `dialogHistory` read and write them with the same rules. A config that can't be read gives the standard config. A change writes only the config of its own Overview, and only when the config changed, so a config that can't be read, or one that the rules would clean, stays in the file as it came until its own Overview saves over it. The history is written in its clean form when it changes, and until then the file keeps it as it came. No configs means no `overviews` key. The history keeps the fields it doesn't know, as a config does (OV7 of the Overview), and two folders or two commands are the same when they're equal Swift strings, so two forms of one accented letter are one entry. The length of a command counts `Character`s (S15 of the stores). Tests: `aBadOverviewConfigGoesAloneAndTheOtherValuesStay`, `aChangeWritesOnlyTheConfigOfItsOwnPanel`, `twoFormsOfOneTextAreOneEntry`. | `BifrostLayout` comes before both modules and can't use those types. A value that nothing has read doesn't need cleaning, and Swift string equality is the rule for every name in the app (U5). | No. The Overview and the dialog read the same values either way. Two forms of one accented letter in two folder paths, or a slash command of more than 99 emoji, isn't a normal case. |
| W10 | The Panel menu of a frame | A box below the menu button (`role="dialog"`, 208 px wide, in the title colour with a border) holding the Lock check box. It has a padding of 12 and a gap of 12 between its parts (`p-3`, `gap-3`), Lock is a square check box of 14 with its label, and "Overview settings…" has a hover of white at 5 %. Changing the check box keeps the box open, and a press outside it or Esc closes it. The box opens at the click of the button. | A Bifrost menu (`FrameMenu.swift`, `docs/behaviour/menu.md`): a borderless panel 208 units wide, below the menu button at its right edge and 4 units under it, in the title colour with a border, with rows of 20 (a padding of 4 above and below the rows and 8 at the sides), Lock as a check box row with the square check box of 14 (an empty box while the frame isn't locked), and the highlight of white at 10 % on the row under the pointer. Lock keeps the menu open, and a press outside it or Esc closes it. It opens at the press of the button (row M9 of the menu port). The user judges it by hand. |
| W11 | The Layouts popover | A box to the right of the Layouts button, 8 px from it, with its bottom level with the bottom of the button, and no arrow. | A SwiftUI popover (`NSPopover`) to the right of the button, with the system's arrow and rounded corners. | W12 | The body of a tab that isn't active | React shows only the content of the active tab. | W13 | The keyboard focus ring | A square 1 px outline in the accent colour (`:focus-visible` in `app.css`). | The system focus ring of AppKit and SwiftUI on the title bar buttons, the tabs and the side bar buttons. | The full keyboard and VoiceOver pass comes before cutover (the UI section of the architecture design). | Yes, only with Full Keyboard Access. | W14 | The icon of a minimised chat | The session's icon (`SessionIcon`) and the dot of its state, as in the chat's title. | W15 | The cursor while dragging or resizing a frame | The browser picks the cursor from the CSS `cursor` values of the page (the `cursor-*-resize` classes of the handles in `Frame.tsx`), and the drag has the pointer capture of the element that was pressed (`setPointerCapture` in `WindowManager.tsx`). | From the press of a move or resize until it ends, the window stops updating its cursor rects (`CanvasView` calls `disableCursorRects`, then `enableCursorRects` and `resetCursorRects` at the end). The cursor of the press stays the cursor of the whole drag, and doesn't change over the edges of other frames, over terminals or over other parts of the window. The end of the drag, a cancel, or the window losing its key state turns the cursor rects back on. | Each step of a drag moves the frame view, and each move marks the cursor rects as out of date. AppKit then rebuilds every cursor rect of the window on each display cycle, on the main thread, and in the optimised build this made some drag frames miss the display (phase-3-performance.md, Step 4). Without it, a drag missed no frames (118.6 fps, 0.00 missed a second). | Yes, in a small way: the cursor doesn't change during a drag. For the hands-on test (user decision, 2026-11-16). |
| W16 | Clamping a rect (`clampRect`), for example a saved rect with half units from a file | `clampRect` (`geometry.ts`) clamps the place and the size and then rounds each value. A place and a size that both end in a half each round up, so the rect can end 1 unit past the right or bottom edge of the canvas (y 513.5 and h 286.5 give 514 + 287 = 801 in 800), and bounds with a half unit can give a size 1 unit larger than the canvas. | `Geometry.clampRect` rounds the size first and keeps it within the whole units of the canvas, then rounds the place and moves it into the room that the whole size leaves. A rect on screen never passes the canvas edge. In a canvas of whole units, every rect that `geometry.ts` keeps inside the canvas gives the same result. | A frame that's showing must stay inside the canvas. The seeded property test of the layout found the case, and it now checks the exact bounds. | Yes, but only with a ui-state.json that has half units, which neither app writes (only a file someone edited by hand). The frame then shows 1 unit higher or further left than in the Electron app. For the hands-on test. |
| W17 | Rounding a value of a rect | `Math.round`, where a half goes up, so -2.5 gives -2. | `rounded()`, where a half goes away from zero, so -2.5 gives -3. | It's the Swift rule. A result rect is inside the canvas, so its values are 0 or more, and a half of 0 or more rounds the same both ways. A negative half only comes up in a step before a clamp, such as the centre of a size larger than the canvas or a resize edge left of the canvas, and the clamp then moves it to 0. | No. |
| W18 | A value that isn't finite | `Math.min` and `Math.max` give NaN for a NaN, so a NaN passes through every rule. | The layout refuses a rect or a canvas size that isn't finite where it comes in (`WindowLayout`, the load of a file), and a pointer movement that isn't finite counts as 0. The rules then use `Swift.min`, `Swift.max` and `rounded()`. | One check where a value comes in, rather than a NaN case in every rule. | No. AppKit gives finite values. |
| W19 | The keyboard focus of a greyed-out global button | `GlobalButton` of `SideBar.tsx` stays focusable when it's off (`focusableWhenDisabled`), so Tab still reaches Resume all while it's greyed out, and the focus shows its tooltip with the reason. | The global buttons are SwiftUI buttons, and an off button (`disabled`) leaves the key view loop, so Tab skips it. Its tooltip with the reason still shows under the pointer. | SwiftUI has no focusable disabled button, and an enabled button that ignores its click would tell VoiceOver that it can act. The full keyboard and VoiceOver pass comes before cutover (W13). | Yes, only with Full Keyboard Access, for the hands-on test. |
| W20 | The glow of the top frame | A `box-shadow` of `0 -6px 12px -6px` in `--color-accent-glow` on the frame (`Frame.tsx`), so a soft cyan light shows above the top edge and fades out towards both ends. | `EdgeGlow` in `BifrostLook`: the Core Animation shadow of a strip that lies along the top edge, 6 units in from each end, with a softness (the standard deviation of the blur) of 6 units, clipped to the area above the edge. The light at the edge is half the alpha of the token, and it falls off upwards and towards both ends in the same way as the Electron glow. | The native app has no CSS. A Core Animation shadow is the native way to blur a shape, and because the strip has a path, it needs no offscreen pass. | Yes, but only in that the pixels can differ slightly from the Electron app. `GlowLookTests` renders the frame and checks the fall-off against a Gaussian blur of the Electron values. For the hands-on test. |
| W21 | A click on the empty background of the canvas | The focus look of a frame follows only the z-order (`top={frame.id === topId}` in `WindowManager.tsx`), so a click on the background keeps the look on the top frame, and its chat stays the focused chat for the size rule. | A press of any mouse button whose hit view is the canvas itself, also the first click on a window that isn't key, makes the window the first responder and applies `.dropFocus` (`CanvasView`, `WindowLayout.focusedFrame`). The top frame keeps its place but loses the focus look, and no chat is focused, so no chat sends a resize. A press on a frame, or an open, a restore, a stack or a tear-out, gives the focus back. | After a click on the background, Esc went to the chat that still had the keyboard and stopped Claude's answer (user decision, 2026-11-19). | Yes, for the hands-on test: the focus look goes at a click on the background, and Esc opens Settings. |
