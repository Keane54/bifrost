# Deliberate differences

This table lists the places where the native usage rules, the account usage poller, the usage
notification, the Usage HUD and the time texts work differently from the Electron app's
TypeScript code on purpose. That code (`time.ts` and `usage.ts` in `src/shared/`, `token.ts`,
`parse.ts` and `poller.ts` in `src/main/account-usage/`, `rules.ts`, `state-store.ts`,
`claude-json.ts` and `monitor.ts` in `src/main/usage-alerts/`, `usage-view.ts` and
`UsagePanel.tsx` in `src/renderer/src/usage/`, and
`formatWhen` in `src/renderer/src/info/show-info.ts`) is the reference for what Bifrost decides,
not for how it gets there. The last column says whether you'd notice the difference in normal use,
and a row marked "for the hands-on test" is one to check by hand in the real app.

Two rows are visible, each only now and then: US1 only in September, and US10 only with
VoiceOver. Both are for the hands-on test.

A few functions look different and give the same values. `TimeText.duration` takes a `Duration`
where `formatDuration` took milliseconds, and `UsageView.reset` and `UsageSource.pick` work out
the time between two wall times as a `Duration` too. `UsageSource.pick` returns an enum that holds
either the account values or the session snapshot, with a `limits` property for the windows, where
`usageSource` returned an object with a `kind`. `formatWhen` moved from Show Info into
`TimeText.when`, and the Overview's `formatAge` and `ageStepMs` moved into `TimeText.age` and
`TimeText.ageStep`, so the Usage HUD can use them from `BifrostSessions`. A bar's percent is kept
between 0 and 100 before it's rounded rather than after, which gives the same whole number. The
account usage poller keeps the result of its last poll in `lastResult` and clears it at a stop,
where `createAccountUsagePoller` sent each result, and the stop, to the health log.

The usage notification has a few of these too. `UsageAlertStore.set` changes the periods at once
and hands back the task of the save, where `set` returned a promise. `UsageAlertMonitor` gets the
open store and the home, and it reads `~/.claude.json` itself, where `createUsageAlertMonitor` got
a promise of the store and a `readExtraUsage` function. The text of a notification keeps its
percent between 0 and 100, which changes nothing, because a window only notifies from 89.5
percent.

| US1 | The name of September in a date of another day (`TimeText.when`, which Show Info and the update rows of Settings use) | The en-GB data of the ICU in Chromium gives "Sept", as in "Tue 1 Sept 14:03". | `DateFormatter` with the `en_GB` locale of macOS gives "Sep", as in "Tue 1 Sep 14:03". | US2 | Times far out of range | Times are doubles. A time more than 8.64e15 ms from 1970 isn't a valid date, so `Intl.DateTimeFormat` throws a `RangeError` and the panel can't draw its text. | Times are `Int` milliseconds, and every one gives a text. | US3 | The size limit of the account answer | Two checks: a `Content-Length` header over 1,000,000 bytes, then a body text over 1,000,000 UTF-16 units. | One check on the bytes of the body. | US4 | The reset time of a window in the account answer | `Date.parse`, which cuts a fraction of more than three digits and also reads other forms, for example `Sat, 07 Nov 2026 02:00:00 GMT`, `2026-11-07` and a time with no zone. | `RateWindow.resetTime`, the ISO 8601 parse that the Live usage lines use too (V2 of the Live port), which rounds the fraction to the nearest millisecond and gives no window for the other forms of `Date.parse`. | One parse for both sources of usage values. | No. The endpoint sends six digits of fraction, as in `2026-11-07T05:00:00.469616+00:00`, so a reset time can be 1 ms later than in the Electron app, and the HUD shows minutes. `anAnswerWithBothWindowsGivesTheValues` pins it. |

| US7 | A redirect from the usage endpoint | `redirect: 'error'` makes the fetch throw, which is a fetch error. | The session's delegate refuses the redirect, so the request ends with the redirect answer, which is a bad status. | `URLSession` refuses a redirect through its delegate. | No. Both keep the old values and give the result failed, and the token never goes to the new URL. | US8 | The log of the account usage | The poller logs nothing. | Each poll that gives no new values logs a fixed reason, with an HTTP status at most, no token at the info level, an expired login or a rate limit as a notice, and each other reason as an error. | The unified log shows why the account values are missing, and no event holds a text, so no line can hold the token. | No, only in Console. `noLogLineHoldsTheToken` pins it. |
| UA1 | The store of `usage-alerts.json` (`UsageAlertStore`) | `openUsageAlertStore` writes each `set` in turn with `writeJsonAtomic`, and a save writes only the two known keys. A file that isn't JSON is written over at the next save, with no copy. | The store saves through `FileSaver` and a `SaveQueue`, like every store file. Unknown top-level keys stay (S1 of the stores port), a file that doesn't parse is copied to `usage-alerts.json.unreadable` before the first save over it (S9), and a value that waits while a write runs gives its place to a newer value, so the file gets the newest periods with fewer writes. | One save path for every store file. | No. `unknownTopLevelKeysSurviveASave`, `aFileThatIsNotJSONGivesNoPeriodAndASaveKeepsACopyFirst` and `aSetChangesThePeriodsAtOnceAndTheNewestValueWinsOnDisk` pin it. |
| UA2 | A kept time in `usage-alerts.json` | Any finite number counts, and the rules compare the times as doubles. | A kept time must be a whole number of milliseconds that fits an `Int`, and anything else is no notified period. | UA3 | The read of the extra usage flag in `~/.claude.json` (`ClaudeJSON`) | `stat`, then `readFile` of the whole file, then `JSON.parse` of the whole text. | One open with `O_NONBLOCK`, whose `fstat` gives the type and the size, a read of at most 20 MB and one byte, and a decode of `oauthAccount.hasExtraUsageEnabled` only. | The check and the read see the same file, a file that grows after the check can't fill the memory, and no other account data is decoded. A value elsewhere in the file that `JSONDecoder` can't hold (S6 of the stores port) doesn't stop the read. | No. Every file that Claude Code writes gives the same flag. Only two kinds of file differ: one with a repeated key, at the top or inside `oauthAccount`, where the first one counts and `JSON.parse` took the last, and one nested more than 512 levels deep, which `JSONDecoder` refuses, so the flag is off. `aFileAbove20MBIsSkipped`, `aMissingFileAFolderAFifoAndBadJSONGiveNoFlag` and `aValueThatAJSONValueCannotHoldElsewhereInTheFileDoesNotStopTheRead` pin it. |
| UA4 | The monitor of the usage notification (`UsageAlertMonitor`) | The monitor checks nothing until the promise of its store resolves, each notification waits for a promise of the flag, `ipc.ts` gives it each answer of the poller and each change of the session usage, and a failure logs to the console. | The services open the store after the settings store and then make the monitor, so no value can come before the store or the setting.
