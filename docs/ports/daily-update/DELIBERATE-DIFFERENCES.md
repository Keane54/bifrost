# Deliberate differences

This table lists the places where the native Daily update works differently from the Electron
app's TypeScript code on purpose. That code (`daily-schedule.ts`, `daily-state.ts`,
`daily-update.ts`, `state-store.ts` and the files of the run in `main/daily-update/`) is the
reference for what the Daily update decides, not for how it gets there. The last column says
whether you'd notice the difference in normal use, and a row marked "for the hands-on test" is one
to check by hand in the real app.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| DU1 | When the reminders come | The service checks the schedule on a timer and asks what to do each time. | The schedule gives the next date at which its answer can change (`nextWake`), and the service sleeps until then. It asks again after a system event such as waking from sleep. | A timer wastes wakeups and can run late after sleep. A planned date is exact, and the calendar API gives a date even for an hour that a clock change skips. | No. |
| DU2 | Which copy owns the state | Nothing stops a second copy of the app from writing `state.json`. | The first open takes a lock on `.lock` in the folder. A second copy shows a message and neither reminds nor writes. | Two copies (a second Dev app, or the release app after the cutover) would send the same reminder twice and overwrite each other's drafts. | Only if you run two copies: the second one shows "Daily update is running in another copy of Bifrost." |
| DU3 | The file before the take-over | The file is read and rewritten with no copy. | The first open keeps `state.json.before-native` and never replaces it. | The native app now owns the file, and the copy lets you go back if anything is wrong. | No. |
| DU5 | The probes of a run | Two probes: one before the merged PRs to check the source, and one just before the run for the deny list. | One probe, after the merged PRs, gives both the check and the deny list. | `--permission-mode dontAsk` already refuses a tool that has no allow rule, so the deny list only needs a fresh list. One probe saves a start of Claude Code and some seconds per run. | No. |
| DU6 | The 5-minute limit | The limit covers the `claude -p` run, and each probe and gh call has its own limit on top. | The limit covers the whole run: gh, the probe and `claude -p`. | The panel and the reminders can rely on one bound for a run. | Rarely: with a very slow gh and probe, a run can stop a little sooner. |
| DU7 | The Dock bounce of the second reminder | Electron calls `app.dock.bounce` when the second reminder shows. | The icon bounces one time with `requestUserAttention(.informationalRequest)`, and never in a test home. | This is the native call for it, and it follows the system setting for the Dock. | Yes, for the hands-on test: the icon should bounce one time when the 10-minute reminder shows. |
| DU8 | The draft in the panel | The draft shows read-only with bold in bold. Edit swaps it for a box of Markdown, and Done saves it. | The editor shows bold in bold and you change the text in place. Each change saves as Markdown, text typed after a bold part stays bold, and a paste is plain text. | One editor with no mode is simpler, and you never see the stars unless you type them. | Yes, for the hands-on test: change a draft, then Copy it and paste it into Slack. |
| DU9 | Redo of a changed draft | The tab swaps its buttons for "Replace your changes with a new draft?" with Replace and Cancel. | The confirm dialog of the window asks the same question. | The app asks every question of this kind the same way. | Yes, for the hands-on test: change a draft, then click Redo draft. |
| DU10 | The ticket source and its tools | Choosing a server saves it with its proposed read tools at once. The tools list shows each tool by its full name. | Choosing a server saves it with no tools. The proposed tools wait, ticked, until you click Use these tools. The list shows each tool by its name after the server's prefix. | The design says that you confirm the tools, and a short name is easier to read. | Yes, for the hands-on test: Find servers, choose your board and check the ticks before you use them. |
| DU11 | The work areas | Add work area shows an empty box that saves once it has a name. Remove acts at once. Ticking "Takes all other work" moves the flag from another area. | Add work area adds an area named "Work area 2" (the next free number) that you rename. Remove asks first. A second area with "Takes all other work" is refused with "Only one work area can take all other work." | Every area in the file always has a name, a removal can't happen by a slip, and a refusal tells you what's wrong instead of changing another area quietly. | Yes, for the hands-on test: add two areas, tick "Takes all other work" on both, and remove one. |
| DU12 | The status line, the times and Settings | The state is "Not sent yet", "Sent", "Skipped today" or "Nothing due today", and "Refreshing…" shows during a run. An earlier run shows its day name. The times are time pickers. | The state is the line of the service ("Your drafts are ready.", "Bifrost is writing your drafts." and so on). An earlier run shows its day and date. The times are `HH:MM` text fields, and Settings has a Daily update panel row that opens the panel. With no claude, the panel and Settings say "Bifrost couldn't find Claude Code, so it can't write your daily update." | The state line says what Bifrost is doing, the time texts match the rest of the app, and the panel row saves a trip to the side bar. | Yes, for the hands-on test: read the status line before and after a refresh, and open the panel from Settings. |
| DU13 | The sessions of the runs | The probe and the run are `claude -p` runs that Claude Code saves as sessions, each in the project of its run folder. | Both runs pass `--no-session-persistence`, so Claude Code saves no session for them. | Each run has a new folder, so each saved run added a project under `~/.claude/projects` that nothing removed, and the user never asked for it. | Only in Claude Code: the run folders no longer show up as projects with a session to resume. For the hands-on test. |
