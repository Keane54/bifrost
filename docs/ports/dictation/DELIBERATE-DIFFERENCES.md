# Dictation: deliberate differences

This table lists the places where the native app's dictation differs on purpose from the
TypeScript code of the Electron app. The TypeScript code is the reference for what the app
decides, not for how it does it, so a row records a change of result or of approach that's worth
knowing about. The last column says whether you'd notice the difference in normal use. The
dictation rules themselves are in `docs/behaviour/dictation.md`.

The rows cover the dictation of a chat window: the rules ported from `dictation-typing.ts`,
`dictation-session.ts`, `dictation-notice.ts`, `vim-mode.ts`, the values of `dictation-look.ts`
and the part of `dictation-protocol.ts` that a chat window reads, plus the speech engine, the
dictation service and the green glow, which take the place of the Electron speech helper. Rows
D3, D4, D7 and D8 are gone: they described how the effect cores of the Electron app did the work,
and no Swift code works that way. The other IDs stay as they were, so the gaps are expected.

A row you can see is marked "for the hands-on test", and you check it by hand at O1 using
`docs/hands-on-tests.md`.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| D1 | The error codes and the System Settings panes | The codes `speech-asked` and `speech-denied`, their notice texts, and the Speech Recognition pane of System Settings. | None of these codes, texts or the pane exist. Only `mic-denied` has the "Open System Settings" button. | On macOS 26, `SpeechAnalyzer` needs no Speech Recognition permission (user decision, 2026-11-15: SpeechAnalyzer only). | No. macOS 26 never asks for that permission, so those notices can't appear. |
| D2 | The code for a missing engine | `no-helper`: the build has no speech helper. | `DictationErrorCode.unavailable`, with the raw value `no-helper` and the same text, means the engine isn't there. | The native app has no helper process, but the text stays the same. | No. |
| D5 | The text of a refused start | The `.catch` turns the error message into friendly text with `friendlyError`. | The dictation of a chat refuses a start in a chat with no PTY and shows the friendly text of `DictationRefusal.noTerminal`. `DictationNoticeEdgeTests` checks the text. | The refusal is a typed value inside the app, not an error message that needs translating. | No. The text is the same. |
| D6 | How a change of the view is noticed | `publish` compares the notice object by identity, so a new notice that's equal to the old one still calls `changed`. | The view is a value, so an equal view causes no call to the chat. | Swift values have no identity. | No. The same text shows, and the notice's timer starts again. |
| D9 | The download percent | A progress that isn't a number shows "NaN%". | A progress that isn't a number shows 0%. | Turning a value that isn't a number into an `Int` crashes the app. The service only ever gives a progress from 0 to 1 (Task 3). | No. |
| D10 | Reading the vim mode | `JSON.parse` reads the whole file, and the stamp is `mtimeMs` and `size`. | Only the five top-level keys that can turn vim mode on are decoded, so a 3 MB file decodes in about 5 ms (a full `JSONValue` decode took about 300 ms). Any other value for one of those keys, such as a number too large for a `Double`, just doesn't count as vim and never fails the read. Text that isn't JSON is a parse error, and the last good value stays. The stamp is the modification time in seconds and nanoseconds, plus the size (`stat`). | The read mustn't delay the hold. | No. Claude Code writes no such value. |
| D11 | The numbers of the look | JavaScript's `**` and `Math.exp`. | Foundation's `pow` and `exp`, so the last bit of a value can differ. | Each platform has its own maths library. | No. |
| D12 | Characters | `Intl.Segmenter` (the ICU of the Electron version) finds the graphemes. | The Characters of the Swift standard library (the extended grapheme clusters of its Unicode version). Two Characters count as the same only when they have the same Unicode scalars, like JavaScript's `===`. | Swift strings are made of Characters. A new Unicode version can change a rule in both apps. | No. The test texts give the same counts. |
| D13 | The engine on a Mac without SpeechTranscriber | The helper falls back to `SFSpeechRecognizer` on macOS 13 to 15, or when `SpeechTranscriber.isAvailable` is false. | There's no fallback. The engine gives `.unavailable`, and the chat shows "Dictation isn't available in this build of Bifrost." The rest of `SFRecognizer.swift` and `PickRecognizer.swift` isn't carried over. | User decision, 2026-11-15: SpeechAnalyzer only, on macOS 26 only. | Yes, but only on a macOS 26 Mac where `SpeechTranscriber.isAvailable` is false, where dictation doesn't work. For the hands-on test. |
| D14 | A start while the engine boots | The service sends the start at once, and the helper acts on it after its boot, so a hold that ended during the boot still opens the microphone briefly before the stop ends that session. | The service begins a session only once the engine is ready. A start during the boot waits for ready, and a hold that ended before then begins no session, so the microphone never opens. | The engine runs in the app process, so the service knows the engine's state at each start. | Only in the microphone indicator of macOS, which doesn't light up for a hold that ended during the boot. For the hands-on test. |
| D15 | A start during a model download | The helper answers each start during a download with the progress. A start that's still in the pipe at the very end of a download can open a session after ready, and the view then gets ready before the first level or text. | The service decides each start from the state of the engine, so a start during a download never opens a session. A level or a text only ever comes from a session the service began after it gave ready, so the Electron race, where a late start opens a session after ready, can't happen. | There's no pipe between the service and the engine. | No. The race needed a start at the very end of a download, and the view then got model-ready, as it does now. |
| D16 | The dictation timers | Each turn has its own timers: the hold limit or the stop wait, and the end limit. | The service has four timers: the idle rule, the 2-minute limit of the dictation that's running, the engine limit of the boot or begin that's running, and the 2-minute stall limit of a model download (row D27). Only one dictation runs at a time, so one hold limit is enough. No timer waits for an end, because the session waits at most 1.5 s for its final text (row D24). | The engine runs in the app process, and its calls end or fail on their own. | No. |
| D17 | The range checks on events | `parseHelperLine` refuses a level or a progress outside 0 to 1, a language ID that's empty or over 64 units, and a line over 64,000 units. 10 bad lines fail the helper. | The engine gives typed events. Its level meter and download progress keep each value in 0 to 1, and the notice shows a progress that isn't a number as 0%. The language ID comes from macOS, so the service doesn't check it. There are no lines, no line limit and no count of bad lines. | The engine gives typed events. | No. |
| D18 | Process failures | A crash or spawn error of the helper fails it, and the next warm-up starts a new one. The helper stops 2 s after its stdin ends. The helper fails with no ready within 10 s, and with no end within 5 s of a stop. | There's no process, because the engine runs in the app. The failures that remain are a failed boot, a failed begin, a failed session and the engine limit: 10 s for the boot (a model download isn't held to it, and the 10 s start again when the download ends, row D27) and 10 s for a begin. The boot and a begin wait on the speech service of macOS, which can stop answering. The 5 s end limit goes, because the end of a session has its own 1.5 s limit. Each boot keeps its own order of sessions, so after a begin hangs, the next start boots a new engine rather than waiting for it (Task 26), and once the engine is released that begin opens no microphone. Each failure writes one log line with none of the user's text. | The global constraints of the plan remove the pipe protocol, the process code and the build step. Swift rework Task 25: a limit only where a call could otherwise wait forever. | No, in normal use. Only when the speech service of macOS stops answering during a begin: the chat then shows the error 10 s after the begin, even while the key is held, rather than 5 s after the release. |
| D19 | Closing a window | The page ends, so each chat stops its dictation. The helper stays until the app quits or the idle rule ends it. | Each chat stops its dictation, and the shell also calls `stopAll`, which closes the session at once and releases the model and the audio engine. | The microphone must close when the window closes. | Yes, a little: the first hold after you reopen the window loads the model again, so the green look can take longer to appear. For the hands-on test. |
| D20 | Keeping the model in memory | `modelRetention: .processLifetime` keeps the model for the lifetime of the helper. The idle rule ends the helper, and the model with it. | `.lingering`, and the idle release also calls `SpeechModels.endRetention()`. | In the app process, `.processLifetime` would keep the model for the whole lifetime of the app. | No. |
| D21 | Asking for the microphone | The helper asks for the microphone and for Speech Recognition at the first hold. | The service checks only the microphone before each begin, and asks once. | Row D1: macOS 26 needs no Speech Recognition permission. | No. |
| D22 | Drawing the green look | CSS: `border-top-color`, a `box-shadow` of `0 -b b -b`, a `radial-gradient` with `filter: blur()`, and a `requestAnimationFrame` loop. | Core Animation: the top line view; for the shadow, the shadow of a strip that lies along the top edge, clipped to the area above it (`EdgeGlow`, which the cyan glow of the top frame uses too), so the light fades upwards and out at both ends; a radial `CAGradientLayer` with a `CIGaussianBlur` filter for the glow below the border, clipped to the inside of the frame so its blur never shows above it; and a display link. The glow below the border moves more with the voice than in the mock: it reaches 80 points down rather than 65, its alpha goes up to 0.77 rather than 0.65, its ellipse widens from 55 % to 72 % of its width where the mock kept 67 %, and the level falls with a time constant of 150 ms rather than 220 ms. At level 0 it looks the same as the mock. | The native app has no CSS, and a Core Animation shadow is the native way to blur a shape. The user asked for a little more motion and growth on the glow after trying it (user decision, 2026-11-18). | Yes, on purpose: the glow is higher, brighter and wider than the approved mock while you speak, and it falls back faster. The blur can also differ a little. `GlowLookTests` renders the frame and checks the shadow against the Gaussian fall-off of the mock, and checks that the glow is a soft hump. For the hands-on test (O1). |
| D23 | Which view a dictation belongs to | The page passes the view ID as text. `dictation-ipc.ts` refuses a view that isn't a chat view (`CHAT_VIEW`) and logs a line. | The view is the chat's `SessionID`: the chat passes it, and the service keys its dictations and events by it. Because the type only holds a session ID, text that isn't one, or a panel of another kind, can't reach the service at all, so there's nothing to log. | The chat window calls the service inside the app process, so no text comes from a page, and a typed value needs no fallback text (the final review of phase 3b). | No. |
| D24 | The end after a stop | The service waits 2 s for the end from the helper, then gives the text so far. The helper runs every start, even one that a stop follows at once, so the microphone opens briefly. | The end comes from the session: the final text, or the text so far when the final text doesn't arrive within 1.5 s. A dictation that stops before its begin has run, for example while the session before it is still ending, begins no session and gets an empty end at once. | There's one microphone, and a begin waits for the end of the session before it, so the service knows the begin hasn't run yet. | Only in the microphone indicator of macOS: a hold that ends while the previous session is still ending doesn't turn the microphone on. For the hands-on test. |
| D25 | White space in the vim mode read and in the space before a dictation (rework Task 16) | JavaScript `\s` and `trim`: U+FEFF is white space and NEL (U+0085) isn't. | `Character.isWhitespace`: NEL is white space and U+FEFF isn't. A space with a combining mark is also white space. | One text rule for the whole app (`TextRules.swift`). | No. Claude Code writes no such mode value, and the typed tail has no NEL because it drops the C1 controls. |
| D26 | The voice level bar for VoiceOver | `role='img'` with the label "Voice level" and no value. | A level indicator with the label "Voice level" and a value from 0 to 1, the level that the bar shows. VoiceOver reads the value when it asks for it, and a change of level posts no notification. | VoiceOver can read the level. | Only with VoiceOver, which reads the voice level of a chat that's listening. For the hands-on test. |
| D27 | A model download that stalls | The helper sends the progress every 500 ms, even when it doesn't move, so the service never stops a stalled download, and the hold shows the same percent until the app quits. | The progress only comes when it changes. If it doesn't change for 2 minutes, the engine fails with no-model: the chat shows "Bifrost can't get an on-device speech model right now. Hold the key to try again later.", and the next hold starts the download again. Focusing a chat doesn't start it. | The lane review of the audit: a stalled download mustn't hang with no way out. | Yes, but only when a download stalls for 2 minutes. For the hands-on test. |
