# Deliberate differences

This table lists the places where the native stores behave differently from the TypeScript code
of the Electron app on purpose. The TypeScript code is the reference for what the app decides, not
for how it does it. The last column says whether someone using the app would notice the
difference in normal use, and a row marked "for the hands-on test" is one to check by hand in the
real app.

The table covers the safe JSON files (`json-file.ts`), the settings model (`settings.ts`), the
settings store (`settings-store.ts`) and the unknown fields of `registry.json`.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| S1 | Unknown top-level fields of a stored file | `parseSettings` and `loadStore` drop any key they don't know, and a save writes only the known keys, so a field of a newer app is lost. | `Settings` and `RegistryStore` keep every top-level key that their coding keys don't name (`UnknownFields`), and write those keys back after the known ones when they save. A known key never counts as an unknown field. | A file from a newer app must lose nothing ("Files on disk" in the architecture design). | No. |
| S2 | `keys` and `dailyUpdate` in settings.json | The parse applies the rules of `keys.ts` and `daily-update.ts`. A save writes the clean form, and a missing value becomes `{}` or the default Daily update. | The parse keeps the stored JSON value as it is, and a save writes it back as it came. A missing value stays missing, and `SettingsFileEdgeTests` checks that both stay raw. The key rules read the raw value each time it's needed (`KeyChanges(stored:)` and `KeyMap(stored:)`), and the app works with typed slots and chords from there. `KeyChanges.stored(keeping:)` rewrites only the slots whose key changed since the load, in the standard form, and leaves every other entry alone. So a save keeps the entries of slots this version doesn't know, and keys that a later version wrote and this version can't read (a new modifier, for example), which the key map treats as the default key until then. Only Settings > Keys (the key recorder and Reset all keys) and a key edit (`KeyEdit`) write `keys`. The recorder and a key edit rewrite only the slots they change, and Reset all keys removes only the entries this version can read (`KeyEditor.resetAll`), so the keys of a later version survive both. Phase 5 ports the rules of the Daily update. | The key rules read the raw value whenever they need it, so keeping it raw loses nothing that a later version wrote. The Daily update has no rules in the app until phase 5. | No. The key map of a raw value is the one the Electron app reads from the same value. Reset all keys in the Electron app saved an empty map, which removed the keys of a later version too, and the native reset keeps them. No part reads `dailyUpdate` before phase 5. A missing value gives the same defaults in both apps. |
| S3 | The order in which a change is checked | The checks follow the key order of the patch object, and the first bad key gives the reason. | A change is an edit of a `Settings` value. `Settings.validated()` checks the whole value in the order of the fields of the `Settings` interface in `settings.ts`. | A Swift struct has no key order. | No. The settings window changes one field at a time, so an edit has at most one bad field. |
| S4 | The refusals that the types make | A patch that isn't an object gives `refused: bad settings`, an unknown key gives `refused: unknown setting <key>`, and a wrong JSON type, a bad enum value, a number that isn't whole or a font with extra keys gives `refused: bad <key>`. | A `Settings` value can't hold any of these, so no Swift code gives these refusals. The tests of an edit's check cover every value the types can hold. | The types refuse these values before a check can run. | No. The settings window makes each edit from typed controls. |
| S5 | Text rules (D3 and D12 of the registry) | `trim` and the `\S` check after "/" use JavaScript white space, in which U+FEFF is white space and NEL (U+0085) isn't. `includes` compares UTF-16 units. | `trimmed()` and the check after "/" use the Unicode White_Space property (`Character.isWhitespace`), so NEL is white space and U+FEFF isn't. The trim removes whole `Character`s, so a combining mark after a space at either end goes with it. A repeated slash command is found with Swift String equality (canonical equivalence). An ignore entry is ASCII once it's checked, so it compares the same in both apps. | The Swift rule is the Unicode rule, the same as in the registry. | No. A user can't type these characters at the ends of a command or a font family, and two forms of one accented letter in two commands isn't a normal case. |
| S6 | JSON text that only one of the parsers accepts | `JSON.parse` accepts a number outside the `Double` range (it gives Infinity, and that field gets its default) and a lone surrogate escape such as `"\ud800"`. It refuses a byte order mark at the start, and a repeated key keeps its last value. | `JSONDecoder` refuses the whole file for the first two, so every field gets its default and the store keeps a copy of the file before the first save (S9). It accepts the byte order mark, and a repeated key keeps its first value (D11 of the registry). | These are the rules of the two parsers, and JSON sets no rule for a repeated key. | No. Neither app writes such text, because both write the output of their JSON encoder. |
| S7 | The text of a written file | `JSON.stringify(data, null, 2)`, which writes `"key": value` with the keys in insertion order. | `JSONFile.encode`, which writes `"key" : value` with sorted keys, "/" unescaped, and an empty object as `{`, an empty line and `}`. Each file ends with a newline in both apps. | That's the form of `JSONEncoder`, and the form `registry.json` had in the pilot. | No. The JSON data is the same. |
| S8 | Cleaning up after a failed write | After any failure, the write removes the temporary path, even when it failed to open the temporary file. | The write removes the temporary file only when its own open created it, so it never removes another writer's file. | A file that the write didn't create isn't its file to remove. | No. Each temporary name has a new UUID. |
| S9 | A settings.json that doesn't parse at all (bad JSON, or the text of S6) | The load gives the defaults, and the first save writes over the file. | The load gives the defaults. Before the first save over the file, the store copies it to `<file>.unreadable` once, logs where the copy is, and then writes. A new copy replaces an old one, so the folder keeps one copy, and a failed copy turns saving off so the file stays. The store copies rather than renames: it uses the copy step of the later-version backup and then lets the safe write replace the file, which ends in the same state and never leaves the file missing. | `JSONDecoder` refuses some text that `JSON.parse` accepts (S6), and without the copy a file that the user edited by hand would lose all its values. | No in normal use, since neither app writes such a file. The copy is one extra file in the support folder. |
| S10 | The lines of the log | `log(message, error)` gets the error object, the load logs nothing about bad values, and a listener that throws gives `A settings listener failed.` | Each event is a `StoreEvent` that goes to the macOS unified log (category `stores`) with the path and the error private: a read error, a kept copy, a failed copy, and one line with the sorted keys that fell back to their defaults. For a file of a later version, that's every known key in the file. The store has no listeners, because the app observes the settings. | The unified log keeps the paths private, and the decoder logs a bad field. | No. Only the log shows it. |
| S11 | The errors of a change | `update` and `change` reject with `Error(reason)`, or with the error of the write. | `edit` throws `SettingsError`: either `.refused(SettingsRefusal)`, with a case for each reason, or `.notSaved(FileError)`, with the call, the path and the error number. `message` gives the text: the same reason text for a text field, `Bifrost can't use that value for <field>.` for a value out of range, or the text of the error (`ErrorText`, S13), for example `Cannot save <file>: Permission denied.` The text names the save and the path of the file, not the step that failed or the temporary path. | Typed throws, which keep a failed write and a refusal as two separate cases. | No for a refusal, because the settings window shows the same reason text. The text of a failed write is S13. |
| S12 | A registry.json that doesn't parse at all (bad JSON, or the text of S6) | The load gives an empty store for bad JSON. For the text of S6, `JSON.parse` reads the file and only the bad value is lost. The next save writes over the file. | The decode gives an empty store for bad JSON. For the text of S6 it drops only the bad value, as the Electron app does, but because `JSONDecoder` can't read the file as a JSON value, a save would lose the unknown fields and the exact text. So in both cases, before the first save over the file, the shared saver (`FileSaver`, which `StoreSaver` wraps) copies it to `registry.json.unreadable` once and logs where the copy is. A new copy replaces an old one. A failed copy is logged and turns saving off, so each later save does nothing, as after a read error. The open logs to the same store log as the other stores, and its read error line ends with the message of the error. | `registry.json` holds the local session names that the user typed. | No. Neither app writes such a file, and the copy is one extra file in the support folder. |
| S13 | Error texts | Node uses its own form, with the error name, the libuv text, the call and the path, for example `EISDIR: illegal operation on a directory, open '<path>'` for a read, `... copyfile '<file>' -> '<copy>'` for a copy and `EACCES: permission denied, open '<temporary path>'` for a write. | Error texts are native Swift texts (user decision, 2026-11-15). `ErrorText` gives `<action> <path>: <reason>.`, for example `Cannot read <path>: Is a directory.`, `Cannot copy <file> to <copy>: Is a directory.` and `Cannot save <file>: Permission denied.` The reason is the system's text (`strerror`), with no POSIX error name. A registry failure gives its message, and any other error gives its `localizedDescription`, never the debug text of an `NSError`. | The user asked for one native form for all error texts. | Yes, accepted. The settings window and the log show the text. |
| S14 | The name of the backup copy of a later version | The name uses JavaScript's `String(version)`, for example `settings.v2.backup.json` or `settings.v1e+21.backup.json`. | The name shows the version as a whole number with no `.0` when it fits an `Int`, and otherwise as the `description` of the `Double`. | There's no need to copy the JavaScript number format. | No. The names differ only for a whole version from 2^63 to 10^21, which no app writes. |
| S15 | The length limits of a slash command (200) and a terminal font family (64) | `length`, which counts UTF-16 units. | `count`, which counts `Character`s, so an emoji or a letter with a combining mark counts as one. | Every length limit in the app counts `Character`s. | Yes, for the hands-on test: a slash command of up to 199 emoji after its slash, and a font family of up to 64 emoji, fit their limits, where the Electron app refused more than 99 and 32. |
