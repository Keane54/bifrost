# Deliberate differences

This page lists the places where the native app deliberately behaves differently from the
Electron app's TypeScript code for running programs: the process runner (`execFile`), the child
environment, the login environment, the path of claude, the claude runner and `listAgents`. The
TypeScript code is the reference for what Bifrost decides, not for how it gets there. The last
column says whether you'd notice the difference in normal use.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| P1 | The login environment | The script runs the app binary as Node (`BIFROST_NODE`, `ELECTRON_RUN_AS_NODE=1`), and Node prints `process.env` as JSON between the markers. The shell gets the two helper keys, and the result drops them. | The script runs `/usr/bin/env -0` between the markers, and the shell only gets the six shell keys. The parser splits the entries at NUL and each entry at its first `=`, and skips empty entries (the output ends with a NUL). An entry with no `=` or with an empty key gives no environment. | A native app has no Node. `env -0` prints the same environment, and a value can hold a line feed. | No. The environment has the same keys, apart from `_`, which holds the path of the program that printed it. |
| P2 | The end of a command | Four optional flags: `timedOut`, `overflow`, `aborted` and `signal` (a signal name). | One value, `ExecEnd`: `exited`, `timedOut`, `overflow`, `cancelled`, `notStarted` or `signal(Int32)` (a signal number). As in Node, a program that exits with code 0 after the timeout gives `exited`, not `timedOut` (final review, item 4). | One value can only hold one end, so two flags can never disagree. | No. |
| P3 | The output limit | Node stops the program at `maxBuffer`. stderr is the program's stderr, or `stdout maxBuffer length exceeded`. Node keeps the decoded text up to a cut that it makes in UTF-16 units. | stderr is the program's stderr, or `The output is over the limit of <n> bytes.`, and the runner keeps the first `<n>` bytes of each stream. | The text names the limit, and the cut is a byte cut. | No. The limit is 1 MiB, and the output of `claude agents --json` is much smaller. No caller shows the output of a command that went over the limit. |
| P4 | The text of the output | UTF-8 by default. A caller can ask for latin1, so that each byte is one character. | UTF-8, with U+FFFD for a byte that isn't UTF-8, and no latin1 option. | No phase 2 caller needs latin1. A later caller that reads a binary file can get a byte option then. | No. |
| P5 | The error texts of a program | Node's `execFile` gives `spawn <file> <error name>` for a start error, for example `spawn /x ENOENT`, and `Command failed: <command>` with a line feed for a program with no exit code. `listAgents` gives `claude exited with code <n>`. | Error texts are native Swift texts (user decision, 2026-11-15). `ErrorText` gives `Cannot start <program>: <reason>.` (with `in <folder>` after the program when the folder of the run is the problem), `<program> stopped with signal <n>.`, `<program> did not finish within <n> s.` when the run's time limit stopped the program (final wave of phase 3a), and `claude stopped with code <n>.` The reason is the system's text for the error (`strerror`). The runner checks the folder and the file before the start, and gets the same error number as Node. A program that writes to stderr keeps its own stderr. | The user asked for one native form for all error texts. | Yes, accepted. The error line of the session list shows the text. |
| P6 | A name with no slash | libuv searches the `PATH` of the command's environment. | The runner searches the `PATH` of the command's environment, or `/usr/bin:/bin` when it has no `PATH`. It skips an empty or a relative folder, and only takes a regular file that the user can run. | The runner hands Foundation `Process` a full path, and an empty or relative folder would depend on the app's current folder. | No. A normal login shell's `PATH` has no empty or relative folders. |
| P7 | The test home (`test-home.ts`, final review item 2) | `testHomeConfig` gives the home and Electron's `userData` folder. A refused value makes `index.ts` print `testHomeError` and exit with code 1. The default real home is the home in the user database (`userInfo().homedir`). | `HomeLocator.testHome` only gives the home, because the native app finds its folders with `DataFolders`. `HomeLocator.choose` gives the app's home: the release app ignores the variable, and the development app doesn't start with a refused value. The app shows the start-error alert, `<name> can't start`, with the text of `HomeLocator.refusalText`, then quits. The launch code gives the real home (`homeDirectoryForCurrentUser`, which is the home in the user database and doesn't read `HOME`). | A native app has no Chromium folder, and an alert is how the native app reports a start error. The release app never has a test home (phase 1). | No. Only a test sets the variable. |
| P8 | The login shell for the path of claude (sessions review, 2026-11-17) | Two login shells: `resolveClaudePath` runs `-lic 'command -v claude'` with the app's full environment, and `loadLoginEnv` runs the env script with only the six shell keys. A shell with no path gives the first runnable known path. | One login shell, with only the six shell keys, gives both the path of claude and the environment of the claude runs. A shell with no path gives the first claude on the app's own `PATH` (`ProgramLookup`), then the first runnable known path. | One shell start fewer at each launch, and claude runs in the environment of the shell that found it. The lookup on the app's `PATH` keeps a claude that only that `PATH` has, which the full-environment shell used to find. | Rarely: only when the app starts with a `PATH` (for example from a terminal) that has a different claude ahead of the one that the login files give. Bifrost then uses the claude of the login files. |
| P9 | A program that outlives its SIGTERM | With `killSignal: 'SIGTERM'`, Node sends SIGTERM at the timeout and then waits for the program to end, however long that takes. The caller has to race the run against its own limit (as `claude rm` did), and the program can keep running after that. | `Command.terminateGrace` (5 s by default) starts at the SIGTERM of a timeout, a cancel or the output limit, on the runner's clock. A program that still runs at its end gets SIGKILL; one that ends within it gets none. `nil` turns the grace off for a command that must never get SIGKILL, and its caller sets its own limit. | A command that asked for a clean stop shouldn't be able to hold its caller, and a session lock, for ever by ignoring SIGTERM. | No: only a program that ignores SIGTERM sees it. |
| P10 | A test home inside the real data (holistic review, 2026-11-18) | `testHomeConfig` refuses only `/`, the real home and a parent of it. | `HomeLocator.testHome` also refuses a folder at or below `~/.claude`, `~/.claude.json`, `~/.bifrost`, `~/.bifrost-native-dev` and the two Bifrost support folders, by the paths as given and by their real paths. The refusal text names these data folders. | The app writes its shared state (the Live socket, the mod and skills folders, the settings of the plugin commands) into the test home. A test home inside the real data would put those writes into the real files of Claude Code or Bifrost. | Only to a developer who sets `BIFROST_TEST_HOME` to such a folder. Hands-on test. |
