# Deliberate differences

This table lists the places where the native Overview rules work differently from the Electron
app's TypeScript code on purpose. That code (`config.ts`, `rows.ts`, `columns.ts`, `format.ts`,
`session-icon.ts`, `table-state.ts` and `settings-model.ts` in `src/renderer/src/overview/`) is the
reference for what the Overview decides, not for how it gets there. The last column says whether
you'd notice the difference in normal use, and a row marked "for the hands-on test" is one to
check by hand in the real app.

OV1 and OV6 are the rows a user can see: OV1 only for unusual session names, and OV6 only for
names with emoji or accents. OV8 to OV10 cover the table itself (`OverviewTable.tsx`, `cells.tsx`
and `SessionIcon.tsx`), and all three are visible. OV11 to OV16 cover the tab bar, the tab menu,
the Overview Settings panel and the Overview items of the Panel menu (`OverviewTabs.tsx`,
`OverviewSettingsPanel.tsx` and `PanelMenu.tsx`), and all six are visible. OV18 covers the row
icon of a session that an app is showing (`SessionIcon.tsx`), and it's visible too. The other rows
change nothing on screen.

Three functions look different and give the same values. `TimeText.ageStep` (shared with the
Usage HUD) returns a `Duration` where `ageStepMs` returned milliseconds. `previewLines` splits a
message at each line feed by Unicode scalar, so a Windows line ending (CR LF) gives the same lines
as in the Electron app, even though Swift treats CR LF as one character. Its trim follows row OV2.
`nextColour` takes a `KeyName` where the TypeScript took the text of the key.

| ID | Where | TypeScript | Swift | Reason | Visible? |

| OV1 | Sorting the text columns (Name, Project, Branch and Model) | `Intl.Collator('en', { numeric: true, sensitivity: 'base' })`. | `compare(_:options:range:locale:)` with `.caseInsensitive`, `.diacriticInsensitive` and `.numeric` and the `en` locale. On macOS 26.6.2 the two agree on case, accents, digits, punctuation, symbols and most emoji, with four exceptions. A skin tone modifier doesn't count, so 👍 and 👍🏽 are equal and keep the session list order, and 👍a sorts before 👍🏽b (the Electron app put 👍 first and 👍🏽b before 👍a). A run of digits ends where the digits change script, so "2٣" reads as 2 then 3 instead of 23. A number above 18,446,744,073,709,551,615 wraps around, so "x18446744073709551616" sorts like "x0". A zero-width space (U+200B) counts, so "é" followed by one sorts after "e" instead of level with it. The compare comes from the system, so a macOS update can change these cases. | The system compare sorts names the way a person reads them, and for ordinary names it gives the same order as the Electron app. | Yes, but only for names like these. The user evaluates it by hand, for the hands-on test. |
| OV2 | Trimming a tab name and the set name | JavaScript `trim`, in which U+FEFF is white space and NEL (U+0085) isn't. | `trimmed()` uses the Unicode White_Space property, so NEL is white space and U+FEFF isn't, and a combining mark on a space at either end goes with it. | It's the text rule of the whole app (`TextRules.swift`), as in D3 of the registry and U4 of the windows. | No. A user can't type these characters at the ends of a name. |
| OV3 | The order of the width keys in the saved file | The widths object keeps the order in which the user set the widths, and the save writes them in that order. | The widths are a dictionary with no order, and the store writes the keys sorted. | The same widths always give the same file, and the key order means nothing to the parse. `theWidthsEncodeWithSortedKeys` checks it. | No. |
| OV4 | An action that changes nothing | `overviewReducer` returns the same object, and React skips the update. | `apply` returns false and the config stays equal to what it was. | A Swift value has no identity, and the result tells the caller when to save. | No. |
| OV5 | Values far out of range | Numbers are doubles: a time difference never overflows, a cost of 1e21 or more shows in exponent form, and `moveTab` takes only -1 or 1 by its type. | Times are `Int` milliseconds, and a difference that doesn't fit gives no age text and a 60 s step, as a bad time did. A cost of 2^40 dollars or more uses the digits of `String(format:)`, so a halfway value can round to even and a huge one shows all its digits. `moveTab` takes any `Int` and refuses a move off either end, including one that overflows. | Each value comes from a row or from the app's own code, and none comes near these limits. | No. |
| OV6 | The length of a tab name (24) and of the set name (40) | `length`, which counts UTF-16 units, so an emoji outside the basic plane counts as two. | `count`, which counts `Character`s, so an emoji or a letter with a combining mark counts as one. | Every length limit in the app counts `Character`s, as the layout names in the same ui-state.json do (U5 of the windows). Every name that the Electron app accepted still fits. | Yes: a tab name of up to 24 emoji and a set name of up to 40 emoji fit, where the Electron app refused more than 12 and 20. The user evaluates it by hand, for the hands-on test. |
| OV7 | Fields of a saved config or tab that the app doesn't know | `parseOverviewConfig` builds new objects from the known fields, so a save drops every other field. | `OverviewConfig` and `OverviewTab` keep the fields they don't know (`UnknownFields`), and the JSON form writes them back under the known fields, so a known key always wins. The filter and the sort keep only their known fields. | A config from a newer version of the app loses nothing when this one saves it, as for every other store (U2 of the windows). | No. |
| OV8 | The scroll bars of the table | The rows area scrolls with Chromium's own scroll bars for macOS, which imitate the system ones. | The table sits in an `NSScrollView` with the system scroll bars, so they follow the "Show scroll bars" choice in System Settings: they appear while you scroll, or always. | A native table scrolls the way every other Mac list does, with the system's momentum and its own scroll bars. | Yes. The user evaluates it by hand, for the hands-on test. |
| OV9 | Dragging and resizing a column header | An HTML drag: the browser showed a faded copy of the header under the pointer, and the header under it got the drop outline. The right 6 units of a header resized it, with a handle that lit up under the pointer, and a header label lit up under the pointer. | The table's own column work (user rule: native features). A dragged header moves live with the pointer and the other columns make room, with no drop outline. The edge between two headers resizes the column on its left, with the resize cursor of macOS and no handle highlight, and a header label keeps its colour under the pointer. The click, the sort mark, the press tint and the panel colour of the header stay. | The table does the pointer work, so the header behaves like the header of any Mac list and needs no gesture code of its own. | Yes. The user evaluates it by hand, for the hands-on test. |
| OV10 | The tooltips of the Project cell and of the row icon | A `title` attribute, so Chromium shows its own tooltip after its usual delay, in the system look. | The cells use the Bifrost tooltip (`TooltipController`): it opens after the pointer rests for 300 ms, at once while another tooltip shows, and in the look of the other Bifrost tooltips. | Bifrost draws all its own tooltips (user decision), so these match the tooltips of the frames and the side bar. | Yes.
