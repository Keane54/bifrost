# Deliberate differences

This table lists the places where the native app shell works differently from the TypeScript code
of the Electron app on purpose. The TypeScript code is the reference for what the app decides, not
for how it does it. The last column says whether someone using the app would notice the
difference in normal use, and a row marked "for the hands-on test" is one to check by hand in the
real app.

The rows come in four groups. The D rows cover the display modes (`display-mode.ts`), the M rows
the menu (`menu.ts`), the H rows the showing of the window (`show-window.ts` and the window of
`index.ts`), and the A rows the wiring of the app. D2, D5, D6, M4, H7 and H8 are for the hands-on
test. M3 is visible, but it comes from the updater of phase 1 rather than from the shell. A3 is
visible until each panel arrives in its own phase: most in phase 4, Reviews and the Daily update
in phase 5, and the module panels after the cutover.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| D1 | Going from Fullscreen to Borderless | The `leave-full-screen` listener of `index.ts` runs `sync` before the controller carries on, so `onChange` gets `window` and then `borderless`: the mode file is written twice and the menu is built for each. | `DisplayModeController` calls `onChange(.borderless)` once, after the window is borderless. | The window is in the window mode between the two steps for no longer than one event, so one change is the true result. | No. The file ends up holding `borderless` in both apps, and no menu is open during the change. |
| D2 | A full-screen change that macOS doesn't complete | The controller waits at most 3 s for the `enter-full-screen` or `leave-full-screen` event and then carries on. For Borderless, it then calls `setSimpleFullScreen(true)` on a window that can still be in full screen, and `sync` reads the window. | There's no wait and no timer. `DisplayModeController` follows the full-screen callbacks of AppKit, and AppKit ends each change with a "did" or a "did fail" callback. A failed exit keeps the full screen and drops the Borderless step, and a failed enter leaves the window mode. A call that starts no change, because the window is already in the target state, ends the change at once. | AppKit reports the end or the failure of every change, and a borderless style on a full-screen window isn't a valid window state. | Yes, for the hands-on test. Press the green button after a toggle gets stuck: the window must go into or out of full screen, and the next request must work. |
| D3 | The check marks of the View menu | `modeHandlers` builds the menu when View is clicked and again after the change, and every change also builds it (`onChange`). | The menu is rebuilt only when a key changes. The target of the View items gives each item its check mark from the mode in `validateMenuItem(_:)`, which AppKit calls whenever the menu opens and before a menu key acts. | This is the native way to show state in a menu (`NSMenuItemValidation`). A native item doesn't move its check mark on a click, so no rebuild is needed. | No. The menu shows the mode in both apps. |
| D4 | Closing and reopening the window | Closing destroys the `BrowserWindow`. Reopening from the Dock makes a new window at the saved bounds, and the saved mode applies again. With no window, a View click only builds the menu. | The window stays after a close (`isReleasedWhenClosed = false`), and reopening shows the same window, at the place and in the mode it closed in. The saved mode applies only after the first show. A View click while the window is closed changes nothing. | The app keeps one window for its whole life. | No. The saved bounds and mode are the ones at the close, so the reopened window is the same in both apps. |
| D5 | Requests during a full-screen change | Each request waits in a queue, and the requests run in order, each after the change before it ends. | One request waits. A newer request replaces it, and a second toggle cancels a waiting toggle, because two toggles bring back the mode before them. The final mode is the same as in TypeScript, except for a View item followed by the Fullscreen toggle during one change. | Keeping one waiting request is the AppKit way: after fast clicks, the window doesn't go in and out of full screen once per click. | Yes, for the hands-on test, though only with two or more requests during one full-screen change (about a second). Press the Fullscreen key many times quickly during the animation: the window must end in a clear mode, and the green button must still work afterwards. |
| D6 | A full-screen request for a window that isn't showing | `setFullScreen` goes to macOS, which decides what happens to a minimised or hidden window. | `DisplayModeController` changes nothing when the window isn't showing (`isVisible` is false, or `isMiniaturized` is true, meaning closed, hidden or minimised), because AppKit gives no callback for a change it doesn't start. The Borderless and Window items still work. | With no wait timer, a request that AppKit ignores mustn't wait for a callback that never comes. A test window never shows, so a test never gets a real full screen. | Yes, for the hands-on test, though only with the Fullscreen key while the window is minimised. |
| M1 | The developer items of the View menu | A development build has Reload (F5) and Toggle Developer Tools. | There are no developer items. | The native app has no web page to reload and no web developer tools. | No. A release build of the Electron app has no developer items either. |
| M2 | The items of the Edit menu | Electron's role items (`undo`, `redo`, `cut`, `copy`, `paste` and `selectAll`), to which macOS adds Writing Tools, AutoFill, Start Dictation and Emoji & Symbols. | The items use the same AppKit actions (`undo:`, `redo:`, `cut:`, `copy:`, `paste:` and `selectAll:`) and go to the first responder, and macOS adds the same items. | Electron's role items are these AppKit items. | No. |
| M3 | Check for Updates… in the app menu | There's no such item. | The updater item from phase 1 (the Sparkle updater) stays after About, and it's enabled only when the updater can start a check. | The phase 1 plan added it with the updater. | Yes. It comes from the phase 1 plan. |
| M4 | A Bifrost menu item that can't act | Every item is enabled, and an item that can't act does nothing when chosen. | `validateMenuItem(_:)` greys out an item that can't act (`MenuItemModel.Action.isEnabled(in:)`): Window, Borderless and Fullscreen while the window is closed, Close Panel while no frame shows, and Zoom In, Zoom Out and Actual Size until the settings load. The key of a greyed-out item doesn't run it, and goes on to the window, which ignores it. | The Human Interface Guidelines say to disable a menu item that can't act. | Yes, for the hands-on test. Close every panel (or minimise every frame): Close Panel is grey and Cmd+W does nothing. Close the window: the mode items and Fullscreen are grey. |
| H1 | Writing the bounds in full screen, in the borderless mode and in a zoomed window | Each move or resize starts the timer, and the save writes `getNormalBounds`, which are the same normal bounds as before. | A move or resize in these states starts no timer, and the normal bounds don't change. A close and a quit save the normal bounds, as in TypeScript. | There's no point writing the same value again. | No. The file holds the same bounds. |
| H2 | The presentation options after the borderless mode | `setSimpleFullScreen(false)` restores the options that the app had when the borderless mode started. | The window sets no options (`[]`). | The app sets no other presentation options. | No. |
| H3 | The window level of a borderless window in an app that isn't a regular app | Electron puts the window at the pop-up menu level, so the menu bar of another app isn't above it. | The level doesn't change. | Only a headless test home uses the accessory policy, and it shows no window. | No. |
| H4 | The key window in a test home | There's no such rule. | In a Debug build with a test home, the window acts as the key window while the app isn't active (`WindowShow.actsAsKey`), so the test port can type into it. | A test window never takes the focus, and an input method context is active only in a key window. | No. Only a test home has it. |
| H5 | A saved full screen in a test home | The saved mode applies after the first show, also in a test home, so the window goes full screen. | `WindowShow.appliesSavedMode` returns false for a saved full screen when the show isn't normal (a test home), so the window stays in the window mode and the file keeps the saved mode. A saved borderless mode still applies. | The native full screen moves the window to its own space and brings it to the front, and a test home never takes the focus. | No. Only a test home sees it. |
| H6 | How a quit waits for its writes | The close event writes the bounds, and the quit carries on. | `applicationShouldTerminate` waits for the write of the normal bounds, the save of the layout and any settings write in progress, for at most 2 s in total (`QuitWait`), and then the quit carries on. | A write that never finishes mustn't stop the quit. | No. A write ends within a few milliseconds. |
| H7 | A change of screens while the window is borderless | `setSimpleFullScreen(true)` gives the window the frame of its screen once. | The window gets the frame of its screen again whenever the screens change (a new resolution, a display that's added or removed, or a new arrangement, through `NSApplication.didChangeScreenParametersNotification`) and when it moves to another screen (`windowDidChangeScreen`). | A borderless window has no title bar, so the user couldn't move or resize it back to cover the screen. | Yes, for the hands-on test. In Borderless, change the display's resolution, or plug in or unplug a display: the window should cover its screen again. |
| H8 | The appearance of the windows that Bifrost doesn't draw | The app is dark only. | The app sets the dark appearance once, on the app itself (`applicationWillFinishLaunching`), and no window or view sets its own. So the start-error alert, the About panel and the Sparkle update windows are dark too, even when macOS is in light mode. | One setting covers every window, and a new view can't miss it. | Yes, for the hands-on test. With macOS in light mode, open About Bifrost Dev: the panel should be dark. |
| A1 | Closing the window | Closing destroys the `BrowserWindow` and its page, so each chat terminal ends and its PTY closes. Reopening makes a new page, and each chat attaches again. | The window stays. At the close, the shell detaches each chat (sending SIGHUP only to each attach child) and saves the layout. A closed window has no chats, and at a reopen the chats attach again. | The app keeps one window for its whole life (D4). | No. The sessions carry on in both apps, and the chats attach again at the reopen. |
| A2 | The test port of the smoke test | There's no port. The Playwright smoke test reads the app with `app.evaluate` and clicks the page. | A Unix socket in the test home of a Debug build (`test.sock`, mode 0600) takes one JSON line in and gives one JSON line out. The requests are state, open, type, key, hold, bench, overview, setting, action, send and quit. The type, key and hold requests send key events through the key filter of the window, overview sorts an Overview, setting changes the settings with a patch, action runs a session action through the action runner and answers its dialogs, and send types a text into a session as the send box does. | A native app has no page for Playwright to drive (spec 16). | No. Only a Debug build with a test home has the port. |
| A3 | The panels of later phases | Each kind of panel has its full body. | The Overview and Overview Settings panels have their full bodies (phase 4a), and so do Settings (phase 4c), the Selected Item (phase 4b) and each chat. Every other panel shows "This panel comes in a later build of Bifrost Dev." (`LaterPanel`). The Selected Item never shows that text: until Bifrost has found `claude`, it stays empty (X32 of the actions port). | The panels come in their own phases: the Selected Item and most others in phase 4, Reviews and the Daily update in phase 5, and the module panels after the cutover. | Yes, until each panel's phase. |
| A4 | Quitting from the test port | There's no such quit. | The quit starts from a block of the run loop, after the answer has gone to the client. A quit started from a block of the main dispatch queue couldn't run its saves, because it waits for them in a nested run loop and the main queue can't run their tasks inside one of its own blocks. The 2 s time limit still ends such a quit, because the timer of `QuitWait` gives its reply through the main run loop. | The answer of the port comes from a block of the main dispatch queue (Network). | No. |
