# Deliberate differences

This table lists the places where the native session registry behaves differently from the
TypeScript code of the Electron app on purpose. The TypeScript code is the reference for what the
app decides, not for how it does it. The last column says whether someone using the app would
notice the difference in normal use, and a row marked "for the hands-on test" is one to check by
hand in the real app.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| D1 | Numbers: times, process IDs, `startedAt` | Every number is a `Double`, so the parser keeps a process ID of 1.5 or Infinity (`1e400`) and a start time of 1.5. | Times are whole milliseconds (`Int`) and process IDs are `pid_t`. A process ID or start time that isn't a whole number, or a process ID outside the range of `pid_t`, counts as the wrong type, so the entry gets no process ID and a start time of 0. The services read the wall clock as a `Date` and turn it into milliseconds where it enters the registry. | Process IDs and millisecond times are whole numbers, and `Int` compares exactly with no NaN. | No. Claude Code always sends whole numbers. |
| D2 | Sets in the store | `started`, `lastActive`, `prSessions` and `prNames` are arrays in insertion order, so a repeated value in `started` stays in the file. | They're `Set<String>`, and the file writes them, and the worktrees, in sorted order. A repeated value counts once. | The registry reads each of them into a set anyway. Only the watchlist and the deferred deletes have an order the user can see, and those stay arrays. | No. No other app reads the store file (user decision, 2026-11-16: the Electron app doesn't run). |
| D3 | Trimming text (local names, HEAD files, `gitdir` lines, git output, empty parser output) | JavaScript `trim`, which also removes U+FEFF but keeps U+0085 (NEL). | The Unicode White_Space property through `Character.isWhitespace`, which removes NEL and keeps U+FEFF. The trim removes whole `Character`s, so a combining mark sitting on a space at either end goes with it. Every text rule in the app uses this meaning of white space (`TextRules.swift`). | The Swift rule is the Unicode rule. Both characters are invisible, so a local name with one of them inside or at an end is refused anyway. | No. Only a name that starts or ends with NEL, U+FEFF or a combining mark on a space differs, and a user can't type those. |
| D4 | The length limit of a local name | 64 UTF-16 code units. | 64 `Character`s (`name.count`), so an emoji or a letter with a combining mark counts as one. | Every length limit in the app counts `Character`s. The Electron app doesn't run on this Mac (user decision, 2026-11-16), so no other app shares the store file. | Yes, for the hands-on test: a local name of up to 64 emoji fits, where the Electron app refused more than 32. |
| D7 | The `gitdir:` line of a `.git` file, and branch names | `/^gitdir:\s*(.+)$/m`, so the path can start on a later line, and a path made only of spaces gives the folder itself. A branch name can contain VT, FF or NEL. | The path is the rest of the first `gitdir:` line, trimmed. An empty path counts as no gitdir, so the reader asks git. A branch name can't contain a line break character. | git writes `gitdir: <path>` on one line, and when the file looks odd, git should decide. | No. Both apps end up asking git. |
| D8 | Rate limits: breaking a tie | The first reading in the insertion order of a `Map` wins a tie of use and time. | Readings are taken in session ID order, so the lowest session ID wins a tie. | A Swift dictionary has no order, and a rule that doesn't depend on the history of the map is easier to reason about. Test: "a tie in use and time gives the lowest session ID". | Rarely: the name in the Usage HUD when two sessions report the same use in the same millisecond. |
| D9 | Rows that share one current ID | After the row that owns the live lines, the other rows come in the insertion order of the `currents` map. On load, the first row in the key order of the file gets the live lines. | After the owner, the other rows come in row ID order, and on load the lowest row ID gets the live lines. | There's no insertion-ordered map, and the order only matters when three or more rows share one conversation. | Rarely. It needs three or more rows that hold one conversation. Test: `SharedCurrentEdgeTests`. |
| D10 | The row ID `__proto__` in the store file | `JSON.parse` returns the key, but an assignment to `__proto__` does nothing, so the loader drops the local name, current ID and short ID of that row. | It's an ordinary key. | That's a JavaScript prototype rule, not a rule of the app. | No. Row IDs are UUIDs. |
| D11 | A repeated key in a JSON object (`claude agents --json`) | `JSON.parse` keeps the last value. | `JSONDecoder` keeps the first value. | That's how each decoder behaves, and JSON itself sets no rule. | No. Claude Code writes each key once. |
| D12 | Comparing and sorting strings | `===` and `<` compare UTF-16 code units, and a name prefix is 8 code units. | `==`, dictionary keys and `<` follow the String rules of Swift (canonical equivalence and Unicode order), and a prefix is 8 `Character`s. | Swift strings are Unicode strings, and APFS also compares names without regard to their Unicode form. | No. Session IDs and short IDs are ASCII. |
| D13 | Event and forget listeners | A listener can throw, and the service catches and logs the error. | There are no listeners. State events go to the `events` stream (an `AsyncStream`), and forgotten row IDs are in the observable set `forgotten`, so a reader can't throw into the service. | This is the Swift form of the same signals. | No. |
| D14 | The text of an error line | The error text of a JSON syntax error comes from V8, and a loop error logs the error object. | The error text of the parser comes from Foundation and only goes to the log (see D27), and the log line of a loop error holds the message text. | The wording of a parser isn't a rule of the app. The tests check the kind of error, not its text. | No. The session list shows a friendly reason rather than the parser's text (D27). |
| D16 | The order of different kinds of work in one millisecond | A dependency call starts in a promise job after the decision, so where it falls among the other work of that millisecond depends on the promise jobs. | Each loop is a task on the main actor, so two loops that wake together run in the order of the main actor. Only one `claude agents` process runs at a time, in the order of the calls. | There's no event loop. Each loop keeps its own timing, and the service tests check it on a manual clock. | No. |
| D17 | A row that holds NaN | The update check compares JSON text, in which NaN becomes `null`. | Rows compare with `==`, and NaN isn't equal to itself, so such a row would go out at every change. | It can't happen: the parser of the live lines refuses NaN. | No. |
| D18 | `waitForRow` | A promise that rejects with `Error('timeout')` or `Error('stopped')`, with the timeout in milliseconds. | `async throws(RowWaitError)`, with `.timeout`, `.stopped` or `.cancelled` (the caller was cancelled), and the timeout is a `Duration`. | This is the Swift form of the same rule. | No. |
| D19 | The unknown fields of `registry.json`, and a `registry.json` that doesn't parse at all | `loadStore` drops any key it doesn't know, and a save writes over a file that doesn't parse. | The store keeps the unknown fields it loaded (`UnknownFields`), so each save writes them back. Before the first save over a file that doesn't parse, the shared saver (`FileSaver`) keeps one copy at `registry.json.unreadable`. See S1 and S12 of the stores port. | A file from a newer app must lose nothing, and Bifrost never writes over a file it couldn't read ("Files on disk" in the architecture design). | No. |
| D20 | The review folders of the branch reader | One folder to skip: the reviews folder of the app (`reposRoot(bifrostHome)`). | `skipRoots` is a list. The start plan gives `<dot folder>/reviews/repos` for the dot folders of the development app (`.bifrost-native-dev`) and of the Electron app (`.bifrost`), both in the home and in the real home, with no folder repeated: two roots without a test home and four with one. Each root gets the rules of the TypeScript root: no HEAD file is read and no git runs there, also through a `.git` file outside the root that points in. | The development app polls the real session list, which includes the PR sessions of the Electron app, and the claude of a test home gets the environment of the app, so it can list the real sessions too. | No. The Electron app shows no branch for its PR sessions either. |
| D21 | Starting with no claude | The registry starts, and every poll gives the error `claude not found`. | `AppServices` doesn't start the registry, and the session list stays in the status "claude not found", which no update can replace. | One status with the right text, and no test that depends on when a poll runs. Both apps look for claude once, at the start. | No. Both windows say that the app can't find claude until it starts again. |
| D22 | The listeners of the service | `onUpdate`, `onUsage`, `onEvents` and `onForget` add a listener and return nothing. | There are no listeners. `rows`, `error`, `loaded`, `usage`, `liveCount` and `forgotten` are observable properties, and state events come through the `events` stream. The session list reads the rows and the error from the registry from the end of the first active poll, and keeps no copy. | Observation is the Swift way, and an observer that goes away ends its own observation. | No. |
| D23 | Reading the process table to find a terminal app (user decision, 2026-11-16) | `readProcessTable` runs `/bin/ps -axo pid=,ppid=,comm=` with a time limit of 5 s and parses the text. The command is the `comm` text of `ps`, which is the first argument of the process (`argv[0]`), for example `-zsh`, `claude` or the path of a link. `ps` is setuid root, so it can read `argv[0]` of every process, and a zombie process shows as `<defunct>`. | For an external row, `SystemProcessInspector` reads no table (the scan of the `claude attach` clients is D28). For each process ID of a new external row, it walks up the chain of parents only, with `proc_pidinfo` (`PROC_PIDTBSDINFO`) giving the parent of each process on the walk. The command is `argv[0]` (`sysctl` with `KERN_PROCARGS2`, parsed the way `ps` does it), so it matches `ps` for every process the user owns (hand check in the task 2c report of phase 4a). The app isn't root, so for a process of another user the command is the path of its executable (`proc_pidpath`), and for a zombie process it's the short name the kernel keeps (`p_comm`). A process that ends during the walk ends the walk with no app. No program starts, so the read needs no time limit. | No program starts (each start is slow with the endpoint scanner on the Mac), the test sandbox needs no setuid exception, and the code is native. | No. The terminal-app rule looks for `.app/` in the command. A difference would need a process of another user in the parent walk of a session, with `.app/` in the path of its executable but not in `argv[0]` (or the other way round). The short name of the kernel has no `/`, and `<defunct>` has no `.app/`. The same read also checks the process before Take control signals it. There a zombie counts as `claude` only when its real executable file is named `claude`; the usual install is a link to a versioned file, whose zombie reads as the version and doesn't count, the same result as `<defunct>` (X5 of the actions). |
| D24 | When updates go out | Two updates of the rows are at least 250 ms apart, and so are two updates of the rate limits, and a change inside that gap goes out at its end. A new row name renames the rate limits at the next tick (up to 1 s later). | The rows, the error, the rate limits and the live count change straight after each change. | The gap was a limit of the IPC to the renderer, and the native app has no IPC. | Yes: the session rows update at once rather than up to 250 ms late, and the Usage HUD gets a new row name at once. For the hands-on test. |
| D25 | The case of a session ID | A session ID keeps whatever case Claude Code or the mod gave it. The chat panel ID pattern ignores case, so `chat:ABC...` and `chat:abc...` were two panels for one session. | A session ID in the UUID form is lower-cased wherever it comes in: the parser of `claude agents --json`, a line from the mod, a panel ID (`SessionID`), and, when the store file loads, each row ID (the keys of the maps, `started`, `lastActive`, `prSessions`, the watchlist, the worktrees and the deferred deletes) and each current ID. Two keys of one map that differ only in case become one row: the key that's already lower case wins, then the first key in sort order, and in a list the first entry of the row wins. Any other ID keeps its case. | One session has one ID, so the row, its chat panel and its live lines always match. | No. Claude Code gives lower-case session IDs, so a store file only has upper case if someone edited it by hand. |
| D26 | The branch of a folder whose `.git` is a link (SVC-18) | The reader looks at the link itself, so a `.git` link to a folder is neither a folder nor a file, and the walk carries on to the parent folder. | The reader follows links (`stat`), so a `.git` link to a folder is that repo, and a linked HEAD gives the time of its target. git gets the login environment. | The branch of the session's own repo is the right one to show. | Yes, for the hands-on test: a session in a folder whose `.git` links to a repo shows that repo's branch, not the branch of an outer repo. |
| D27 | The error line of the session list (audit, CORE-4) | Most errors reach the Overview as they are: `empty output`, `parse error: ...` with the text of the JSON parser, or the stderr of claude. Only a failed run with Node's `Command failed:` text gets the friendly `Bifrost couldn't read the session list. It tries again in a moment.` | Each reason is a case of `AgentListError` (an empty output, no array, not an array, JSON that doesn't parse, a failed run of claude, or no claude), and the Overview shows only its friendly message, for example `Bifrost can't read your sessions right now because Claude Code ran into a problem. It'll keep trying.` The detail, which is the parser's text or the stderr of claude, goes to the log once for each distinct error, marked private. | The raw text means nothing to someone using the app and can hold a path, so it belongs in the log rather than on screen. | Yes, for the hands-on test: the error line of the Overview when `claude agents --json` fails. |
| D28 | The terminal app of a background session (user request, 2026-11-18) | The app looks up a terminal app only for an external row, by the walk up the parents of its process. An owned row has no terminal app. | While the registry has an owned session, each good active poll also runs `SystemProcessInspector.attachClients`: one `sysctl` with `KERN_PROC_UID` lists the processes of the user, only a process with a controlling terminal gets its arguments read, and each `claude attach <id|name>` client gets the app of the walk up its parents. Clients below Bifrost's own process are left out. The registry reads the argument as Claude Code does (the start of an ID, or a session name) and gives each owned row that isn't parked the app of its newest client that has an app: the latest start, then the higher process ID. So `terminalOf` and the `terminalApp` of a row now cover owned rows too. | A background session runs inside Claude Code's background service, so the walk up from its process never reaches the terminal where the user watches it with `claude attach`. The scan rides on the poll that already runs, adds no timer, and reads the arguments of only a few dozen processes. | Yes: an owned row that you view in Warp shows the Warp icon (OV18 of the Overview). The user evaluates it by hand, for the hands-on test. |
