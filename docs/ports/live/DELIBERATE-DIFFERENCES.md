# Deliberate differences

This page lists the places where the native app deliberately behaves differently from the
Electron app for Live details: reading the lines of the mod (`live-event.ts`, `model-name.ts`),
parsing the one HTTP request, running the server (`live-server.ts`), the plugin commands and
their lock (`version.ts`, `plugin-cli.ts`, `serial.ts`), and the Live details control
(`live-control.ts`). The Electron app uses Node's HTTP server
for the request. The TypeScript code is the reference for what Bifrost decides,
not for how it gets there, and the last column says whether you'd notice the difference in normal
use.

## The accepted differences

in "Settings > Live details, the warning dot and the Setup dialog" below. The tests
`LiveStateTextEdgeTests` and `LiveUsageEdgeTests` pin V1, and the test `aResetTimeIsISO8601` in
`LiveLineTests` pins V2.

## The HTTP request parser

The Electron app uses Node's HTTP parser (llhttp). The Swift parser only takes the request of the
mod, `POST /v1/event HTTP/1.1` with a Content-Length and a JSON body (rework Task 24,
2026-11-16), and like Node it refuses two Content-Length lines, even with the same value. The
TypeScript column comes from a probe of Node 26 on a Unix socket. Row H3 is for the hands-on test.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| H1 | A Content-Length over 65,536 | Node reads the body. For `POST /v1/event`, the server answers 413 once the body goes over the limit. For another method or target, the Electron app answers 404 at once and doesn't read the body. | The head alone gives the answer, and the parser doesn't wait for the body: 413 for `POST /v1/event`, and 404 for another method or target, as the Electron app does. | There's no body to read and keep. | No. A line of the mod is under 30 KB. |
| H2 | The size of the head | Node refuses more than about 16 KB of header lines (`HPE_HEADER_OVERFLOW`), and doesn't count all of the request line. | The head (the request line, the header lines and the empty line) has at most 16,384 bytes. | One count, and the limits keep the parser's memory small. | No. The head of the mod is small. |
| H3 | Forms that Node accepts and Swift refuses | Node accepts a body in chunks (`Transfer-Encoding: chunked`, also `gzip, chunked`), `HTTP/1.0`, `HTTP/2.0`, two spaces between the parts of the request line, and empty lines before the request line. | `bad`: the server closes the connection without an answer, and the line is lost. | The parser only takes the request of the mod (rework Task 24, 2026-11-16). | For the hands-on test. Not while the mod sends a Content-Length, which the mod's fetch does for its text body. Phase 4d checks the requests of the native mod. A mod that sends chunks gets no Live details. |
| H4 | Forms that Swift accepts and Node refuses | Node refuses a method it doesn't know (for example `post`), a method or a target with a byte that isn't allowed, and a header value with a control character. It closes the connection without an answer. | The server answers 404 for any method or target other than `POST /v1/event`, even with such bytes. The parser reads no header value apart from Content-Length, so a control character in another value doesn't matter. | The parser only checks what the request of the mod needs. | No. The mod sends `POST /v1/event` and no control characters. |

An HTTP/1.1 request with no Host line gives `noHost` at the end of the head, and the server
answers 400, as Node does, so that form isn't a difference. The checks at the end of the
head run in the same order as in Node and the Electron app: the framing (`bad`), the Host line
(`noHost`), the method and the target (`notFound`), then the size (`tooLarge`).

## The server

`LiveServer` follows the start and stop rules of `live-server.ts` with Swift tasks: one stored
start task that a second start waits for, and a cancel for a stop (rework Task 24, 2026-11-16). It
runs the socket with `NWListener`. These rules are the same as in Node:

- A bad request closes the connection without an answer.
- A request that isn't complete after the request timeout closes the connection without an
  answer.
- A client that ends its side before the request is complete gets no answer, and the server
  closes the connection at once.
- With 64 connections open, the server closes a new connection at once.
- The server answers another method or target with 404 at the end of the head (H1).

The TypeScript column comes from a probe of Node 26 on a Unix socket. A user can only see rows
N4, N11 and N12.

The version check, the plugin commands and the lock follow `version.ts`, `plugin-cli.ts` and
`serial.ts`, with the same IDs, arguments, limits and texts. A user can't see these rows: each one
needs a hung or odd Claude Code, or two starts at once, and the Swift unit tests pin each of them.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| P1 | A write command that ignores its SIGTERM, whose caller stops waiting, or that still runs at the quit | `execFile` sends SIGTERM at 30 s and never SIGKILL. The command rejects at 40 s, and the process can run on and change the settings after the lock is free. A result after the limit always gives the timeout text. | The runner sends SIGKILL 5 s after the SIGTERM (`Command.defaultTerminateGrace`), so the command rejects at about 35 s and its process has ended.
