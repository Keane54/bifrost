# Keys: deliberate differences

This table lists the places where the native app's key handling differs on purpose from the
TypeScript code of the Electron app. The TypeScript code is the reference for what the app
decides, not for how it does it, so a row records a change of result or of approach that's worth
knowing about. The last column says whether you'd notice the difference in normal use. The key
rules themselves are in `docs/behaviour/keys.md`.

The rows cover the key rules ported from `shared/keys.ts`, the key dispatch of `KeysProvider.tsx`,
`hold-gate.ts`, `raw-chord.ts`, `focus-zone.ts`, `key-labels.ts`, the Esc rule of `commands.ts`,
`chat/key-rules.ts`, `chat/dictation-keys.ts` and the chord match of a binding. They also cover
the window key filter, which is the native form of `KeysProvider.tsx` and of the key wiring in
`chat-terminal.ts`, and the window and row commands of `commands.ts`. `promptBlocks` of
`shared/input.ts` belongs to the input port (`docs/ports/input`).

You can see rows K1, K2 and K3 in use, and the user accepted all three (2026-11-15). K8 shows only
with more than one Overview, and it's for the hands-on test. The other rows aren't visible.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| K1 | A hold key rolled over into another key (O down, P down, O up) | P's key down cancels O's pending key up, so O's key up doesn't act. The hold gate then still holds O, and the next row click becomes a hold click that opens the row (gate finding 5, scenario `hold-gate/rollover-stale`). | A hold key's key up always removes it from the hold gate, even when that key up doesn't act (`KeyLayer.handle`), so the next row click is a plain click. The pending key up still governs the command: O doesn't run Open when it goes up. | Accepted change (2026-11-15) that fixes the rollover bug of the Electron app. | Yes, accepted. After a fast O, P rollover, a click on a row selects it rather than opening it. |
| K2 | Shift+Enter in a chat while an input method is composing text | The chat input sends ESC CR, which Claude Code reads as a new line, even during a composition (gate finding 7, scenario `shift-enter/composing`). | `ChatKeyAction` sends no ESC CR while `isComposing` is true, so the key goes to the terminal and the input method gets it. The key still stops a dictation, as every other key does. | Accepted change (2026-11-15): the input method owns its keys while it composes. | Yes, accepted. While you compose text, for example with Japanese or Chinese input, Shift+Enter acts in the input method and doesn't add a new line to the prompt. |
| K3 | How the chord match compares two letters | The compare ignores case and compatibility forms. Option+0 types "º", which counts as equal to "o", so Option+0 runs an Alt+O binding (2 of 952 x 93 oracle cases: Alt+O and Alt+Shift+O). | `keysEqual` compares two letters without case but with their accents, and with no compatibility mapping, so "º" and "ª" aren't "o" and "a". The match by position still works, so Option+O ("ø") still matches Alt+O. | Accepted change (2026-11-15): a key that types a symbol isn't the letter of a binding. | Yes, accepted, but only with a custom binding of Option and a letter, on a key that types a compatibility form of that letter: Option+0 ("º") no longer runs Alt+O, and Option+9 ("ª") no longer runs Alt+A. The two oracle cases that changed aren't default bindings. |
| K4 | The end of the typed text (`typedTail`) | The rule counts UTF-16 units. The cut keeps the last 1,000 units, so it can split a surrogate pair or a grapheme, and JavaScript keeps the half pair. An escape of ESC plus one character skips one UTF-16 unit for that character, even when it's an emoji. | The rule reads Unicode scalars, and the tail keeps the last 1,000 Characters (rework Task 16), so it never splits a surrogate pair or a Character. An escape of ESC plus one character skips one scalar, and a DEL removes one Character. The U+FFFD case of gate finding 10 goes away (3 of 200 oracle traces). | A Swift String can't hold half a surrogate pair, and every length limit in the app counts Characters (change 4 of the move). | No. Dictation's typer only reads the end of the tail, to decide on its leading space. The tail is never shown, and a cut at 1,000 Characters is far from the end. |
| K5 | The fields of a key event | A `KeyboardEvent` has a legacy `keyCode`, where 229 means a key of a composition, and the event types keydown, keyup and keypress. The hold key and the matcher treat `keyCode` 229 as a composition. | `KeyEvent` holds the values of an NSEvent: the macOS key code, the characters, the characters without modifiers, the binding modifiers, and whether it's a key down or a key up. It has no DOM `key` or `code` names and no key press. `isComposing` marks each key of a composition: the window filter sets it while the first responder (the terminal or a text view) has marked text (`KeyEvent(_:isComposing:)`, `KeyFocus`). | AppKit has no key code 229 and no key press event, because `keyDown` delivers the text through the input method. The Swift tests set `isComposing` for a composition and have no key press cases (`docs/behaviour/keys.md`). | No. Each key of a composition has `isComposing`, so the rules see the same compositions, and a key press never reached the Electron rules anyway. |
| K6 | An Esc or a Tab that reaches the end of the responder chain | An event that no handler prevents gets the default behaviour of Chromium and macOS. Tab moves the focus to the next element, and an Esc that nothing prevents can end full screen ("The green button and the Esc key change the mode", `index.ts`). Bifrost's Esc calls `preventDefault` only when its intent acts, so a key repeat of Esc isn't prevented. | `BifrostWindow.keyDown` passes an Esc or a Tab that the filter didn't use on to AppKit: `cancelOperation:` ends full screen, and Tab moves the focus through the key-view loop. `endOfChain` keeps an Esc only when its intent acts (isn't `none`), so a key repeat of Esc goes to AppKit. | Found in the Task 6 review: the window took every key that no view took, so Esc couldn't end full screen and Tab couldn't move the focus. | No. The same keys reach the platform, and the focus order follows the key-view loop of AppKit, which is the native form of the focus order. |
| K7 | The focus zone of the focused view | `focusZone` reads the DOM element: its tag, its type, the roles of the element and its parents (`CONTROL_ROLES` and the dialog roles) and the data marks of its parents. | `KeyFocus` reads the first responder and its superviews. A `ChatKeyTarget` is the chat, and an `NSText`, including the field editor, is text. An `NSControl`, a view with the accessibility role of a control (button, menu button, radio button, check box or menu item, the native form of `CONTROL_ROLES`) and a view with `FocusMark.control` are controls, and so is anything inside one. A view with a `FocusMark` identifier is the send box, the key recorder or a dialog, and a view in another window, a sheet of the window or an alert of the app is a dialog. A frame's tab is a radio button, so it's a control. A focused SwiftUI button makes its `NSHostingView` the first responder, so the side bar's host has `FocusMark.control`. `FocusZone(_:)` in BifrostKeyboard keeps the order of the checks. | AppKit has no DOM, so the marks and accessibility roles of the views take the place of the data marks and ARIA roles. ARIA `option` has no role here, because a list box is a dialog in both apps. | No. A focused tab and a focused side bar button are controls, as their buttons are in the Electron app (review of Task 7). A later SwiftUI host with controls needs `FocusMark.control`, or its focused control reads as the other zone. |
| K8 | The Overview that the Overview tab keys and the row keys act on | `focusedOverview` of `commands.ts` gives the active Overview of the highest frame that isn't minimised, wherever the keyboard focus is. | `KeyCommands` first takes the Overview whose rows have the keyboard focus (`OverviewPanels.focusedPanel`), which they get from a click on them or in the Overview's tab bar, and only falls back to the highest frame when no Overview's rows have it, for example while you type in a chat. Focus Overview gives the rows of its Overview the focus, as in TypeScript. | The keys follow the Overview you clicked, which is what the keyboard focus suggests on a Mac. With two Overviews side by side, raising the other one by its title bar doesn't move the keys to it. | Yes, but only with more than one Overview showing. The user evaluates it by hand, for the hands-on test. |
