# Deliberate differences

This page lists the places where the chat window of the native app deliberately works differently
from the Electron app's TypeScript code. The TypeScript code is the reference for what Bifrost
decides, not for how it gets there, so most rows describe a different mechanism that gives the
same result. The last column says whether you'd notice the difference in normal use.

The rows cover the decisions of one window (C1 to C9, C22 and C23: the attach, the size, the agent
view and the screen rules), its terminal (C10 to C21: the terminal view, the set of chats, the
panel body and the terminal options), the texts of a refused open (C24), the Take control
loader and the attach during Take control (C25 and C26) and the trust panel of Reviews (C50). Rows
that a user can see, or might see, are for the hands-on test: C10 (accepted), C16, C17, C18, C19,
C21, C24, C25, C26 and C50.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| C1 | The time | Each step reads `Date.now()`, the wall-clock time. | The window reads the time from its owner's clock (`ChatTerminals.now`), a `ContinuousClock.Instant` that is the owner's start time moved on by the time on its injected monotonic clock. `SizeSync` gets that time, and the start of an open sets the send time, as in TypeScript. | A monotonic clock doesn't jump when you or the network change the system time, and the tests can drive a manual clock. | No. |
| C2 | The terminal's starting size | xterm.js starts at 80 x 24 and keeps that size until a size decision or an open changes it. | The first size decision always gives the terminal view its size. With no fit and no session size, that's `SizeRule.defaultTerm` (120 x 32). | `SizeSync` doesn't know the terminal view's starting size, so it never assumes one. | No. An open sets the size before the first output, and the PTY's size never comes from the starting size: `openSize` doesn't read the terminal's size, a send is always the fit or its one-row bump, and a reattach only follows an open, which has already set the terminal's size. |
| C3 | The keyboard focus after a focus gain | The window keeps the request until the text area has the focus, and tries again on each later `setView` or `setPanel`. | `SizeSync` gives `.focusTerminal` once for each focus gain, as soon as the focused window has its panel. The window waits for the press to end, checks that no menu or dialog has the focus, then focuses the terminal. | The focus is an AppKit matter, not part of the size rules. | No. |
| C4 | A size over 1000 columns or rows | Any finite fit of 1 or more, and any session size, counts. The main process then refuses an open or a resize with a bad size. | A fit, a session size or a read with 0 or more than 1000 columns or rows counts as no size (`TerminalSize.isValid`, carried over from Task 8). | The PTY accepts 1 to 1000 (Task 8), so the window never asks for a size the PTY would refuse. | No. Only a panel wider than 1000 columns of the font could have such a fit. |
| C5 | The note and the zoom | Every step sets the note text, the zoom and the pointer blocker again. | The note and the zoom (`.scale`) are only set when their value changes. | Fewer effects, with the same result on the screen. | No. |
| C6 | A close during an open | The open goes through IPC, so the window can close while it runs. The window's close shuts the view in the main process once the open finishes, and `replaced()` then tells whether a newer window of the session has the view. Only when it hasn't does the window close the new PTY again. | The open is asynchronous, and the spawn runs off the main actor (pty row T15). Closing the window cancels the open's task, so when the spawn ends, the manager closes the new child at once (SIGHUP to its pid only) and the window gets no attach. A window that closed before its open started doesn't open at all. A reattach closes the window's old attach just before its spawn. Each window owns its own attach and closes only that one, so a newer chat window of the session keeps its attach. | Each window owns the attach it opened, and the open's task carries the cancel. | No. |
| C7 | The bump timer | Every bump send starts a new bump timer, and an older one can still be running. | One `SizeSender` for each window sends the bump, then the fit 60 ms later (`SizeRule.bumpGap`). A new size only moves the time of the send, and a stop makes a fit that's waiting for the gap go nowhere. | One timer of each kind. The fit follows its bump by 60 ms, and the next send needs 150 ms of quiet, so two bumps never overlap. | No. |
| C8 | The attach history | `AttachHistory` is an object that the window and its owner share. | The owner keeps each session's history as `[ContinuousClock.Instant]` (`ChatTerminals.attachHistory`), and each check of the window reads and writes the history of its session. | A value type with one owner. | No. |
| C9 | A failed write of an older attach | Each write carries the attach number (`attachCount`). A failed write of an older attach reports back later, and the window ignores it. | A write carries no attach number. A write to the window's `PTYAttach` gives its result at once, so a failed write always belongs to the current attach. | The native app's PTY write is synchronous. | No. |
| C10 | A click on a link | Only OSC 8 links are links (the `linkHandler` of xterm.js; the app has no web-links add-on), and a plain click opens one. | A Cmd+click opens a link: an OSC 8 link, and also a plain URL in the text, which SwiftTerm finds. Opening a plain URL is new in the native app. A plain click goes to Claude Code, because Claude Code uses the mouse. | The user decision "Cmd+click opens links" (2026-11-14), which the architecture design keeps in its UI section. | Yes, and accepted by the user. For the hands-on test. |
| C11 | The scrollback | 5,000 lines (`terminal-options.ts`). | 500 lines (`ChatTerminalView.scrollback`). Phase 3b Task 5 measured eight streaming chats on the normal screen: 500 lines cost about 3.5 MB more than 200 lines, inside the 5 MB rule, so the value stays at 500. | Memory: six chats with 5,000 lines each used most of the prototype's general memory. | No. `claude attach` always uses the alternate screen, which has no scrollback. |
| C12 | A hidden chat | Visible chats draw with WebGL, up to 12 of them. A hidden chat releases its WebGL context and keeps the DOM renderer. | A hidden chat (a minimised frame or a back tab) stops its Metal renderer and leaves its superview, and a visible chat goes back and starts Metal again. Every chat keeps its PTY and its terminal model, and there's no limit of 12. | Releasing the drawing surfaces of hidden terminals saves memory, and Metal has no context limit like a web page has. | No. |
| C13 | The scroll bar and the width of the fit | A CSS rule keeps xterm.js's overlay scroll bar showing while the normal buffer has lines above the screen. The FitAddon always takes 14 px off the fit width while the scrollback isn't 0 (`FitAddon.ts`), even on the alternate screen. | While the normal screen has lines above it (never on the alternate screen), SwiftTerm's scroll bar uses the legacy style, which always shows and takes its width, about 15 pt, from the grid. Otherwise it uses the overlay style, which shows nothing without history, and the fit loses no width. So the fit can have one or two more columns than in Electron, and the PTY gets one resize when the history first appears. Row C21 covers how the knob looks. | SwiftTerm has no public way to keep its overlay scroll bar showing. | No. `claude attach` always uses the alternate screen, so the scroll bar only shows after an attach ends, on the normal screen, and Claude Code draws for the size of its PTY. |
| C14 | Reading the screen | `buffer.active` rows from `baseY`, with `translateToString(false)`. | The window reads the live screen through SwiftTerm's copied reads, never the scroll position. At the live screen (always the case on the alternate screen) it reads the visible rows (`terminalStateSnapshot`, `visibleRowsText`). After a scroll back on the normal screen, it copies the live rows from a content snapshot (`terminalContentSnapshot`). An unwritten cell before text is a space, the second cell of a wide character is empty, and SwiftTerm leaves off the unwritten cells at the end of a row. | SwiftTerm 1.99.3 has no `getTerminal()`, so the chat can't read a buffer line directly. The snapshots are its copied reads of the buffer. | No. The rules see the same rows and the same text. |
| C15 | Resizing the terminal locally | `term.resize(cols, rows)`. | The terminal view's frame becomes the frame of the size (the cells plus half a point of slack), and SwiftTerm takes the whole cells that fit. A font change sets the frame to zero first. | SwiftTerm's `TerminalView.resize(cols:rows:)` also does a soft reset (DECSTR), which shows the cursor that Claude Code hid and resets other modes. | No. |
| C16 | The Option key | xterm.js with `macOptionIsMeta` off: Option+letter types the layout's character (a dead key composes), Option+Backspace, Option+Enter and Option+Esc add ESC, Option+arrow sends `CSI 1;3 <arrow>`, and Option+Tab sends Tab. | SwiftTerm with `optionAsMetaKey` off and `optionAsMetaKeyForFunctionalKeys` on does the same for letters, Backspace, Enter and Esc. Option+Left and Option+Right send ESC b and ESC f (SwiftTerm's word moves), Option+Up and Option+Down send the plain arrow, and Option+Tab sends ESC Tab. | SwiftTerm fixes the arrow rules. Option isn't used as Meta, because with Option as Meta, Option+E sends ESC e, so a dead key and the Option characters of a layout (for example @ on a German layout) couldn't reach Claude Code. | Slightly: only the Option+arrow keys and Option+Tab differ. Check it in the real-attach check (O2). For the hands-on test. |
| C17 | The kitty keyboard protocol | xterm.js 6 has no kitty keyboard protocol, so every key has its legacy form. | SwiftTerm answers `CSI ? u`, so while Claude Code has the protocol on, keys that go to the terminal take their kitty forms. A Cmd key down with a printable character that no Bifrost key and no menu item takes goes nowhere, as in xterm.js (`ChatTerminal.isCommandText`). Its repeats and its key up go nowhere too, even after Cmd is released, so a kitty repeat or release never arrives without its press (final wave, group D). | The protocol is part of SwiftTerm, and Claude Code asks for it. | Unknown. Check it in O2. For the hands-on test. |
| C18 | The OSC 52 copy | xterm.js 6 has no clipboard add-on in the app, so the app ignores OSC 52, and a copy in Claude Code puts nothing on the clipboard. | Claude Code's OSC 52 puts the text on the pasteboard (`clipboardCopy`). A program can't read the pasteboard. | Copying from Claude Code should reach the clipboard, as it does in any Mac terminal. | Yes: a copy in Claude Code (for example, a selection made by dragging) reaches the clipboard. For the hands-on test. |
| C19 | Option and the mouse | `macOptionClickForcesSelection`: Option+drag makes a normal text selection, even while Claude Code reads the mouse, and sends no mouse report. An Option+click without a drag moves the prompt's cursor to that cell with arrow keys (`altClickMovesCursor`, on by default). | Option+drag makes a normal selection and sends no mouse report: the chat view hands SwiftTerm each left-button event of an Option press with Shift in place of Option, and Shift makes SwiftTerm skip the mouse reports. An Option+click without a drag does nothing. When Claude Code turns on the Shift capture (XTSHIFTESCAPE), Option+drag goes to Claude Code. | SwiftTerm makes a block selection on Option+drag and has no rule that moves the cursor of a prompt. | Yes: an Option+click doesn't move the prompt's cursor. For the hands-on test. |
| C20 | A reply that isn't UTF-8 | xterm.js gives each reply as a string, and node-pty writes it as UTF-8. A mouse report in the legacy encoding past column 94 has characters from U+0080 up, so each one goes to the PTY as two bytes. | SwiftTerm's bytes go to the PTY unchanged, so a mouse report in the legacy encoding past column 94 has one byte for each value, as in xterm. | A Swift String can't hold bytes that aren't UTF-8, and the PTY takes bytes. | No. Claude Code uses the SGR encoding (1006), which is ASCII. |
| C21 | The look of the scroll bar (final wave, group D) | The theme in `terminal-options.ts` colours the slider of xterm.js's scroll bar `--color-terminal-slider` (#ffffff66) at rest, `--color-terminal-slider-hover` (#ffffff99) under the pointer and `--color-terminal-slider-active` (#ffffffcc) during a drag, with no track. The slider is 14 px wide (C13). | SwiftTerm's scroller still takes the clicks and the drags on its knob, but it draws nothing (alpha 0). A slider view draws that knob in `ThemeTokens.terminalSlider` at rest and in `terminalSliderHover` under the pointer, with no track. During a drag the knob keeps the hover colour: SwiftTerm gives no public sign that its knob is being dragged, so `terminalSliderActive` goes unused. The knob has the size and the place of the legacy macOS scroller's knob (about 15 pt wide, C13). | SwiftTerm 1.99.3 has no public way to draw its scroller. | Yes, slightly: the colour during a drag and the size of the knob. The scroll bar only shows on the normal screen after an attach ends (C13). For the hands-on test. |
| C22 | The white space of the screen rules (rework Task 16) | JavaScript `\s` and `trim`: a row of only U+FEFF is blank, and a row of only NEL isn't. | `Character.isWhitespace`: a row of only NEL is blank, and a row of only U+FEFF isn't. A space that carries a combining mark counts as white space. The footer and the counts line of the agent view still match on Unicode scalars. | One text rule for the whole app (`TextRules.swift`). | No. Claude Code draws no such row. |
| C23 | The end of a refused reattach | After the wait for the session input, the rows can refuse the open of a reattach. The window ends with `[open failed: ...]`, and the view's old PTY stays open until the window closes, because only a failed write closes the PTY when the window ends. | Every end of the window closes its attach (SIGHUP to the attach child only), so a refused reattach closes the old attach too. | One rule for every end, so no hidden attach stays behind a window that has ended. | Not in normal use: only when the row changes (for example, it's parked) while a reattach waits for a send of the session input. A later send to the session then opens a hidden attach, where Electron refused it with the agent view text. |
| C24 | The reasons of a refused open (audit, CORE-4) | IPC-style texts after `[open failed:`: `refused: not an attach to an owned session that is not parked`, `refused: the attach is not for the session of the chat view`, `refused: bad terminal size` and, with no claude, `claude not found`. | Friendly texts from `AttachRefusal`: `Bifrost can only open a session it started that isn't parked.`, `This window is for another session. Open the chat again.`, `The window is too small or too large for a terminal.` and `Bifrost can't find Claude Code. Install it, then open Bifrost again.` (the text of the Overview's error line; sessions review, 2026-11-17). | You read these texts in the chat window, and the "refused:" form was the text of a rejected IPC call. | Yes, rarely. For the hands-on test: the end line of a chat whose short ID another row shares, or whose row changed during the open. The text for no claude doesn't show in normal use: without claude the session list never loads, so a chat waits for it and never opens. |
| C25 | The Take control loader (phase 4b) | `TakeControlLoader.tsx` with the CSS rule `.loader-rainbow`: a linear gradient that blends in OKLab, a mask that fades it in, and the `loader-shift` keyframes on its background position. `ChatTerminals` gets an `onShown` call from each terminal, and the line has the `status` role. | `LoaderLayer`: a `CAGradientLayer` twice the width of the band, which blends in sRGB, under a mask with the same alpha steps, and a Core Animation shift of its anchor point with the same 12-second ease-in-out, there and back. Its colours are the stops of the background's base gradient (`Motion.baseColours`: green, blue, violet, red, violet), where the CSS rule had the six app icon colours from violet to red. `ChatTerminals` observes `isShowingText` of the terminal with Observations, and a screen reader hears the line as an announcement. | Core Animation draws and moves the band without any work of the app, and it has no OKLab blend. The loader shares its colours with the window background (user decision, 2026-11-19), so it follows any change to them and never shows the yellow and orange that the background keeps out of its base. | Yes: the band has the colours of the window background, and its middle colours are a little darker than in an OKLab blend. For the hands-on test. |
| C26 | The attach during Take control | The chat window attaches as soon as its row reads as a running owned session, also while Take control still runs. The `restart-chat` step after a good Take control only restarts a terminal that ended, so an attach made during the move stays. | The window doesn't attach while Take control runs (`ChatTerminals.holdsAttach`, from `TakeControlLoader.runs`). When Take control ends, with a finish or a stop, the window attaches if its row can attach (`ChatTerminal.takeControlEnded`). | The row can show the new background process before Take control has checked that the process stays, and an attach from that moment might not be the moved session. In 1.0.0 the chat could stay on such an attach after the move, and only a close and a new open of the window attached it (bug report, 2026-11-19). | Yes: after Take control, the chat shows the session by itself. For the hands-on test. Test: `theOpenChatAttachesToTheSessionAfterTakeControl`. |
| C50 | The trust panel of Reviews (phase 5a) | `TrustPanel.tsx`: an xterm.js terminal in a panel of the web page, with the line "Claude Code asks if you trust this folder. Accept it below. Bifrost then closes this window and starts any review that's waiting." and Try again after an early end. The keys and the size went over IPC to the PTY of the trust view. | A Bifrost panel (`PanelID.trust`, `TrustPanels`) with the chat terminal of the app (`TrustTerminal`: a SwiftTerm view with the look and the options of a chat), the same line and Try again. The view is a chat key target, so the Bifrost keys of a chat apply and a plain key goes to `claude`. Its PTY is a `PTYRun` (`PTYManager.openTrust`), which the list of the attaches never shows. | One terminal and one key path for every terminal of the app. `TrustTerminalTests` pins the run, the checks and that Bifrost never types. | Yes: the trust panel looks and types like a chat window. The user evaluates it by hand, for the hands-on test. |
