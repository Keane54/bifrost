# Deliberate differences

This page lists the places where the native session input deliberately works differently from the
Electron app's TypeScript code: `shared/input.ts`, `main/actions/session-input.ts`,
`main/actions/quiet-watch.ts`, the parts of `ipc.ts` that wire them up, and the Interrupt key
(`interrupt:mod`). The session input came over in phase 3b, Task 1. The TypeScript code is the
reference for what Bifrost decides, not for how it gets there. The last column says whether you'd
notice the difference in normal use.

Rows I13 and I14 are the only ones a user can see, and both are for the hands-on test. A refused
send shows its text in the status of the send box, and a refused Interrupt in the error line of
the action runner.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| I1 | The views | The view IDs are the texts `chat:<id>` and `send:<id>`, and `CHAT_VIEW` is a pattern. | The views are `PTYView.chat` and `PTYView.input` (carried item 2). `PTYView.chat` holds a `SessionID`, so a text that isn't a session ID in the form of a chat panel can't make a chat view. | No text seams for the PTY views (3a final review). | No. |
| I2 | The time | Each pause reads `performance.now()`. | Each job reads the injected clock (`ContinuousClock` in the app) and sleeps on it until a given time (rework Task 19). | The tests move a manual clock. | No. |
| I3 | The queue of a session | Each job is a promise that starts after the promise of the job before it. | Each job is a task that waits for the task of the job before it (rework Task 19), so a job starts in a later turn, with the rows of that turn. | The Swift form of the same queue. | No. The order and the times are the same. |
| I4 | Cancelling a send | `SendTicket` and `Promise.race`: the race ends the wait of a cancelled send. | Interrupt cancels the task of each send that hasn't written yet (`Task.cancel()`, rework Task 19). A send that waits for a chat open, for quiet output or for a pause ends at once. A send in the queue ends when it starts, after the check of its row. A send in the size read ends when the read returns (a `proc_pidinfo` call and an `ioctl`), and opens no attach. Just before its first write, a send checks for the cancel. | Cancelling a task is the Swift form of the race. | No. |
| I5 | The chat attach of a job, and a chat open in flight | Each job start asks the PTY manager (`pty.has(chatView)`). The chat open waits in a loop until the session has no job (`idle`), then opens the PTY at once, so a job never sees a chat open in flight. | Each job asks the PTY manager for the chat attach (`attach(.chat(id))`) when it starts and again after the size read. The spawn of a chat attach runs off the main actor, and the manager gives no attach during the spawn. So before the open, the chat window calls `chatOpening`, which waits until the session has no job and marks the open at once. While an open is in flight, a job of the session waits. When the open ends (`opened`, or `chatOpenFailed` for any end without an attach), the job starts again with the state after the open, which is the chat attach or a hidden attach. A chat attach that opens during the size read also starts the job again, and a cancel ends a waiting send at once. | The native open is asynchronous (fix round 1 of Task 1). Without the wait, a job during the spawn could open a hidden attach beside the chat's attach, and that attach could resize the session the chat shows. | No. A job waits at most for the chat's spawn. |
| I6 | Opening a hidden attach | `pty.open` starts the child at once (node-pty), and a spawn error rejects the send with the error text. | The job opens the attach in its own task, and the spawn runs off the main actor (pty row T15). A cancel of the job during the spawn makes the manager close the new child at once (SIGHUP to its pid only), and the job ends when the spawn ends. A failed open, and an open that a close of all PTYs cancelled, end the job with `endedBeforeReady`, and the error text goes to the log. | The native PTY manager's open is asynchronous. Error texts don't need to match (user decision, 2026-11-15). | No. Phase 3b shows no refusal. |
| I7 | The terminal of the hidden attach | No terminal: the output of `send:<id>` stays in the main process, and nothing answers a query from Claude Code. | A SwiftTerm `Terminal` with no view, at the session size (`HiddenTerminalModel`). Its replies (a cursor position report, a device attributes report, a colour query) go to the PTY, with the colours of a chat terminal. It doesn't answer the kitty keyboard query (CSI ? u), so Claude Code keeps the legacy key forms, as with the Electron app, and the raw ESC of an Interrupt is the Escape key. | Claude Code gets the answers that a chat window gives, apart from the kitty protocol. | No. The attach is hidden. |
| I12 | The replies after the ESC of an Interrupt | No replies (row I7). | Once the ESC of an Interrupt has been written into a hidden attach, its terminal's replies go nowhere until the close (1 s later). The 200 ms Esc pause only covers the writes of the session input, so a reply less than 200 ms after the ESC could join the ESC into one key (fix round 1). | The session reads an ESC and the bytes just after it as one key. | No. |
| I8 | A size that a PTY refuses | A size that was read goes to the open as it is. | A read with 0 or more than 1000 columns or rows counts as no size (`TerminalSize.isValid`), and the job ends with `noSize`. | The PTY accepts 1 to 1000 (chat row C4). | No. Only a session wider than 1000 columns has such a size. |
| I9 | A value that isn't a string | `send` and `interrupt` refuse it with "refused: bad input", and `setBlocked` ignores a value that isn't a Boolean. | Nothing matches this: the Swift types only allow a session ID text, a text, a view and a Bool. | The renderer sends values over IPC, while the native calls are typed. | No. |
| I11 | `opened` for a view that isn't a chat view | Any view starts a watch, although only the chat views call it. | Only a chat view starts a watch. The watch of a hidden attach starts when the session input opens it. | Only the core opens a hidden attach. | No. |
| I13 | The text rules of a send and a rename (rework Task 16) | The trim and the white space of a rename use JavaScript `\s`, so U+FEFF is white space and NEL (U+0085) isn't. The limits (20,000 for a text, 64 for a name) count UTF-16 units. | White space is `Character.isWhitespace` (the Unicode White_Space property), so U+FEFF stays in the text, and the clean-up removes NEL before the trim. The trim removes whole Characters, so a combining mark on a white space at an end goes with it. The limits count Characters. The slash rule and the line breaks still read Unicode scalars. | One text rule for the whole app (`TextRules.swift`). | Yes, for the hands-on test: a name of up to 64 emoji fits, where the Electron app refused more than 32. A text with U+FEFF at an end keeps it. |
| I14 | The refusals of the session input (audit, CORE-4 and SVC-9) | Plain texts, three of them in the `refused: ...` form of an IPC error. A red box with no known cause blocks a send. | `InputRefusal` is an enum with a friendly text for each case. `Bifrost can only type into a session that it started and that is running.`, `The session is still starting. Try again in a moment.` and `Interrupt stopped the send before it went.` replace the `refused:` texts. Every red box has a cause, so the case of no cause is gone. | A caller can switch on the reason, and the user reads plain sentences. | Yes, rarely: the send box shows the text of a refused send, and the error line the text of a refused Interrupt. For the hands-on test. |
