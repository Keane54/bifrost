# Deliberate differences

This page lists the places where the native app's PTYs, session size reads, attach rules and link
rules deliberately work differently from the Electron app's TypeScript code: `pty-manager.ts`,
`node-pty-spawn.ts` and node-pty for the PTY, `session-size.ts` and `terminal-size.ts` for the
session size, `can-attach.ts` and `attachTarget` in `views.ts` for the attach rules, and
`open-link.ts` for the links. The TypeScript code is the reference for what Bifrost decides, not
for how it gets there. The last column says whether you'd notice the difference in normal use.

A user can see rows T9 and T14. The user decision on error texts covers T9, and the user
confirmed T14 (user decision, 2026-11-15). Rework Tasks 22, 22b and 22c and the lane F fix round
added visible changes to T14, and those are for the hands-on test.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| T1 | The start of the child | node-pty starts its helper program with `posix_spawn`, using `POSIX_SPAWN_SETSID`, `POSIX_SPAWN_CLOEXEC_DEFAULT`, `POSIX_SPAWN_SETSIGDEF` and `POSIX_SPAWN_SETSIGMASK`, with the terminal as descriptors 0, 1 and 2. The helper opens the terminal again, which makes it the controlling terminal, then changes to the folder and runs the program. | `PTYProcess` calls `forkpty`, which opens the PTY with node-pty's modes (its flags and its control characters, which are the system defaults) and the starting size, and starts a copy of the app. In the copy, `login_tty` makes a new session, makes the terminal its controlling terminal, and puts the terminal on descriptors 0, 1 and 2. Then `posix_spawn` with `POSIX_SPAWN_SETEXEC` runs the program in place of the copy, with `POSIX_SPAWN_CLOEXEC_DEFAULT`, `POSIX_SPAWN_SETSIGDEF` and `POSIX_SPAWN_SETSIGMASK`. Its file actions change to the folder (`posix_spawn_file_actions_addchdir`) and keep descriptors 0, 1 and 2 (`posix_spawn_file_actions_addinherit_np`). A pipe brings the error of a failed exec back to the app. The fork and the copy live in `PTYProcess.forkAndExec`, which only gets C values that the app made before the fork. The `fork-child` step of `scripts/check.sh` checks that its compiled code, in both the Debug and the Release build, calls no function of the Swift or the Objective-C runtime. | A native app has no helper program, and `posix_spawn` alone can't give a controlling terminal on macOS: its file actions run before the new session, so only a program that opens a terminal itself (bash, sh) would get one, and a resize wouldn't send SIGWINCH to any other program. The sessions services use no UI framework. | No. The child gets the same terminal, controlling terminal, session, descriptors, modes and signal state as in Electron, which the real-process tests show, also with a perl child that doesn't open a terminal itself. |
| T2 | The exit of a child | `onExit` gives the view, the exit code and the signal. The exit code is 0 when a signal ended the child. | The attach's `exit` gives the exit code, with the same rule, and no signal. After a close it gives no code. | No caller uses the signal: the chat window only shows the code. | No. |
| T3 | The output of a PTY | node-pty gives text chunks. The manager passes each chunk to `onData`, and the output batcher sends batches to the page. | The child holds on to the bytes. One drain at a time is in flight on the main actor, each drain takes at most 262,144 bytes, and each one is an element of the attach's `output`. A drain happens when the reader asks for the next element. The output of a closed PTY is drained and dropped until its exit. | The main actor stays free during a burst, and the order stays. The native app has no IPC to batch for. | No. |
| T4 | The signal of a close | `close` takes a signal name, and any name other than SIGHUP and SIGTERM gives SIGHUP. | `close` takes a `CloseSignal`, which is `hangup` or `terminate`. No other value exists. | The type only allows the two signals. | No. |
| T5 | A signal after the reap | The manager removes a PTY when it exits, so no later close signals it. node-pty sends a kill to the pid. | The attach has the same rule: a close after the exit does nothing. On top of that, `PTYProcess.signal` does nothing once the child has been reaped, because the reap and the signal run under one lock. | The system can give a reaped pid to a new process. | No. |
| T6 | Writing the input | node-pty writes through a libuv stream. | `PTYProcess.write` writes on a serial write queue to a master that doesn't block. A full PTY waits with `poll` until the child reads, and the lock is never held during the wait. | A paste of 1 MB mustn't stall the main actor. | No. |
| T7 | The order of `list` | The order of the opens. | The order of the view names. | A dictionary has no order, and the Performance panel (3b) doesn't show the order. | No. |
| T8 | The full redraw | `ipc.ts` looks for `ESC [ 2 J` in each text chunk and pokes the size watcher. | The chat looks for `ESC [ 2 J` in each byte chunk of its attach (`PTYAttach.hasFullRedraw`) and pokes the watcher. Both miss a sequence that two chunks split. | The chat reads every chunk of its attach anyway. | No. |
| T9 | A PTY that can't start | The manager only exists once claude has been found. node-pty throws "posix_spawnp failed." when its helper can't start. A missing folder or program makes the helper exit with code 1, so the chat window shows `[process ended: code 1]`. | `PTYProcess` checks the folder before the start. A missing folder throws `Cannot start <program> in <folder>: <reason>.`, and a program that can't start throws `Cannot start <program>: <reason>.` (`ErrorText`, as in row P5 of the process port). The chat window (Task 10) shows `[open failed: <message>]`. | Error texts are native Swift texts (user decision, 2026-11-15). | Yes, accepted (the user decision on error texts). Only a session whose folder was removed shows it. |
| T10 | Parsing a link | The browser's URL parser (WHATWG). The web target is `url.href`. | Foundation `URL`. The link first loses its tabs and line breaks, and the control characters and spaces at its ends. Every character that a URL can't hold is then percent-encoded as UTF-8, keeping the existing percent signs, and the strict parse reads the result. A web link that the strict parse refuses (for example one with a lone "%") falls back to the lenient parse, and in that case a file link only uses the part before "?" and "#". The web target is the parsed `URL`. The cases in `aLinkIsReadAsABrowserReadsIt` (`LinkRulesTests`) agree with Node. What's left: a backslash, "http:/x" and "file:x" (WHATWG reads them as "/", "http://x/" and "file:///x", and Swift refuses the last two), and a web link with a lone "%" (Swift encodes each of its percent signs again). | A native app has no WHATWG parser. | No. Claude Code prints full, encoded links (OSC 8). |
| T11 | The length of a link | `uri.length`, in UTF-16 units. | `link.count`, in Characters (rework Task 16). | Every length limit in the app counts Characters. The limit stays at 4,096. | No. Only a link of more than 2,048 emoji or other long Characters differs. |
| T12 | A chat open | `checkChatOpen` gives the session ID and the folder, and the view is the string `chat:<session ID>`. | `AttachRules.check` gives a `CheckedAttach` with the view, the short ID and the folder, and the PTY manager only opens that value. The view is `PTYView.chat(SessionID)` (final wave, group E), so the session ID must have the form of a chat panel. | One type for the attach target of a window and of an open, and a typed view needs no parse of a string. | No. |
| T13 | The device of the session size reader (Task 7 of the rework) | The reader keeps the device of each pid for 30 s, because a `ps` run is slow, and drops it after a failed size read. | The reader keeps no device. Every read finds the device, then reads the size. | Finding the device is a cheap `proc_pidinfo` call (T16), and a kept device could give a new process with a reused pid the size of the old process's device. | No. |
| T14 | The action of a file link | `openLink` decides from the link's own path: `fs.stat` follows a symbolic link, and the extension is the link path's extension. So a symbolic link with a plain name that points to an app or a script, a Finder alias file, a trailing slash (`Tool.app/`) or a dot segment (`Tool.app/.`, `Tool.app/Contents/..`, also percent-encoded) gives `shell.openPath`, which starts the app or runs the script. A package document (for example `.rtfd`) opens in its app. A path with a NUL does nothing (`fs.stat` throws). A list of 26 extensions names the runnable files, so a type that the list doesn't name (for example `.js`, `.exe` or `.mobileconfig`) opens in its default app. A folder whose name is on the list shows in Finder. | `LinkRules.check` and `LinkRules.action(for:opener:)` decide from the real path (`realpath(3)`: no `.`, no `..`, no trailing slash and no symbolic link), and a failed `realpath` does nothing. The type of the real path (`contentType`, `UTType`) decides first: a type that runs or installs something when macOS opens it shows in Finder. That covers a type that conforms to `executable`, `shellScript`, `pythonScript`, `perlScript`, `rubyScript`, `appleScript`, `osaScript`, `package`, `aliasFile`, `x509Certificate` or `pkcs12` (Keychain Access adds a certificate to a keychain, and a profile installs), and a short list of types that `UTType` doesn't mark as runnable: `com.apple.installer-package-archive`, `public.stored-url`, `com.apple.terminal.settings`, `com.apple.shortcut`, `com.apple.shortcuts.workflow-file`, `com.apple.mobileconfig`, `com.apple.configprofile`, `com.apple.provisionprofile`, `com.apple.safari.extension` and `com.sun.java-web-start`. Source code opens, even when macOS marks its type as a program or a shell script: `javaScript`, `phpScript`, `public.object-code`, `com.sun.java-class` and `com.apple.mach-o-dylib`. A file with an execute bit, a package (`isPackage`) and a Finder alias file (`isAliasFile`) show in Finder, and so does a plain file with the extension of a declared package type (for example `Flow.workflow`), because macOS gives it to the app of that type. A path with a NUL does nothing. A file that these type rules open still shows in Finder when the app that opens it would run it, or when the rules can't check that app. Launch Services gives the real path's own app (`NSWorkspace.urlForApplication(toOpen:)` of the file URL), the default app of its type (`urlForApplication(toOpen:)` of the `UTType`) and the terminals (the apps that declare `public.unix-executable`, with no list of names). The file shows in Finder when the file's app isn't the default app of its type (a per-file Open With binding, the extended attribute `com.apple.LaunchServices.OpenWith`, can name any app on the disk), when only one of the two exists, when the app has no bundle ID, when the app is a terminal or a launcher (`com.apple.JavaLauncher`, `org.python.PythonLauncher`, `com.tcltk.wish`, `com.apple.installer`, `com.apple.AutomatorInstaller`, `com.apple.systempreferences`, `com.apple.mcx.ProfileHelper`, `com.apple.keychainaccess`), when the list of terminals is empty (Launch Services didn't answer), and when Launch Services gives no answer within 5 seconds. A file with no app at all opens without one, and macOS asks for an app. Any other file opens in the app that the rules checked (`NSWorkspace.open(_:withApplicationAt:configuration:)`). The opens are asynchronous, and when you click a newer link before a link's action is ready, the older link does nothing. The action holds the real path, so Finder shows, and the default app opens, the target of a symbolic link. | A click on a link must never run a program (user decision, 2026-11-10). The Electron rule fails for these forms, and a list of extensions misses every runnable type it doesn't name. | Yes (user decision, 2026-11-15). A link in one of these forms to a program, an alias file or a package shows the item in Finder, where Electron starts the program or opens the package. For the hands-on test (rework Tasks 22 and 22b): these files now show in Finder, where before they opened in their default app: `.tcsh`; Perl modules (`.pm`) and `.rbw`, because they have the type of a Perl or a Ruby script; `.exe`, `.ipa`, `.pyc` and the other program types; `.url`, `.wflow`, `.mobileconfig`, `.configprofile`, `.provisionprofile`, `.jnlp` and `.safariextz`; and a plain file with the extension of a bundle type (for example `.saver`, `.plugin`, `.appex` or `.rtfd`). Source code opens as before, for example `.js`, `.mjs`, `.tsx`, `.php`, `Makefile`, `.mk`, `.o`, `.class` and `.dylib`, but only when its default app doesn't run it (rework Task 22c). That depends on the default apps of the Mac: a file whose default app is a terminal (on the test Mac, `.js`, `.mjs` and `.tsx` open in Warp, and `.dylib` in Terminal) or Java Launcher (`.class`) shows in Finder, and the same file opens on a Mac where its default app is an editor. Check a Cmd+click on a `.js`, a `.class` and a `.swift` link. For the hands-on test (lane F fix round): a certificate (`.cer`, `.crt`, `.der`, `.pem`, `.p12`, `.pfx`) shows in Finder, where Electron opened it in Keychain Access. A file whose default app is Wish, Automator Installer or Keychain Access (for example `.tcl`, `.p7b` or `.keychain` on the test Mac) shows in Finder, where Electron opened it in that app. A file with a per-file Open With binding to an app that isn't the default app of its type (Finder, Get Info, Open with, without Change All) shows in Finder, where Electron opened it in the bound app. Check a Cmd+click on a `.cer` link, on a `.md` file with such a binding, and on a file with no app (for example `notes.xyzzy`): macOS must ask for an app. A plain folder whose name was on the old list (for example `tools.sh`) now opens in Finder as a folder, where before Finder showed it inside its parent folder. |
| T15 | The spawn of a PTY (final wave of phase 3a, group A) | The main process spawns the PTY in `pty.open` straight away. That isn't the UI thread: the renderer opens through IPC, so for the renderer the open finishes later, and the window can close during it. | `PTYManager.open` is asynchronous. The spawn (`forkpty` and `posix_spawn`) runs on the blocking executor, off the main actor, while the manager's state stays on the main actor. The view's old PTY closes before the spawn. A cancel of the open's task, a `closeAll` or a newer open of the view during the spawn cancels the open: the open gives nil, so no caller gets that child and no callback of the view runs for it, and the manager closes the new child at once (SIGHUP to its pid only). Output and an exit that arrive during the spawn come after the open finishes. | On a Mac with an endpoint scanner, `posix_spawn` waits for a scan of every program start, so a spawn on the main actor could freeze the interface at each chat open. | No. The chat opens as before, and a window that closes during the open leaves no attach child behind, as in Electron. |
| T16 | Reading the session size (task 2b of phase 4a, user decision, 2026-11-16) | `ps -o tty= -p <pid>` gives the device and `stty -f <device> size` gives the size: two programs, each with the runner's time limit (10 s). The size has no upper limit. | `SystemProcessInspector` gets the device from `proc_pidinfo` (`PROC_PIDTBSDINFO`, `e_tdev`) and `devname_r`, and the size from `open` (`O_RDONLY`, `O_NOCTTY`, `O_NONBLOCK`, `O_CLOEXEC`), `ioctl` (`TIOCGWINSZ`) and `close`. Only a pseudo-terminal (`/dev/ttys<n>`) opens. A size that isn't valid (`TerminalSize.isValid`, 1 to 1000) gives nil, just like a failed read. No program starts, so the reads have no time limit. The watcher's 150 ms debounce stays, and the reader keeps no device (T13). | No program start, no setuid exception in the test sandbox, and native code. `O_NOCTTY` means the app never gets a controlling terminal from a session's device. | No. The chat terminal and the session input already refused a size that isn't valid, so the result is the same. |
