# Settings: deliberate differences

This table lists the places where the native Settings panel differs on purpose from the TypeScript
code of the Electron app. The TypeScript code is the reference for what the app does, not for how
it does it, so a row records a change of result or of approach that's worth knowing about. The
last column says whether you'd notice the difference in normal use. The rules of the panel are in
`docs/behaviour/settings.md`.

The rows cover the panel of `settings/SettingsPanel.tsx`, `settings/rows.tsx` and
`settings/SettingRow.tsx`, the search of `settings/search.ts`, the save tracker of
`settings/save-tracker.ts`,
the slash list edits of `settings/slash-list.ts` and its section `settings/SlashSection.tsx`,
the sections `settings/LiveSection.tsx` and `settings/SkillsSection.tsx`,
the draft rule of `settings/draft.ts`, the
General labels of `settings/general-rows.ts`, the General section of `settings/GeneralSection.tsx`
and the sections of `settings/settings-nav.tsx`, the
effects of a change and the login item of `main/settings/effects.ts` and `main/ipc.ts`, and the key
recorder of `settings/key-editor.ts`, `settings/KeysSection.tsx` and
`main/settings/key-recording.ts`.

| ID | Where | TypeScript | Swift | Reason | Visible? |
| --- | --- | --- | --- | --- | --- |
| S1 | The sections that a later build fills | Every section shows its rows, and the search looks at all nine sections. | Modules (until phase 7) keeps its tab but shows "This section comes in a later build of Bifrost Dev." in place of its rows. The search only looks at sections that have rows (`SettingsSearch.index`), so a search never lands on it, even by its title. | User decision, 2026-11-16: Settings keeps the nine tabs of the Electron app, so each section stays where you expect it while the later phases fill it. | Yes, until each section arrives. Marked for the hands-on test. |
| S2 | Start at login | The login item changes only in the packaged app with no test home (`canSetLoginItem`), so a run from the source tree saves the setting and registers nothing. | Only the release identity with no test home has a login item (`LoginItemRule`, then `SystemLoginItem` through `SMAppService.mainApp`). Bifrost Dev is a full app like the release one, yet it saves the setting and registers nothing, with or without a test home. The release app still takes the real state of its login item when it starts (`SettingsEffects.loginItemFix`). | User decision, 2026-11-16: a development build must never become a login item, which is the same promise the Electron app made for its own development runs. | Yes: in Bifrost Dev the switch saves, but Bifrost Dev never opens at login. Marked for the hands-on test. |
| S3 | The controls of the Settings panel | The rows are HTML controls styled to the Bifrost look: the base-ui check box, the browser's select and number input, and a search input. | The rows are SwiftUI controls and AppKit text fields drawn with the same look: the UI font at 12, the panel edge colour, the small dark check box with On or Off beside it (the Bifrost check box that the Overview Settings panel uses too), square choice buttons for Labels and Display mode, the dialog buttons and the stack tab style of the frame (`SettingsRowViews.swift`, `SettingsPanel`). A choice from a list is a SwiftUI pop-up menu, so its list is a macOS menu rather than a Bifrost menu, which is fine for now (user decision, 2026-11-17; a later build may move it to the Bifrost menu). A number field is a plain text field with no arrows, which refuses text that isn't a whole number when you leave it. The search and close icons and the chevron of the font menu are SF Symbols, and the check mark is drawn as the lucide check. | Native controls keep the focus, the keyboard and VoiceOver working the way macOS users expect, which a copy of the web controls would lose. | Yes: the panel looks close to the Electron one, and the details are for you to judge by hand. Marked for the hands-on test. |
| S4 | Cmd+F opens the search | `isSearchShortcut` compares the key's text with "f", so on a Russian or Greek layout, where that key types "а" or "φ", Cmd+F does nothing. | `SettingsSearch.isSearchShortcut` matches the chord Cmd+F with the app's key rules, so the key in the F position counts on a layout of another script, while a Latin layout such as Dvorak still matches by the letter. | Every other Bifrost shortcut and every macOS menu shortcut works this way, so Cmd+F shouldn't be the one that stops working when you switch layouts. | Yes, on a non-Latin layout only. Marked for the hands-on test. |
| S5 | The key recorder of Settings > Keys | The page records a key by its physical code with a recorder library, and while it records the menu is rebuilt so that it stops taking its keys (`recordingTemplate`). A dead key such as Option+E is recorded as Alt+E. A key with no binding shows "Bifrost cannot read this key. Try another key." or "Bifrost can't use this key.", an AltGr key shows "This key press types a character. Try another key.", and every key on the space bar outside the dictation slot shows "Bifrost can't use this key." | The recorder is an AppKit view (`KeyRecorderView`). The window gives it every key event and key equivalent first while it records, so the menu keeps its keys and is never rebuilt. A dead key with no Cmd and no Ctrl is refused with "That key types a character. Try another one.", a key with no binding with "Bifrost can't use this key. Try another one.", and a key on the space bar outside the dictation slot with "The space bar can't be a shortcut. Try another one." (`RecordRefusal`). With Cmd or Ctrl a dead key is a normal shortcut, such as Cmd+Option+E. Reset all keys keeps the entries that this version can't read (`KeyEditor.resetAll`). | AppKit offers a key equivalent to the window's views before the menu, so the view can take the key without touching the menu. A dead key with no Cmd and no Ctrl changes the next key you type, so it can't act as a shortcut of its own. A reset shouldn't delete the keys of a later version (stores row S2). | Yes: the texts, and Option+E is refused. Marked for the hands-on test. |
| S6 | The key that the recorder saves on another keyboard layout | The recorder saves the US key at the place of the key you press. On a German keyboard, where Y and Z swap places, Cmd+Shift+Y saves Mod+Shift+Z. The row shows ⇧⌘Z, and the shared matching then runs the shortcut on the key labelled Z, not on the key you pressed. On a French keyboard, Cmd+A saves Mod+Q and is refused as a macOS shortcut. | The recorder saves the key the way the shortcut matching reads it (`Chord(event:)`): the letter, digit or symbol that the key types when a binding can name it and matches it directly, else the US key at its place, which is the matching's own fallback. Cmd+Shift+Y on a German keyboard saves Mod+Shift+Y, and Cmd+A on a French keyboard saves Mod+A, which is then refused as the Select All shortcut. A key that the matching can't read as any binding, such as Ö on a German keyboard with no modifier, is refused with "Bifrost can't use this key. Try another one." The dictation key still saves the place, because the chat input finds the dictation key by its place. | The key you press should be the key the row shows and the key that runs the shortcut. | Yes, on a layout other than US. Marked for the hands-on test. |
| S7 | Typing while Save waits | The text fields still take text while Save waits. A draft typed during the wait isn't saved by that Save, so it's lost when Settings closes. | While Save waits, the Save button, the tabs, the search field and the text fields are off (`SettingsModel.isSaving`). | Nothing you type can slip in after Save has looked at the fields and then vanish when Settings closes, and no row can disappear from the panel, with its error, before its save comes back. A change of the settings from outside the panel can still hide a row during a search, which is accepted. | Hardly, since Save rarely takes long enough to notice. Marked for the hands-on test. |
| S8 | Settings > General | The terminal font family field suggests SF Mono, Menlo, Monaco and Courier New in a browser list as you type. A saved terminal app or project app that isn't installed shows its stored ID, such as `ghostty`. A number outside a row's range, such as a font size of 30, is refused with "That setting isn't valid.", and so is a bad font family. Start at login is greyed out in a development run, with the hint "Only works in the installed app.", and a failed change of the login item shows nothing. A click on an empty part of the panel, or a change that removes the focused field, gives the focus to the panel in the other zone, where every single-key shortcut and the hold keys act. | A small menu beside the family field lists the same four families, and a choice saves at once. A saved app that isn't installed shows its name, such as "Ghostty (not installed)". A number outside the range is refused before anything saves, with "Enter a whole number from 9 to 24." or that row's range, and a bad family gets "Use 1 to 64 characters, without quotes or ; { } < >." Start at login isn't greyed out in Bifrost Dev: the switch saves, but Bifrost Dev never becomes a login item (row S2). When a change of the login item fails, its reason stays under the Start at login row until a later change works or the real state of the login item agrees with the switch again, which Bifrost reads each time Settings opens and each time the app becomes active (`AppServices.readLoginItemAgain`). It has an "Open System Settings" button when macOS waits for your approval (`GeneralSection`). The panel itself is in the Control zone, so Enter, Space, Tab, the arrows, Home, End and the hold keys don't act there, while single letters and the Cmd shortcuts do (`SettingsHost`). | A macOS text field has no suggestion list of its own, so a menu is the plain way to offer the families. The other texts say what to do instead of only that something went wrong, and a login item that waits for approval needs a way to find the switch in System Settings. The SwiftUI controls of the panel have no view of their own, so the host of the panel carries the control mark for all of them, and the panel itself falls in the same zone. | Yes: the font menu and the texts. Marked for the hands-on test. |
| S9 | Settings > Slash commands and Settings > Keys | A refused slash command shows its reason as a plain dim line under the field, and Enter or Add in an empty field shows "Start the command with "/", with no space after it.". A failed move or removal shows its error at the bottom of the section. In Keys, Change and Reset all keys stay on while Save waits. | A refused command shows its reason in the error line of the field, with the close button that every error line has, and Enter or Add with an empty field does nothing (`SlashSection`). The error of a move or a removal shows under the list, apart from the error of the field. A search hides the field, and a command typed in it goes with the field, so Save never saves a command you can't see. In Keys, Change and Reset all keys are off while Save waits, while Clear and Reset stay on (`KeysSection`). | The field is a draft of the save tracker like any other field, so its reason belongs to its own row: a good move then never hides it, and an empty field has nothing to save. A recording or a confirm dialog that starts during the wait could save after Settings closed. | Yes: the look of the reason and the empty Enter. Marked for the hands-on test. |
| S10 | Settings > Live details and Settings > Skills | HTML in the Bifrost look: the state line, dialog buttons, the steps of Install as an ordered list, the notes, the closable error line, and for Skills the list of skills with their group labels. The Live details tab has a small white square while there's a warning. Remove asks with the page's confirm dialog. | The same parts in SwiftUI with the look of S3 (`LiveSection`, `SkillsSection`, with the shared `PluginBlock`): the dialog buttons of the panel, a numbered list for the steps, selectable texts, the `ErrorLine` of the rows, and the same square after the Live details tab title. Remove asks with Bifrost's confirm dialog over the canvas (`DialogHost`, row X23 of the actions port), and with no confirm dialog it's greyed out, as Reset all keys is. | One SwiftUI panel with native controls (S3). | Yes: the two sections and the tab dot. For the hands-on test. Tests: `LiveSectionTests`, `SkillsSectionTests`. |
| S11 | The close button of an error line | Each error line had its own small close button. | Every error line of the app uses one close button: the x icon of the app's icon set at 12 units in a 16-unit square, the hover colour under the pointer and the Bifrost tooltip "Close". The Settings rows, Live details, Skills and the Selected Item panel used to show a heavier system x of 9 points. | One shared error line in the look module, the same as the error lines of the Overview, the Watchlist and Show Info. | Yes. The user evaluates it by hand, for the hands-on test. |
| S50 | The confirm of Watch GitHub and of "Handle comments on my PRs automatically" in Settings > Reviews | The confirm dialog of the web page (`useConfirm`), in the look of the app. | Bifrost's own confirm dialog in the dialog layer of the window (`SettingsLinks.confirm`, the box of the session actions), with the same title, text and Turn on button. Cancel leaves the box off, and with no dialog the box can't turn on. | One dialog for every confirm of the app keeps the keys, the focus and the look the same everywhere. | Yes: the dialog looks like the other Bifrost dialogs. Marked for the hands-on test. |
| S51 | The ignore list of Settings > Reviews | A refused entry shows its reason as a plain dim line under the field. | A refused entry shows its reason in the error line of the row, with the close button that every error line has, and the field keeps the text (`ReviewsSection`). A good save of the list, such as a Remove, clears the reason. | The field is a draft of the save tracker, as the field of the slash commands is (S9), so its reason belongs to its row. | Yes: the look of the reason. Marked for the hands-on test. |
