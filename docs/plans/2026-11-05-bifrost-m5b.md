# Bifrost M5b (Finish, part 2: info panels, theme, smoke test, DMG) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show Info, the Event log, the Usage HUD and the Service status panel, the theme check and the Bifrost icon, a Playwright smoke test with a fake `claude`, and a universal DMG with an ad-hoc signature that the user installs on his Mac.

**Architecture:** The main process gives the new data: more fields of the Live usage data in each row, the newest rate limits, a ring buffer of the last 5,000 live state events, a PR lookup with `gh`, and one Service status check each minute with the rules of `claude-statusline`. Pure modules format the data for each panel (`info/`, `events/`, `usage/`, `service/`). The panels are M2 panel kinds. The smoke test starts Bifrost in the M5a test home with a fake `claude` on `PATH`. electron-builder makes the DMG.

**Tech Stack:** Electron 44, React 19, Tailwind CSS 4.3.3, Base UI 1.9.0, lucide-react 1.61.0, `@tanstack/react-hotkeys` 0.16.0 (M5a), `@playwright/test` 1.64.1 (new), electron-builder 26.15.3 (present), Biome, Vitest.

**Spec:** `docs/specs/2026-11-04-bifrost-design.md`

This plan comes after M5a (`2026-11-05-bifrost-m5a.md`). It has 9 tasks and its own exit check (Task 9). The exit check is also the exit check of M5: "You install the DMG on your Mac and use Bifrost" (spec 16). The controller builds the DMG and checks that it starts. The user installs it.

**Order:** M4, the tab colours (2231a0a), the Live details plan (`docs/plans/2026-11-05-bifrost-live-mod.md`) and M5a are on `main` before this plan starts. Read the merged code for the exact form of each name.

## Review Focus

1. A status page is down, slow, or gives HTML (a captive portal, or the Mac is offline or asleep). Owner: Task 7 (the test records the SHA-256 of `~/.claude/settings.json`, `~/.claude/plugins/installed_plugins.json` and `~/.claude/plugins/known_marketplaces.json` before the start, and checks them after the quit).

(Rewritten 2026-11-06 for the Live plan. The data comes from the live usage lines, not from status files or hook files.)

**Interfaces:**

- Produces:
  - `src/shared/types.ts`:
    - `interface UsageSnapshot { sessionId: string; name: string; updatedAt: number; limits: RateLimits }`
    - `SessionRow` gets the optional fields `contextWindowSize?: number`, `rateLimits?: RateLimits`, `claudeVersion?: string`, `effort?: string`, `permissionMode?: string`, `transcriptPath?: string`.
  - `live-event.ts`: `LiveUsage` gets `version?: string`, `effort?: string`, `permissionMode?: string`, `transcriptPath?: string`. New `PATH_MAX = 1024`.
  - The mod: the `usage` line gets the optional fields `version`, `effort`, `permissionMode` and `transcriptPath`. A new hook `classic.Stop` (D28).
  - `SessionRegistry.usage(): UsageSnapshot | null`
  - `RegistryService.usage(): UsageSnapshot | null` and `RegistryService.onUsage(cb: (usage: UsageSnapshot | null) => void): void`
  - API: `usage: { get(): Promise<UsageSnapshot | null>; onUpdate(cb: (usage: UsageSnapshot | null) => void): () => void }` (channels `usage:get` with `fromPage`, and `usage:update`).

Rules for the mod (D28):
- Keep three module values: `effort`, `permissionMode` and `transcriptPath`. Each is undefined at the start. Keep one promise of `$.session.version()` for each module load. A rejection gives no version.
- `classic.Stop` (register it with `.catch(($, e, next) => next(e))`): read `e.effort?.level`, `e.permission_mode` and `e.transcript_path`. Keep each one that is a string. Then `return next(e)`. The hook sends nothing and waits for nothing.
- `sendUsage` adds `version` (the `version` of the result), `effort`, `permissionMode` and `transcriptPath` to the `usage` line when each is known. Cut `version`, `effort` and `permissionMode` to `TEXT_MAX`, and `transcriptPath` to 1,024 characters.
- No other hook changes. The mod imports nothing new.

Rules for Bifrost:
- `parseLiveLine` (a usage line): keep `version`, `effort` and `permissionMode` when each is a string that is not empty. Cut each to `TEXT_MAX`. Keep `transcriptPath` when it is a string that starts with `/`, has no line break, and has at most `PATH_MAX` characters. Leave out each bad field and keep the line (the Live rule).
- `toRow`: `contextWindowSize` is `usage.contextWindow`. `rateLimits` is `usage.rateLimits`. `claudeVersion` is `usage.version`. `effort`, `permissionMode` and `transcriptPath` come from the usage line with the same names. A missing value leaves the field out.
- `usage()`: of all usage entries of the registry (also of sessions that are not rows), the entry with the largest `updatedAt` that has `rateLimits`. The `name` is the row name when the registry has the session, else the first 8 characters of the session ID. No entry gives null.
- The service calls each `onUsage` listener after each update that it sends, when the JSON of `usage()` differs from the last value that it sent. `ipc.ts` sends `usage:update`.
- Spec 6.3 (Usage data): add the four optional fields and their sources (D28).

Rules (the `claude-statusline` rules, D20):
- `rank`: `minor` 1, `major` 2, `critical` 3, each other value 0.
- `indicatorOf`: `data.status.indicator` when it is `none`, `minor`, `major`, `critical` or `maintenance`, else null.
- `componentIndicator`: `data.components` must be an array, else null. Skip a component with `group: true`. Skip a component whose `name` matches `ignore`. The weight of a status: `degraded_performance` 1, `partial_outage` 2, `major_outage` 3, else 0. The highest weight 3 gives `critical`, 2 `major`, 1 `minor`. Else any `under_maintenance` gives `maintenance`. Else `none`.
- `parseIncidents`: `data.incidents` must be an array, else `[]`. With `ignore`, keep an incident that has no components, or at least one component whose `name` does not match `ignore`. Each incident: `name` (a string, else `Incident`), `impact` (`rank` mapped back to the word), `status` (a string), `startedAt` (`Date.parse(started_at)`, or null), `rank` = `min(rank(impact), 1)` when `status` is `monitoring`, else `rank(impact)`.
- `combine`: `w` is the highest incident `rank` (0 with no incident). `level` is the word of `w` when `w > rank(indicator)`, else `indicator`. `since` is the oldest `startedAt` of the incidents with `rank >= rank(level)`; else of the incidents with `rank(impact) >= rank(level)`; else of all incidents; null when no incident has a `startedAt`.
- `checkService`:
  1. Fetch `<base>/api/v2/status.json`. A rejection or `indicatorOf` null gives `level: 'unknown'`, `error: "The status page didn't answer."`, no incidents, and no other fetch.
  2. With `ignore`, fetch `<base>/api/v2/components.json`. A good `componentIndicator` replaces the indicator. A failure keeps the indicator.
  3. Fetch `<base>/api/v2/incidents/unresolved.json`. A failure gives `[]`.
  4. `combine`. The incidents go out sorted by `rank` (high first), then by `startedAt` (old first).
- `createServiceMonitor`: `current()` starts with each service at `level: 'unknown'` and `checkedAt: 0`. `start()` runs one round at once: all services with `Promise.all`, then `emit`. The next round starts `intervalMs` after the end of a round. A round never starts while one runs. A `check` that throws gives `unknown` for that service. `stop()` clears the timer, and a round that ends after `stop` does not emit.
- `ipc.ts`: `fetchJson` is `net.fetch(url, { signal: AbortSignal.timeout(FETCH_TIMEOUT_MS), headers: { accept: 'application/json' } })`, then `res.ok` or throw, then `res.json()`. Start the monitor at app start. With a test home, do not start it. `current()` then gives `unknown` with the error `Bifrost doesn't check status pages in a test home.` `service:open-page` refuses an unknown ID with `refused: unknown service`, else `shell.openExternal(def.base)`. Stop the monitor at `will-quit`.
- `errors.ts`: add `'refused: unknown service'` with the text `Bifrost doesn't know that service.` (the M4 test needs an entry for each `refused:` literal).
- `levelText`: `none` `Operational`, `minor` `Minor issue`, `major` `Major outage`, `critical` `Critical outage`, `maintenance` `Maintenance`, `unknown` `No data`.
- `incidentLine`: `<name> - <impact> (<status>)`, then `, for <duration>` when `startedAt` is known (the `formatReset` duration form of Task 4).
- `checkedText`: `checkedAt` 0 gives `Not checked yet.`, else `Checked at HH:MM.`
